# Agent Planning and Execution Protocols

本文件是仓库内规划、执行、验收、进度恢复和模板的权威来源。协议不依赖特定模型，不负责模型选择或切换，也不自动改变客户端的工作模式。用户决定何时规划、何时执行。复杂开发任务使用完整协议；简单且自包含的修改可以直接完成，不强制创建计划目录，但同样必须遵守严格局部验证策略。

## 1. 文件职责与适用规则

```text
AGENTS.md
.agent/
├── PLANS.md
└── plans/
    └── <task-name>/
        ├── PLAN.md
        └── PROGRESS.md
```

- `AGENTS.md`：简短协议入口，以及仓库有效的工程规则、环境与验证要求。
- `.agent/PLANS.md`：完整 Planning Protocol、Execution Protocol 和标准模板。
- `PLAN.md`：稳定执行契约，定义需求、现状、设计、决策、任务依赖、阶段、验收、约束和风险。
- `PROGRESS.md`：唯一动态执行状态来源，记录实际修改、任务状态、验收证据、发现和恢复操作。

`<task-name>` 使用唯一、稳定且可读的目录名，例如用户给出的任务名称对应的英文短名。只为真实需求创建目录；空目录占位文件不代表任务。每个任务有独立 Task ID，任务内部 ID 使用 `T001`、`M001`、`D001`、`A-T001-01`、`A-M001-01`、`A-F001`、`A-X001`（扩展验证）等稳定编号，不复用已删除编号。

PLAN 中不得维护任务完成勾选框、执行状态列或测试通过记录；这些只能写入 PROGRESS。PLAN 的“计划状态”只表示契约成熟度：`DRAFT` / `DECISION_COMPLETE` / `SUPERSEDED`，不表示执行进度。PROGRESS 引用所执行的计划版本；计划版本变化时必须重新检查受影响的进度和验收证据。

本协议优先于与之冲突的仓库工程规则；没有冲突的规则仍然有效。用户明确要求优先于仓库协议，平台和系统权限规则仍须遵守。`.agent/` 的协议、模板、计划和进度允许未来工作、变更历史与检查点；产品文档仍描述当前实现，不以计划替代真实功能说明。

规划应保持业务代码只读，但可以创建或修订本任务的 PLAN 和 PROGRESS。调查阶段先清点并检查所有 Git 跟踪项目文档，再深入核实任务相关事实；同步因本任务发生理解或实现变化的文档，包括关联模块文档，不借此扩张到无关业务功能。重要需求、决策、假设及用户回答必须持久化，不以聊天历史作为唯一信息源。

### 1.1 Strict Local Verification Policy：强制执行约束

除非用户明确要求或授权，Agent 只能构造最小化探针、运行现有局部测试或进行低成本局部静态检查。本策略适用于调查实验、规划、实现、诊断、任务/阶段/最终验收及上下文恢复，不是性能建议。

**默认禁止：**

1. 整个项目的测试套件、模块/包/crate/workspace 的全部或大量测试、完整回归、批量集成及端到端测试。
2. 为局部修改运行大量无关用例；多个子任务完成后自动批量阶段验收；任务结束后自动全量最终验收。
3. 为提高正确性信心、跨模块影响、局部测试失败或全部通过而自主扩大测试范围。
4. 未经用户明确要求，运行耗时较长的全项目构建、检查或测试流程。
5. 通过脚本、Makefile、CI、工具封装、改名或大量独立探针间接实施上述操作。按实际执行范围判断，命令名称、模块/包选择器或存在过滤参数均不能豁免。

默认禁止的命令包括未过滤的 `pytest`、`cargo test`、`ctest`，以及 `cargo test --workspace`、`go test ./...`、执行完整套件的 `make test` / `npm test` / `pnpm test` 和等效脚本。

**默认允许：**

- 最小化探针：只验证当前修改的一个具体行为，有明确输入、预期输出及可判定的通过条件；尽量独立、快速、少初始化，不触发无关构建/测试。可用临时文件或独立测试目录，不为小改动搭建庞大设施。
- 现有局部测试：精确指定文件、函数或用例，只运行一个或少量直接相关案例。运行前通过阅读脚本/配置确认实际选中范围、参数扩展和隐含构建/测试；隐含昂贵批量操作时优先换用最小探针。
- 局部静态验证：阅读相关代码及类型定义、检查目标文件/最小目标、编译最小示例、检查特定 IR 或局部不变量，不扩张为无必要的全项目构建或检查。

每次运行前确定具体性质和能验证它的最小输入，确认整个调用链的实际成本与范围。跨模块行为优先用覆盖必要交互的局部集成探针。每个探针必须有明确目标；优先复用，避免重复、不追求形式覆盖率、不反复验证未受影响的已通过行为，也不将大量独立探针自动组成批量流程。数量和成本与当前变更的实际风险匹配。

**授权与旧计划：**

- PLAN 必须分开定义“默认局部验证”与“需用户明确授权的扩展验证”。规划可说明扩展验证价值，但建议、普通验收描述、计划定稿以及“执行计划”“继续”“完成最终验收”均不构成批量授权。
- 只有可追溯的用户明确要求或授权才允许相应批量操作；记录具体命令或等效操作、测试/构建范围、是否必需、用户指令及适用条件。不得扩大到授权范围之外，也不重复请求已获授权。
- 本策略优先于既有计划和模板中的自动全量要求。恢复旧计划时保留历史事实，移除冲突的自动执行要求，将未授权批量项归入“未执行的扩展验证”，同步 PLAN/PROGRESS；这是执行本策略，不是许可削弱用户明确规定的验收。已有明确用户授权按其范围执行。
- 确认扩展验证不可缺少时，说明具体原因并请求一次授权。未获授权时保留局部结论、记录未覆盖风险，继续可独立完成的工作，不反复请求或无限阻塞。等待时间不构成授权。
- 批量测试未运行本身不构成默认任务失败；只有用户明确将其列为必需验收时，才是未满足的验收要求。

阶段和最终验收通过需求/设计/不变量核对、有效局部证据和必要的最小探针完成，不默认重新运行测试。最终验收不等于完整测试套件执行；局部验收可支持交付，不得描述为全量测试、完整回归通过或排除所有潜在问题。

## 2. 标准调用入口

### Planning

用户要求制订计划时，按 Planning Protocol 调查真实代码，澄清需求并讨论重要技术取舍。达到 Decision Complete 后，交付 `.agent/plans/<task-name>/PLAN.md`，列出完整任务、依赖、阶段以及以局部证据为默认的各级验收流程；扩展验证单列并标注授权要求。初始化 PROGRESS：实现状态 TODO、验证状态 UNVERIFIED、各验收结果 NOT_RUN、当前状态等待用户开始执行。规划请求不授权业务实现；交付计划后不自动执行。

调用示例：`请按 Planning Protocol 为 <需求> 制订计划，保存到 .agent/plans/<task-name>/，本次只规划。`

### Execution

用户要求执行计划时，按 Execution Protocol 阅读指定 PLAN 和 PROGRESS，从持久化信息及真实代码恢复位置，按照依赖完成实施、局部验收及用户明确要求的验收和最终报告。在契约内自主调查、实现、修复和局部验证，不重新开展完整规划，也不重复询问已授权的下一步。执行请求不自动授权批量测试、昂贵全项目流程、Git 提交或推送。“提交完整验收报告”指交付报告，不是创建 Git commit，也不表示执行完整回归。

调用示例：`请按 Execution Protocol 执行 .agent/plans/<task-name>/PLAN.md，持续更新 PROGRESS.md，并完成最终验收。`

恢复示例：`继续执行 .agent/plans/<task-name>/PLAN.md，从 PROGRESS.md 和当前代码恢复。`

如果任务路径不明确，先检查实际目录；只有多个候选无法从请求确定时才询问。若计划缺失、仍为 DRAFT 或有核心未决问题，先说明具体缺口并取得必要决策，不猜测契约，也不把执行请求当作自动接受未决方案。

## 3. Planning Protocol

### 3.1 Codebase Exploration：先调查，再设计

先检查 Git 工作区状态和现有约束，然后根据需求调查：

1. 相关目录、模块及可能受影响的其他模块。
2. 关键类型、函数、接口、调用者和消费者。
3. 当前实现、实际行为、正常路径和错误路径。
4. 架构、依赖方向、所有权、不变量与编码约定。
5. 现有测试、测试数据、构建方式和真实验证入口。
6. 项目文档、已有计划、用户已确定的要求和约束。

所有文件路径、API、语义及测试命令均须来自真实调查；记录证据位置，区分静态阅读、执行验证和未验证推断。不能把文档宣称、泛型声明可编译或旧测试结果当成运行时正确性证据。

区分未知信息：代码位置、接口当前行为、数据结构、测试覆盖等可调查事实，应自主查明；功能应具有什么语义、是否保留行为、合理架构的选择、性能与维护取舍、是否允许公共接口变化等需要用户决定的问题，进入讨论。不得把可调查事实转交用户。

规划原则上仅只读调查业务代码。必须验证的技术假设可以在临时目录或隔离工作区构造最小探针，遵守第 1.1 节，明确目标、输入、预期、环境、结果及局限，保护当前代码与用户修改；结束时清理自己的临时产物，不把实验变成未经授权的业务实施或批量验证。

### 3.2 Intent Clarification：需求澄清

调查后逐项检查功能目标、实施范围、合理解释、用户可观察行为、重要边界、冲突要求、未说明约束、兼容性、安全性及客观完成条件。能够构造一种合理实现不意味着需求已明确；不同解释会产生实质不同的行为或设计时，主动向用户提问。

把需求编号为 `R001` 等，明确范围、非目标、约束及可观察结果，并建立需求到任务、验收的映射。没有实质待决问题时直接完成规划，不为流程强行访谈。

### 3.3 Implementation Discussion：技术方案讨论

分析整体架构、模块职责、数据结构及接口、控制流及数据流、性能及内存开销、正确性、安全性、侵入程度、兼容性、扩展性、维护成本以及验证可行性。多个合理方案会对系统产生实质影响，且既有要求不能决定选择时，向用户解释选项和取舍，不静默采用个人偏好。

### 3.4 决策权限

| 等级 | 决策范围 | 权限 |
| --- | --- | --- |
| Level 1 | 命名、私有辅助函数、等价局部实现、简单重构、既有风格的惯常选择 | 自主决定，无需询问 |
| Level 2 | 内部数据结构、模块职责显著调整、性能与复杂度、维护与扩展取舍 | 多个合理方案且现有约束不能定夺时优先提供选项；影响小、易回退、有明确默认值时可自主选择并记录理由 |
| Level 3 | 可观察语义、公共 API、核心架构、重要兼容性、安全边界、不可逆数据变化、重要不变量、对后续有重大影响的技术选择 | 用户要求或现有权威规范未确定时必须取得用户决策；不得自行采用高影响假设 |

用户已确定或权威规范明确的选择不重复询问，记录具体来源。每个重要决策记录 Decision ID、问题、候选方案、最终选择、理由、等级、来源（用户确认 / 自主决定）和对实现及验收的影响。执行中的重大变更同样遵守该权限。

### 3.5 交互式提问

主动寻找值得用户决定的问题，不等到完全无法推进才提问。优先使用当前环境实际可调用且模式允许的结构化提问工具；没有适用工具时用普通对话，不假设工具存在或能够切换模式。

每个重要问题包含：

- **Question**：需要决定什么。
- **Context**：为什么必须决定，以及已调查的事实。
- **Options**：通常 2～4 个合理、可区分的方案；数量受工具限制时适应工具。
- **Tradeoffs**：各方案主要优缺点。
- **Recommendation**：推荐及依据。
- **Impact**：影响的功能、契约、设计和验收。

工具字段较少时将必要说明放入问题或选项描述。一次优先提出 1～3 个相关问题；有依赖的问题分轮讨论。收到回答后重新分析并及时持久化，必要时继续提问，无固定轮数。不重复已答问题，不询问可调查事实、无关细节或形式上的“是否继续”。等待必要决策时继续独立调查，但不能替用户决定依赖项；等待时长或未回复不等于同意。

### 3.6 Decision Complete 与规划质量

仅在以下检查全部满足后将计划标记为 DECISION_COMPLETE：

1. 需求、目标、功能边界和非目标明确且完整覆盖。
2. 核心语义、必要边界及重要非功能约束明确。
3. 重要接口、核心架构和重大决策确定，来源可追溯。
4. 没有会显著改变设计的未决问题或未经确认的高影响假设。
5. 技术设计具体，执行者无需重新作重大需求或设计决策。
6. 任务粒度合理，具备明确目标、可独立验证且依赖无环。
7. 每个任务有具体行为、最小输入、预期、局部测试或探针及通过条件；阶段及最终验收可操作且覆盖需求，复用有效局部证据。
8. 命令真实且实际范围明确；执行时发现的命令有具体发现方法和验证目标；扩展验证及其授权/必需性独立列明，不默认要求完整构建或批量回归。
9. 计划可脱离聊天独立执行，普通工程细节留给执行者。

有缺口时继续调查或讨论，可以保存 DRAFT 和未决问题，不把草案冒充最终计划。最终交付指出计划路径、版本、主要决策和验收边界，初始化 PROGRESS 后等待用户启动执行。

## 4. PLAN.md 契约规范

### 4.1 Self-contained

假设执行者没有聊天历史或规划时的内部推理，只能读取当前仓库、PLAN 和 PROGRESS，且会遇到上下文压缩。计划必须直接写明关键需求、设计、决策和操作；可以链接仓库代码及持久化文档，但不能只引用对话或临时笔记。

禁止以“按照之前讨论的方案实现”“参考之前的约定”“其余部分同上”“按常规方式实现”“完善相关逻辑”“处理所有边界条件”等代替具体契约。非适用内容注明“不适用”及理由，不能默默遗漏关键字段。

### 4.2 必须包含的章节

| 章节 | 必须记录的内容 |
| --- | --- |
| Overview | Task ID、Task Name、概要、计划版本、契约状态 |
| Objectives | 背景、目标、预期行为、范围、非目标、全局约束、交付物、需求映射 |
| Codebase Context | 已核实模块及文件、关键类型和函数、当前实现、接口和约定、受影响模块、构建测试方式及调查证据 |
| Design Decisions | 每个重要决策的完整记录、等级、来源；未决问题仅存在于草案 |
| Assumptions | 假设、依据、验证状态、影响、验证方法；核心高影响假设须在定稿前解决 |
| Technical Design | 架构、职责、数据结构、类型和接口、控制流及数据流、语义、状态转换、不变量、错误路径、边界、兼容性、性能安全及集成 |
| Implementation Tasks | 稳定任务 ID、Goal、Dependencies、Scope、Implementation、Constraints、待验证行为、最小输入、局部测试/探针、预期输出与通过条件、验收 ID |
| Milestones | 稳定阶段 ID、目标、任务列表、前置依赖、交付物、阶段验收和完成条件 |
| Risks and Recovery | 技术风险、待验证的非核心假设、可能失败环节、处理和恢复/回退方法 |
| Acceptance Plan | 默认局部验收的各级定义、实际选中范围与隐含成本、真实命令、证据复用、预期和通过条件；扩展验证及用户授权要求单列 |
| Plan Change History | 版本、变更原因、具体修改、决策来源、受影响任务及验收；不记录任务完成状态 |

### 4.3 任务粒度与依赖

每个 T 编号对应一个主要逻辑目标，覆盖该目标所需的层、调用者、资源所有权、错误路径、配对实现及测试，能够形成一次完整实现与验证循环。任务不是按文件或工具调用拆出的空脚手架。

依赖显式列出任务 ID，无依赖写“无”，依赖图不得有环。任务尽可能完成后保持项目可构建/验证，不合并无关子系统，过大目标继续拆分；“完成整个类型系统”“完善编译器”“优化所有性能问题”不构成可执行任务。任务和阶段不等同于提交：只有用户授权，且形成完整可用的评审单元时才提交，不为检查点提交半成品。

## 5. 验收计划

所有验收使用稳定且唯一的 Acceptance ID，记录所属任务/阶段、具体行为、最小输入、验证方法、实际范围与隐含成本、工作目录及环境、命令或操作步骤、预期和通过标准，并注明类别（默认局部 / 扩展）、是否必需及必需性来源。默认任务、阶段和最终局部验收为必需；扩展验证单列，只有用户明确列为必需时才进入完成门禁。用户授权可选扩展运行不等于将其设为必需。不在失败后降级已明确的必需项；不适用类别注明理由，不伪造 PASS。

### 5.1 Task Acceptance

每个 Implementation Task 优先定义待验证的具体行为、最小输入、预期输出、精确的现有局部测试或需构造的探针以及客观通过条件。按实际风险选择必要正常/边界/错误路径及不变量，不机械展开大量案例。缺少必要验证时将最小探针或扩展现有相关案例写入任务，优先复用文件和编译单元。手动/静态检查写明目标、操作和可观察结果。“代码已实现”不是验证通过依据，不默认要求完整构建或批量回归。

### 5.2 Milestone Acceptance

每个阶段定义局部验收：核对任务完成情况、相关代码、关键语义与不变量，复用仍有效的任务证据；仅为关键交互缺口运行最小集成探针。不因进入新阶段重跑所有相关测试，不自动触发集成套件或批量回归。失败后修复并只重验受影响行为；必需验收失败时不得无条件推进依赖阶段，可以推进不依赖失败部分的任务并说明隔离依据。

### 5.3 Final Acceptance

PLAN 必须为最终验收列出完整清单，按实际任务覆盖：

- 需求完整性：逐条用户需求、功能边界及边界行为。
- 功能正确性：可观察行为、错误处理及不变量。
- 架构一致性：符合设计，接口变更有授权，兼容性成立。
- 局部验证证据：检查已有局部测试/探针结果对当前代码是否仍有效，仅为尚未验证的关键行为补充最小探针；检查已知失败、未解决问题和未覆盖风险。
- 交付完整性：实现和文档完整，无遗留临时实现，披露阻塞及未验证项。

最终验收是实现完整性与证据有效性检查，可以通过局部证据完成；不要求独立重新执行已通过且未受影响的检查，不等于完整测试套件执行。更广保证所需的批量测试记录为“未执行的扩展验证”，未明确授权不得执行；用户明确要求的扩展验收按其范围另行核对。

不得使用“确保没有 Bug”“检查功能正常”代替验证操作。调查时核实脚本、参数、实际用例数量、隐含构建/测试、环境和预期。若执行时才确定命令，写明从哪些配置、脚本或帮助输出发现，以及必须证明的行为；执行时补齐具体命令并再次检查第 1.1 节边界，不编造命令。

### 5.4 本仓库工程约束

所有任务默认只选择最小局部检查；纯文档任务可通过针对文本的静态一致性检查验收。命令由 AGENTS 的环境及检查章节、真实脚本、配置和现有测试确定；命令示例不授予执行权限。需要编译器环境时使用仓库根目录及 `yian-env`，记录安装前缀。

- `yianc` 的 Python 和 native 支持行为、契约、消费者及相关层同步实现；包管理器只有 `bootstrap/anx/` 原生实现。包管理器改动应按适用范围核对 Python/native compiler 对同一 v2 package-map 契约的消费，不因此扩大验证范围。
- 编译器及包管理器以相同最小案例验证两种实现，不自动运行配对套件。`scripts/run_tests.py` 默认 `--implementation both`，仅使用现有原生工具且不会刷新；过滤参数可能仍匹配大量用例或间接执行整个包测试，必须先检查真实范围与成本。单一实现结果只支持该实现，另一实现无法在授权范围内检查时明确记录缺口。
- native 验证必须使用与相关源码匹配的二进制，安装和验证采用同一环境及前缀。可复用已有且确认有效的产物；源码漂移后需先用显式的 `scripts/refresh_toolchain.sh` 更新兼容native seed，若没有兼容seed则用 `scripts/bootstrap_toolchain.sh` cold建立，再验证；这些入口仍受昂贵构建授权约束。需要授权而未获授权时先完成独立局部工作，将native验证记为UNVERIFIED，不用旧二进制冒充验证。LSP与compiler/anx一起由warm refresh构建。
- 各级验收复用有效证据，同一份局部证据可关联多个 ID；每个门禁单独核对适用性，不强制新增一轮运行。
- 不因检查点、阶段切换或最终验收重跑未受影响的行为；修复、契约变更、代码漂移或证据失效后只重跑受影响的局部项。保留失败证据、未验证项及未执行的扩展验证。
- 保留用户修改；仅显式授权时提交，不擅自推送，提交前检查 tracked/untracked 范围及 `git diff --check`、`git diff --cached --check`。

## 6. Execution Protocol

### 6.1 初始化与恢复

每次开始执行、新会话接手或恢复时依次：

1. 阅读 AGENTS 及适用目录规则。
2. 阅读 `.agent/PLANS.md`。
3. 阅读指定任务 PLAN，确认版本、契约成熟度、执行授权及扩展验证的具体用户授权；按第 1.1 节处理旧计划的冲突条款。
4. 阅读 PROGRESS，分别确认实现状态、验证状态、基线、有效证据、未执行扩展项、执行位置和未决事项。
5. 检查 `git status --short`，必要时检查 diff、分支及提交；记录用户已有修改。
6. 核查相关代码和测试现状，确认进度与实现、版本及已运行证据一致。
7. 冲突时自主调查、局部验证并修正记录；无法确认的验证状态标记 UNVERIFIED，实现状态按真实代码单独记录，不能只信日志，也不通过重跑批量测试恢复状态。
8. 选择第一个未完成且任务、阶段依赖均满足的任务，更新当前执行位置。

不得覆盖或丢弃用户未提交修改。恢复时未提交但已验证的工作可能有效，必须检查实际内容；区分已提交、当前工作区和未知状态，不把提交存在作为验收证据。

### 6.2 单任务执行循环

`读取任务与依赖 → 理解代码 → 实现 → 构造最小探针或选择局部测试 → 验证 → 分析结果 → 必要时修复并局部重验 → 更新进度`

修改前核对设计、约束、接口和风格，将实现状态标为 IN_PROGRESS。在方案内自主处理工程细节，保持核心语义；实现完整后标 IMPLEMENTED，不与验证结论混用。每次验证前明确具体性质并按第 1.1 节选择最小检查，不能因修改某模块就运行该模块全部测试，或因可能影响其他模块就运行项目回归。默认局部必需项通过且证据有效后标 LOCALLY_VERIFIED；用户明确要求的全部验收通过时方可标 FULLY_VERIFIED，并注明具体范围。必要验证缺失/失败/失效时标 UNVERIFIED；无法继续的实现工作标 BLOCKED 并记录原因和解除条件。

局部失败后分析输出、代码和日志，定位根因，必要时缩小输入，修复后重跑对应探针/局部测试。无法定位时继续代码分析、日志和更有针对性的探针，禁止自动扩大到批量测试。保持原断言和预期，不以弱化测试掩盖问题。

每完成一个任务更新可靠 Checkpoint，包括实际文件、分别记录的实现与验证状态、真实命令、结果和下一步。不自动追加批量测试；不因普通实现困难反复询问用户，也不以写完代码宣称验证通过。

### 6.3 阶段执行循环

开始阶段前重读相关设计、依赖及阶段验收。完成阶段任务后核对实现、代码及关键不变量，复用有效局部证据，仅为未覆盖的关键交互构造最小集成探针。修复后只重验受影响项，不因任务数量或阶段结束自动运行批量集成/回归或重建。必需局部阶段验收及用户明确列为必需的扩展项通过后，才进入依赖该阶段的后续阶段；未授权的扩展建议不构成默认门禁。

### 6.4 最终验收循环

所有实施任务实现完成后，进行最终需求与证据核对，不另设强制重跑阶段：

1. 重新阅读 PLAN 最终清单及全局约束。
2. 逐项核对实现完整性、关键设计约束和已有证据有效性；复用有效局部结果，注明原命令、基线和证据 ID。
3. 对尚未验证的关键行为构造最小探针；分析失败并在设计范围内修复，记录实际命令、环境、输出及退出码。
4. 使受影响证据失效并只局部重验对应行为，不重复运行未受影响检查，不自动执行完整相关回归。
5. 核对已知失败、未解决问题、未执行扩展验证及用户明确要求项，检查代码、文档、PLAN 和 PROGRESS 一致。
6. 分开更新实现/验证状态、证据和恢复信息，交付局部验收结论及风险。仅在用户明确授权范围内运行扩展验证。

不能跳过最终核对，也不能为通过检查删除失败测试、放宽用户明确要求、静默修改预期或宣称未经验证的成功。有效局部证据足以完成默认最终验收，不能将其报告成完整回归通过。批量测试未授权时记录缺口，不能为满足旧模板而自行执行。

### 6.5 自主性与重新决策

在已确定契约内自主调查、实现和修复，Level 1 和允许的 Level 2 调整无需重新许可。只有需要改变用户明确需求、核心语义、重大架构、明确兼容性、不可违反约束，或遇到无法在现有契约内消除的重大设计冲突时，重新征求用户决策。说明事实、原因、影响、选项和推荐，将依赖该决策的工作标记 BLOCKED；继续可独立推进的工作，不静默变更核心设计。

所需工具或依赖缺失时，可以依 AGENTS 请求用户完成环境配置；明确缺失项、所需操作和未运行验收，环境恢复后继续。环境阻塞不是功能验收通过，也不应伪造替代验证。

## 7. PROGRESS.md 状态与证据

### 7.1 Current Status

实现状态与验证状态分别记录，禁止让单一 DONE 状态同时表达两者：

| 维度 | 状态 | 含义 |
| --- | --- | --- |
| Implementation Status | TODO | 尚未开始实现 |
| Implementation Status | IN_PROGRESS | 正在实现或修复 |
| Implementation Status | IMPLEMENTED | 本任务要求的实现完整，不表达测试结果 |
| Implementation Status | BLOCKED | 实现无法继续，明确原因、依赖及解除条件 |
| Verification Status | UNVERIFIED | 必要验证未完成、失败或证据失效；由具体验收结果区分原因 |
| Verification Status | LOCALLY_VERIFIED | 默认必需局部测试、探针或静态检查通过，证据仍有效；仅证明注明范围 |
| Verification Status | FULLY_VERIFIED | 全部用户明确要求的验收已通过，证据仍有效；必须关联具体用户要求及范围 |

任务表是唯一任务实现与验证清单。Current Status 的当前阶段、任务及下一步引用此表，不另建重复完成列表。IMPLEMENTED + LOCALLY_VERIFIED 可关闭默认局部任务；用户明确必需的扩展验收缺失时，即使局部已通过也必须注明整体必需验收未满足，不得关闭该门禁。无明确用户验收清单时默认报告 LOCALLY_VERIFIED，不以 FULLY_VERIFIED 暗示穷尽测试。FULLY_VERIFIED 不等于全项目测试通过，除非用户要求且实际运行的正是该范围。

阶段同样分列实现和验证状态，并关联阶段证据，不能从任务实现完成自动推定阶段通过。等待执行、执行中、等待决策、环境阻塞、最终验收中、局部验收完成、明确要求的验收完成等文字用于工作流位置，不代替两种状态。验证因环境或授权无法继续时，保留真实实现状态，验证为 UNVERIFIED 并记录阻塞原因；已通过的局部证据不因此抹除。恢复旧 DONE 状态时先核对真实实现及证据再拆分，不能直接推定 FULLY_VERIFIED。

### 7.2 Checkpoint 与 Acceptance Results

记录最新可靠检查点：最近完成工作、修改文件、当前代码及工作区状态、最近局部验证及结果、下一步。证据包含 Acceptance ID、实际方法、验证目标与最小输入、实际选中范围及隐含操作、授权依据（扩展项）、环境/目录/版本/指针模式（适用时）、命令或手动操作、结果及退出码、PASS / FAIL / NOT_RUN、失败原因、修复和重验记录。未运行永远 NOT_RUN，运行中不能提前 PASS。复用有效证据时引用原记录及当前适用性，不编造一次新运行。

证据失效时保留原结果摘要并说明失效原因，将受影响验收结果恢复为 NOT_RUN，关联验证状态改为 UNVERIFIED；只有确需实现修复时才将实现状态重新打开为 IN_PROGRESS。记录代码基线及相关未提交 diff 范围；日志路径不是唯一证据，应保留足够摘要。未执行扩展项单列授权、必需性、未运行原因和未覆盖风险，不伪装为失败或默认完成障碍。

### 7.3 Decision Log、Discoveries 与 Recovery Instructions

执行中的重要决策记录 ID、等级、问题、理由、影响、来源和对应计划版本；稳定契约变化同步 PLAN 的决策及历史，动态日志引用同一 ID，不维护第二份冲突设计。发现记录代码与计划差异、技术限制、边界、风险和计划外问题，明确是否影响当前任务，避免顺便实现无关功能。

Recovery Instructions 明确当前任务、两种状态所在表及有效证据、未完成实现和必要局部验证、扩展验证的用户授权范围/必需性及未运行项、下一步最小操作、优先阅读文件、环境以及未提交修改归属。记录简洁，保留最新可靠检查点、重要决策和失败修复证据，合并重复日志，不无限追加同义进度。

## 8. 上下文压缩与会话恢复

假设会话可中断、聊天可丢失、早期约束可因压缩遗漏。重要信息即时持久化；每完成任务更新检查点，进入新阶段、跨模块实施或重要验证前重查设计、局部证据及授权边界。中途需交接时保存准确检查点，包括两种状态、不完整修改、正在运行的验证和下一步，不把未验证行为标为已通过，也不为恢复信心重新批量运行。

状态不明确时从持久化文件和实际代码恢复，不能因缺失上下文猜测原始需求。无需无意义重读全部文件，但必须保证当前工作所依赖的约束有效。PROGRESS 必须足以使全新会话继续。

## 9. 计划变更

不影响契约的普通实现细节可自主调整并记录。用户需求、确认的重大设计、语义及不变量、公共 API、重要兼容性和全局验收标准不得擅自改变。

发现计划错误时：核实代码和问题 → 分析影响 → 优先在原约束内解决 → 普通工程调整自主处理并记录 → 核心变更取得用户决策 → 修订版本、决策、相关任务和验收 → 记录原因及历史 → 更新 PROGRESS 引用版本并使受影响证据失效。

历史包含足够具体的变更及来源，不能只写“用户同意”或引用聊天。变更后仍需满足 Decision Complete，禁止用修改契约掩盖失败；必要标准变化必须由用户明确决定并披露，不可静默降级。

执行第 1.1 节对旧计划的迁移要求时，不将未经授权的历史批量要求当作既定用户标准。保留需求与设计、原证据和变更依据，仅调整冲突的执行要求；用户明确必需的批量验收仍保留，未满足时如实报告。

## 10. 执行完成条件与报告

实现完成条件：本任务所有实施任务为 IMPLEMENTED，功能边界及核心设计语义符合、必要文档同步、PLAN/PROGRESS/真实代码一致。此时可报告“实现完成”，验证结果另述。

默认局部完成门禁：实现完成，任务、阶段及最终的必需局部验收均 PASS、证据有效，且没有未披露的失败或阻塞。可以报告 IMPLEMENTED / LOCALLY_VERIFIED 并交付；未运行批量测试不使该结论失败。用户明确必需的扩展验收尚未通过时，应同时报告“局部验收通过，用户要求的验收尚未全部满足”。全部明确要求项通过后可报告 FULLY_VERIFIED，必须注明其有限范围。

最终报告清晰列出：

1. 实际实现工作、能力及交付物，实现状态。
2. 实际使用或复用的最小探针、局部测试和静态检查，输入、命令/操作及证据 ID。
3. 各项实际结果、验证状态、最终需求与设计核对结论。
4. 哪些批量测试/昂贵流程没有执行、授权和必需性；无相关扩展项时明确写无。

## 11. 标准模板使用规则

以下模板只包含占位内容，不是具体任务。Planning 时复制到真实任务目录后填写；所有 `<...>`、待填写内容和不可执行的操作描述必须在定稿前替换。章节不适用时保留理由。按实际任务复制任务、阶段、决策和验收块；编号只示范格式，必须保持实际引用一致。
