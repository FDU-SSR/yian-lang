# Agent Planning and Execution Protocols

本文件是仓库内规划、执行、验收、进度恢复和模板的权威来源。协议不依赖特定模型，不负责模型选择或切换，也不自动改变客户端的工作模式。用户决定何时规划、何时执行。它适用于复杂开发任务；简单且自包含的修改可以直接完成，不强制创建计划目录。

## 1. 文件职责与适用规则

```text
AGENTS.md
.agent/
├── PLANS.md
└── plans/
    └── <task-name>/
        ├── PLAN.md
        └── PROGRESS.md
```

- `AGENTS.md`：简短协议入口，以及仓库有效的工程规则、环境与验证要求。
- `.agent/PLANS.md`：完整 Planning Protocol、Execution Protocol 和标准模板。
- `PLAN.md`：稳定执行契约，定义需求、现状、设计、决策、任务依赖、阶段、验收、约束和风险。
- `PROGRESS.md`：唯一动态执行状态来源，记录实际修改、任务状态、验收证据、发现和恢复操作。

`<task-name>` 使用唯一、稳定且可读的目录名，例如用户给出的任务名称对应的英文短名。只为真实需求创建目录；仓库中的 `.gitkeep` 仅用于保留空目录，不代表任务。每个任务有独立 Task ID，任务内部 ID 使用 `T001`、`M001`、`D001`、`A-T001-01`、`A-M001-01`、`A-F001` 等稳定编号，不复用已删除编号。

PLAN 中不得维护任务完成勾选框、执行状态列或测试通过记录；这些只能写入 PROGRESS。PLAN 的“计划状态”只表示契约成熟度：`DRAFT` / `DECISION_COMPLETE` / `SUPERSEDED`，不表示执行进度。PROGRESS 引用所执行的计划版本；计划版本变化时必须重新检查受影响的进度和验收证据。

本协议优先于与之冲突的仓库工程规则；没有冲突的规则仍然有效。用户明确要求优先于仓库协议，平台和系统权限规则仍须遵守。`.agent/` 的协议、模板、计划和进度允许未来工作、变更历史与检查点；产品文档仍描述当前实现，不以计划替代真实功能说明。

规划应保持业务代码只读，但可以创建或修订本任务的 PLAN 和 PROGRESS。调查阶段先清点并检查所有 Git 跟踪项目文档，再深入核实任务相关事实；同步因本任务发生理解或实现变化的文档，包括关联模块文档，不借此扩张到无关业务功能。重要需求、决策、假设及用户回答必须持久化，不以聊天历史作为唯一信息源。

## 2. 标准调用入口

### Planning

用户要求制订计划时，按 Planning Protocol 调查真实代码，澄清需求并讨论重要技术取舍。达到 Decision Complete 后，交付 `.agent/plans/<task-name>/PLAN.md`，列出完整任务、依赖、阶段以及任务级、阶段级、最终验收流程，并初始化 PROGRESS：所有任务 TODO、所有验收 NOT_RUN、当前状态等待用户开始执行。规划请求不授权业务实现；交付计划后不自动执行。

调用示例：`请按 Planning Protocol 为 <需求> 制订计划，保存到 .agent/plans/<task-name>/，本次只规划。`

### Execution

用户要求执行计划时，按 Execution Protocol 阅读指定 PLAN 和 PROGRESS，从持久化信息及真实代码恢复位置，按照依赖完成实施、各级验收和最终报告。在契约内自主调查、实现、修复和验证，不重新开展完整规划，也不重复询问已授权的下一步。执行请求不自动授权 Git 提交或推送；遵守 AGENTS 中的显式提交授权规则。“提交完整验收报告”指交付报告，不是创建 Git commit。

调用示例：`请按 Execution Protocol 执行 .agent/plans/<task-name>/PLAN.md，持续更新 PROGRESS.md，并完成最终验收。`

恢复示例：`继续执行 .agent/plans/<task-name>/PLAN.md，从 PROGRESS.md 和当前代码恢复。`

如果任务路径不明确，先检查实际目录；只有多个候选无法从请求确定时才询问。若计划缺失、仍为 DRAFT 或有核心未决问题，先说明具体缺口并取得必要决策，不猜测契约，也不把执行请求当作自动接受未决方案。

## 3. Planning Protocol

### 3.1 Codebase Exploration：先调查，再设计

先检查 Git 工作区状态和现有约束，然后根据需求调查：

1. 相关目录、模块及可能受影响的其他模块。
2. 关键类型、函数、接口、调用者和消费者。
3. 当前实现、实际行为、正常路径和错误路径。
4. 架构、依赖方向、所有权、不变量与编码约定。
5. 现有测试、测试数据、构建方式和真实验证入口。
6. 项目文档、已有计划、用户已确定的要求和约束。

所有文件路径、API、语义及测试命令均须来自真实调查；记录证据位置，区分静态阅读、执行验证和未验证推断。不能把文档宣称、泛型声明可编译或旧测试结果当成运行时正确性证据。

区分未知信息：代码位置、接口当前行为、数据结构、测试覆盖等可调查事实，应自主查明；功能应具有什么语义、是否保留行为、合理架构的选择、性能与维护取舍、是否允许公共接口变化等需要用户决定的问题，进入讨论。不得把可调查事实转交用户。

规划原则上仅只读调查业务代码。必须验证的技术假设可以在临时目录或隔离工作区进行实验，明确目标、环境、结果及局限，保护当前代码与用户修改；结束时清理自己的临时产物，不把实验变成未经授权的业务实施。

### 3.2 Intent Clarification：需求澄清

调查后逐项检查功能目标、实施范围、合理解释、用户可观察行为、重要边界、冲突要求、未说明约束、兼容性、安全性及客观完成条件。能够构造一种合理实现不意味着需求已明确；不同解释会产生实质不同的行为或设计时，主动向用户提问。

把需求编号为 `R001` 等，明确范围、非目标、约束及可观察结果，并建立需求到任务、验收的映射。没有实质待决问题时直接完成规划，不为流程强行访谈。

### 3.3 Implementation Discussion：技术方案讨论

分析整体架构、模块职责、数据结构及接口、控制流及数据流、性能及内存开销、正确性、安全性、侵入程度、兼容性、扩展性、维护成本以及验证可行性。多个合理方案会对系统产生实质影响，且既有要求不能决定选择时，向用户解释选项和取舍，不静默采用个人偏好。

### 3.4 决策权限

| 等级 | 决策范围 | 权限 |
| --- | --- | --- |
| Level 1 | 命名、私有辅助函数、等价局部实现、简单重构、既有风格的惯常选择 | 自主决定，无需询问 |
| Level 2 | 内部数据结构、模块职责显著调整、性能与复杂度、维护与扩展取舍 | 多个合理方案且现有约束不能定夺时优先提供选项；影响小、易回退、有明确默认值时可自主选择并记录理由 |
| Level 3 | 可观察语义、公共 API、核心架构、重要兼容性、安全边界、不可逆数据变化、重要不变量、对后续有重大影响的技术选择 | 用户要求或现有权威规范未确定时必须取得用户决策；不得自行采用高影响假设 |

用户已确定或权威规范明确的选择不重复询问，记录具体来源。每个重要决策记录 Decision ID、问题、候选方案、最终选择、理由、等级、来源（用户确认 / 自主决定）和对实现及验收的影响。执行中的重大变更同样遵守该权限。

### 3.5 交互式提问

主动寻找值得用户决定的问题，不等到完全无法推进才提问。优先使用当前环境实际可调用且模式允许的结构化提问工具；没有适用工具时用普通对话，不假设工具存在或能够切换模式。

每个重要问题包含：

- **Question**：需要决定什么。
- **Context**：为什么必须决定，以及已调查的事实。
- **Options**：通常 2～4 个合理、可区分的方案；数量受工具限制时适应工具。
- **Tradeoffs**：各方案主要优缺点。
- **Recommendation**：推荐及依据。
- **Impact**：影响的功能、契约、设计和验收。

工具字段较少时将必要说明放入问题或选项描述。一次优先提出 1～3 个相关问题；有依赖的问题分轮讨论。收到回答后重新分析并及时持久化，必要时继续提问，无固定轮数。不重复已答问题，不询问可调查事实、无关细节或形式上的“是否继续”。等待必要决策时继续独立调查，但不能替用户决定依赖项；等待时长或未回复不等于同意。

### 3.6 Decision Complete 与规划质量

仅在以下检查全部满足后将计划标记为 DECISION_COMPLETE：

1. 需求、目标、功能边界和非目标明确且完整覆盖。
2. 核心语义、必要边界及重要非功能约束明确。
3. 重要接口、核心架构和重大决策确定，来源可追溯。
4. 没有会显著改变设计的未决问题或未经确认的高影响假设。
5. 技术设计具体，执行者无需重新作重大需求或设计决策。
6. 任务粒度合理，具备明确目标、可独立验证且依赖无环。
7. 每个任务有客观验收；阶段及最终验收可操作且覆盖需求。
8. 命令真实；必须执行时发现的命令有具体发现方法和验证目标。
9. 计划可脱离聊天独立执行，普通工程细节留给执行者。

有缺口时继续调查或讨论，可以保存 DRAFT 和未决问题，不把草案冒充最终计划。最终交付指出计划路径、版本、主要决策和验收边界，初始化 PROGRESS 后等待用户启动执行。

## 4. PLAN.md 契约规范

### 4.1 Self-contained

假设执行者没有聊天历史或规划时的内部推理，只能读取当前仓库、PLAN 和 PROGRESS，且会遇到上下文压缩。计划必须直接写明关键需求、设计、决策和操作；可以链接仓库代码及持久化文档，但不能只引用对话或临时笔记。

禁止以“按照之前讨论的方案实现”“参考之前的约定”“其余部分同上”“按常规方式实现”“完善相关逻辑”“处理所有边界条件”等代替具体契约。非适用内容注明“不适用”及理由，不能默默遗漏关键字段。

### 4.2 必须包含的章节

| 章节 | 必须记录的内容 |
| --- | --- |
| Overview | Task ID、Task Name、概要、计划版本、契约状态 |
| Objectives | 背景、目标、预期行为、范围、非目标、全局约束、交付物、需求映射 |
| Codebase Context | 已核实模块及文件、关键类型和函数、当前实现、接口和约定、受影响模块、构建测试方式及调查证据 |
| Design Decisions | 每个重要决策的完整记录、等级、来源；未决问题仅存在于草案 |
| Assumptions | 假设、依据、验证状态、影响、验证方法；核心高影响假设须在定稿前解决 |
| Technical Design | 架构、职责、数据结构、类型和接口、控制流及数据流、语义、状态转换、不变量、错误路径、边界、兼容性、性能安全及集成 |
| Implementation Tasks | 稳定任务 ID、Goal、Dependencies、Scope、Implementation、Constraints、Acceptance Criteria、Verification Steps、Expected Results |
| Milestones | 稳定阶段 ID、目标、任务列表、前置依赖、交付物、阶段验收和完成条件 |
| Risks and Recovery | 技术风险、待验证的非核心假设、可能失败环节、处理和恢复/回退方法 |
| Acceptance Plan | 任务、阶段、最终验收的完整定义、真实命令、预期和通过条件 |
| Plan Change History | 版本、变更原因、具体修改、决策来源、受影响任务及验收；不记录任务完成状态 |

### 4.3 任务粒度与依赖

每个 T 编号对应一个主要逻辑目标，覆盖该目标所需的层、调用者、资源所有权、错误路径、配对实现及测试，能够形成一次完整实现与验证循环。任务不是按文件或工具调用拆出的空脚手架。

依赖显式列出任务 ID，无依赖写“无”，依赖图不得有环。任务尽可能完成后保持项目可构建/验证，不合并无关子系统，过大目标继续拆分；“完成整个类型系统”“完善编译器”“优化所有性能问题”不构成可执行任务。任务和阶段不等同于提交：只有用户授权，且形成完整可用的评审单元时才提交，不为检查点提交半成品。

## 5. 验收计划

所有验收使用稳定且唯一的 Acceptance ID，记录所属任务/阶段、要求、验证方法、工作目录及环境、命令或操作步骤、预期结果和通过标准，并注明是否必需。所有任务级和阶段级验收均为必需；最终验收默认必需，可选项须在定稿时明确及说明原因，不得在失败后降级。不适用类别应在 PLAN 中说明理由，不伪造 PASS。

### 5.1 Task Acceptance

按任务性质覆盖正常输入、重要边界、异常及错误处理、核心不变量、兼容性和可能回归。优先自动化；缺少必要测试时把创建或扩展测试写入实施任务，优先复用现有相关文件和编译单元。手动检查写明输入、操作和可观察输出。“代码已实现”不是通过依据。

### 5.2 Milestone Acceptance

每个阶段独立定义验收，检查阶段所有任务、跨任务集成、关键语义与不变量、整体功能及相关回归。失败时修复并重验；不得在阶段存在已知必需验收失败时无条件推进依赖它的阶段。可以推进不依赖失败部分的任务，但必须明确隔离依据。

### 5.3 Final Acceptance

PLAN 必须为最终验收列出完整清单，按实际任务覆盖：

- 需求完整性：逐条用户需求、功能边界及边界行为。
- 功能正确性：可观察行为、错误处理及不变量。
- 架构一致性：符合设计，接口变更有授权，兼容性成立。
- 测试与回归：适用的单元、集成、端到端、构建、静态及已有回归检查。
- 交付完整性：实现和文档完整，无遗留临时实现，披露阻塞及未验证项。

不得使用“确保没有 Bug”“检查功能正常”代替验证操作。调查时核实脚本、参数、用例、构建环境和预期。若必须执行时才确定命令，写明从哪些配置、脚本或帮助输出发现，以及必须证明的行为；执行时补齐具体命令并记录依据，不编造命令。

### 5.4 本仓库工程约束

在计划中选择实际相关检查，不要求纯文档任务运行编译器全集。命令由 AGENTS 的环境及检查章节、真实脚本、配置和现有测试确定；使用仓库根目录及 `yian-env`，记录安装前缀。

- `yianc` 的 Python 和 native 支持行为、契约、消费者及测试同步实现，包括 `frontend/`、`semantic/` 等共享层与对应 bootstrap 包；`anx` 同步 Python 和 native 实现。
- 编译器及包管理器相关测试用相同案例执行两种实现。`scripts/run_tests.py` 默认 `--implementation both`，运行前自动刷新原生工具；单一实现仅用于诊断，不替代配对验收。
- 修改编译器或包管理器后，直接验证 native 前必须通过 `scripts/install.sh` 刷新，安装和验证使用相同 Python 环境及前缀。LSP 通过 `scripts/install_lsp.sh` 单独刷新。
- 任务级、阶段级检查可以聚焦相关案例，最终验收运行计划确定的完整相关检查。最终验收必须独立执行，不能以早期阶段的通过记录代替；同一轮最终运行可支持多个验收 ID。
- 不因记录检查点无意义重跑；修复、契约变更、代码漂移或证据失效后重跑受影响项。保留失败证据和验证缺口。
- 保留用户修改；仅显式授权时提交，不擅自推送，提交前检查 tracked/untracked 范围及 `git diff --check`、`git diff --cached --check`。

## 6. Execution Protocol

### 6.1 初始化与恢复

每次开始执行、新会话接手或恢复时依次：

1. 阅读 AGENTS 及适用目录规则。
2. 阅读 `.agent/PLANS.md`。
3. 阅读指定任务 PLAN，确认版本、契约成熟度和执行授权。
4. 阅读 PROGRESS，确认基线、证据、执行位置和未决事项。
5. 检查 `git status --short`，必要时检查 diff、分支及提交；记录用户已有修改。
6. 核查相关代码和测试现状，确认进度与实现、版本及已运行证据一致。
7. 冲突时自主调查、验证并修正记录；无法确认的完成项标记 UNVERIFIED，不能只信日志。
8. 选择第一个未完成且任务、阶段依赖均满足的任务，更新当前执行位置。

不得覆盖或丢弃用户未提交修改。恢复时未提交但已验证的工作可能有效，必须检查实际内容；区分已提交、当前工作区和未知状态，不把提交存在作为验收证据。

### 6.2 单任务执行循环

`读取任务 → 检查依赖 → 理解代码 → 实现 → 编写必要测试 → 运行验证 → 修复 → 重新验证 → 更新进度`

修改前核对相关设计、约束、接口和风格，将当前任务标为 IN_PROGRESS。在方案内自主处理工程细节，保持核心语义。按预定任务验收验证，修复失败再重验；全部必需任务验收通过且证据对应当前代码后才标 DONE。实现存在但验收未完成标 UNVERIFIED，外部依赖或必要决策阻塞标 BLOCKED，说明原因及解除条件。

每完成一个任务更新可靠 Checkpoint，包括实际文件、实现状态、运行命令、结果和下一步。不因普通实现困难或测试失败反复询问用户，不以写完代码直接宣告完成。

### 6.3 阶段执行循环

开始阶段前重读相关设计、依赖及阶段验收。完成阶段任务后，检查任务完成证据，执行独立阶段验收、必要集成与相关回归、架构和语义检查，修复失败、重验并记录结果。全部必需阶段验收通过后才进入依赖该阶段的后续阶段。

### 6.4 最终验收循环

所有实施任务完成后，独立执行最终验收，不另设独立复核阶段：

1. 重新阅读 PLAN 最终清单及全局约束。
2. 逐项执行，记录真实命令、环境、输出摘要及退出码。
3. 分析失败或未覆盖行为，在设计范围内修复。
4. 将受影响任务和验收证据重新打开，重跑相关任务、阶段检查及最终检查；必要时重跑完整相关回归。
5. 确认全部必需项通过，检查代码、文档、PLAN 和 PROGRESS 一致。
6. 更新 PROGRESS 的最终状态和恢复信息，交付最终验收报告。

不能跳过最终验收，也不能为通过检查删除失败测试、放宽要求、静默修改预期、跳过必要测试或宣称未经验证的成功。

### 6.5 自主性与重新决策

在已确定契约内自主调查、实现和修复，Level 1 和允许的 Level 2 调整无需重新许可。只有需要改变用户明确需求、核心语义、重大架构、明确兼容性、不可违反约束，或遇到无法在现有契约内消除的重大设计冲突时，重新征求用户决策。说明事实、原因、影响、选项和推荐，将依赖该决策的工作标记 BLOCKED；继续可独立推进的工作，不静默变更核心设计。

所需工具或依赖缺失时，可以依 AGENTS 请求用户完成环境配置；明确缺失项、所需操作和未运行验收，环境恢复后继续。环境阻塞不是功能验收通过，也不应伪造替代验证。

## 7. PROGRESS.md 状态与证据

### 7.1 Current Status

统一任务状态：

| 状态 | 含义 |
| --- | --- |
| TODO | 尚未开始 |
| IN_PROGRESS | 正在实现、修复或验证 |
| DONE | 实现完整且全部必需任务验收通过，证据仍适用于当前代码 |
| BLOCKED | 无法继续，明确原因、依赖及解除条件 |
| UNVERIFIED | 实现存在但必需验证未完成，或原证据已失效 |

任务表是唯一任务完成状态清单。Current Status 的当前阶段、任务及下一步引用此表，不另建重复已完成/未完成列表；DONE 行表示已完成，其余行表示未完成，BLOCKED 行表示阻塞。阶段状态在同文件记录并关联阶段验收，不能从任务 DONE 自动推定阶段通过。整体状态使用等待执行、执行中、等待决策、环境阻塞、最终验收中、完成等文字，不将计划成熟度当执行状态。

### 7.2 Checkpoint 与 Acceptance Results

记录最新可靠检查点：最近完成工作、修改文件、当前代码及工作区状态、最近验证及结果、下一步。测试证据包含 Acceptance ID、实际方法、环境/目录/版本/指针模式（适用时）、命令或手动操作、结果及退出码、PASS / FAIL / NOT_RUN、失败原因、修复和重验记录。未运行永远 NOT_RUN，运行中不能提前 PASS。

证据失效时保留原结果摘要并说明失效原因，将当前结果恢复为 NOT_RUN，关联任务从 DONE 改为 UNVERIFIED 或 IN_PROGRESS。记录代码基线及相关未提交 diff 范围；日志路径不是唯一证据，应在 PROGRESS 保留足够结果摘要，避免清理构建目录后无法理解验证。

### 7.3 Decision Log、Discoveries 与 Recovery Instructions

执行中的重要决策记录 ID、等级、问题、理由、影响、来源和对应计划版本；稳定契约变化同步 PLAN 的决策及历史，动态日志引用同一 ID，不维护第二份冲突设计。发现记录代码与计划差异、技术限制、边界、风险和计划外问题，明确是否影响当前任务，避免顺便实现无关功能。

Recovery Instructions 明确当前任务、已验收部分所在表及证据、未完成和未执行验收、下一步具体命令/操作、优先阅读文件、环境以及未提交修改归属。记录简洁，保留最新可靠检查点、重要决策和失败修复证据，合并重复日志，不无限追加同义进度。

## 8. 上下文压缩与会话恢复

假设会话可中断、聊天可丢失、早期约束可因压缩遗漏。重要信息即时持久化；每完成任务更新检查点，进入新阶段、跨模块实施或重要验证前重查相关设计及验收。中途需交接时尽可能先保存准确检查点，包括不完整修改、正在运行的验证和下一步，不标记尚未通过的工作为 DONE。

状态不明确时从持久化文件和实际代码恢复，不能因缺失上下文猜测原始需求。无需无意义重读全部文件，但必须保证当前工作所依赖的约束有效。PROGRESS 必须足以使全新会话继续。

## 9. 计划变更

不影响契约的普通实现细节可自主调整并记录。用户需求、确认的重大设计、语义及不变量、公共 API、重要兼容性和全局验收标准不得擅自改变。

发现计划错误时：核实代码和问题 → 分析影响 → 优先在原约束内解决 → 普通工程调整自主处理并记录 → 核心变更取得用户决策 → 修订版本、决策、相关任务和验收 → 记录原因及历史 → 更新 PROGRESS 引用版本并使受影响证据失效。

历史包含足够具体的变更及来源，不能只写“用户同意”或引用聊天。变更后仍需满足 Decision Complete，禁止用修改契约掩盖失败；必要标准变化必须由用户明确决定并披露，不可静默降级。

## 10. 执行完成条件与报告

只有所有任务 DONE、所有任务级和阶段级验收通过、所有必需最终验收及相关回归通过、核心设计语义符合、必要文档同步、PLAN/PROGRESS/真实代码一致且无未披露问题时，才能宣布完整完成。

最终报告列出完成能力或交付物、主要变更、实际执行检查和结果、最终验收、计划变更、未解决问题及剩余风险；提交已授权时附提交信息和剩余工作区修改。存在 BLOCKED、UNVERIFIED、必需验收 FAIL 或 NOT_RUN 时，说明未完成范围和恢复步骤，不能声称完整成功。可选未运行项仍须披露。
