# 20 anx 概览

> anx 是 YIAN 的包管理器与项目工具，源码在 `anx/`，与编译器（`compiler/`）是同一个仓库里的
> 两个组件。本编（20–25 章）描述它的内部结构；用户视角的用法见
> [anx 用户指南](../anx/index.md)。

## 定位

anx 提供七个子命令，围绕项目清单、依赖、构建与开发工作流：

`new` 创建项目；`build`、`run`、`check` 编译或检查项目；`test` 运行项目用例；`fmt` 格式化根包源码；
`graph` 展示项目与依赖信息。项目模型把清单、依赖路径、源码文件和包导入映射集中表示
（`anx/project.py`）。

构建命令把项目映射写入 v2 契约 `build/pkg.json`，并连同编译文件与白名单选项调用编译器
（`anx/main.py`）。项目测试把 `<项目根>/tests/` 下的各 `.an` 文件作为独立入口编译、运行并与期望比对
（`anx/project_tests.py`）。

anx **不做**的事同样重要：它不解析源文件、不做类型检查、不复制编译器的导入规则到 CLI 里。
源码级诊断（`E304`、`E307`–`E310`）由编译器产出；anx 原样转发编译器输出，并把非 0 退出码
归一化为 `1`。

## 模块地图

| 文件 | 职责 |
| --- | --- |
| `anx/project.py` | 纯项目模型与加载器：`load()`、`Project`、`discover()`、`resolve_import()`、v2 载荷生成 |
| `anx/manifest.py` | `package.anx` 的解析与字段校验，返回 `Manifest` + 诊断 |
| `anx/diagnostics.py` | `Diagnostic` 形状、`AX001`–`AX015` 码、稳定排序与文本渲染 |
| `anx/main.py` | CLI：子命令、白名单选项、诊断渲染、调用编译器、退出码 |
| `anx/project_tests.py` | `anx test` 的发现、期望文件解析、合成测试包、执行与比对 |
| `anx/scaffold.py` | `anx new` 的模板 |
| `scripts/run_tests.py` | 仓库自测（basic / safety / package 三套件），package 套件用 anx 驱动 fixture |

依赖方向是单向的：`main.py` → `project_tests.py` → `project.py` → `manifest.py` / `diagnostics.py`。
其中 `anx/project.py` 只依赖标准库与 `anx/` 内部模块——**不 import `compiler`、不 import
`subprocess`、不做 I/O 之外的副作用**（`load()` 会读清单与扫描目录，但不写文件、不起进程）。
这条约束是为了让语言服务器能在编辑器进程里直接加载模型。

`anx/main.py` 是唯一的例外：它 import 了 `compiler.analysis.source_provenance.resolve_stdlib_root`
（纯路径解析，只用 `os`/`pathlib`）与 `compiler.format.format_text`（`anx fmt` 用）。
`resolve_stdlib_root` 本身不会把编译器拖进编辑器进程；`compiler.format` 会拉入前端与
analysis，但它只在 `anx fmt` 路径上使用。

## 一次 `anx build` 的数据流

```text
discover([project])                 # 向上找最近的 package.anx        project.py::discover
   │
   ├─ load(root, std_root)          # 读清单、走依赖、建索引          project.py::load
   │     ├─ read_manifest × N       # 每个包一次                      manifest.py::read_manifest
   │     ├─ __check_cycles          # 依赖环直接抛 CycleError         project.py
   │     ├─ __build_package × N     # kind/entry/src 校验（AX008）     project.py
   │     ├─ __nested_source_root_diagnostics（AX013）
   │     └─ __index_files           # 路径 → (包, 模块路径)
   │
   ├─ 诊断非空 → 渲染 error[AXnnn] 并退出 1
   ├─ 根包是 lib 且命令是 build/run → 报「不支持」并退出 1
   ├─ build/pkg.json                # 内容不变则不重写                main.py::__write_package_map
   └─ compiler.main --packages pkg.json [选项] <文件…>
         └─ 退出码非 0 → 转发输出后统一退出 1
```

编译器的路径上，`pkg.json` 被 `compiler/analysis/package_map.py` 解析成 `PackageMap`，
供导入解析（可见性、入口、未知包）与类型检查（程序入口、检查根）使用；细节见
[23 包图与依赖图](23.anx_graph.md)。

## 与编译器的契约边界

| 由 anx 决定 | 由编译器决定 |
| --- | --- |
| 包名、`kind`、入口文件（`AX002`/`AX008`/`AX011`） | 入口里是否有唯一的 `main`、`main` 的返回类型 |
| 依赖边、可见集合的数据（写进 `dependencies`） | 按可见集合拒绝 import（`E308`/`E309`） |
| 源码根与文件集合（含嵌套源码根归属） | 导入是否解析到 `.an` 文件（`E304`/`E310`）、是否入口模块（`E307`） |
| 编译命令行与退出码归一化 | 类型检查范围、代码生成 |

契约是**版本化**的：`build/pkg.json` 顶层带 `format: 2`，未知版本直接报错、不做版本猜测
（`compiler/analysis/package_map.py::PackageMap.parse`）。仓库内没有被跟踪的 `pkg.json`
（`build/` 已被忽略）。

## 测试与验收

anx 自身由 `tests/package/` 下的项目 fixture 驱动：每个 fixture 就是一个真实的 `package.anx`
项目，`scripts/run_tests.py --suite package` 对每个 fixture 执行 `anx build` / `check` /
`test` / `graph`（由 `tests/input/package/<fixture>.command` 指定），并与
`tests/output/package/` 下的期望比对。写 fixture 的方法与整套机制见
[25 anx 自身的测试](25.anx_tests.md)。
