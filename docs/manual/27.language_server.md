# 27 Language server

The YIAN language server is the native program in `lsp/`. It uses the compiler, package-manager, JSON-RPC, LSP protocol, and standard-library packages from this repository. The cold bootstrap installs `yianc`, `anx`, `yian-fmt`, and shared resources; the warm refresh installs those components together with `yian-lsp` under the selected prefix.

## Install and remove

Cold bootstrap the native YIAN toolchain, then run the warm refresh to build and install the language server with the complete native toolchain:

```bash
conda run --no-capture-output -n yian-env bash scripts/bootstrap_toolchain.sh \
  --prefix "$HOME/.local" --python python

scripts/refresh_toolchain.sh --anx "$HOME/.local/bin/anx" \
  --yianc "$HOME/.local/bin/yianc" --prefix "$HOME/.local"

"$HOME/.local/bin/yian-lsp" --version
```

The warm refresh requires native `anx` and `yianc` seeds, the standard-library and runtime resources, LLVM 22, clang 22, and a native C toolchain. It rebuilds `yianc`, `anx`, `yian-fmt`, and `lsp/` as raw/O2 tools, checks the formatter smoke test and the LSP executable, runs a stdio initialization handshake against staged resources with `YIAN_FMT` bound to the staged formatter, then publishes the full toolchain. The binary is built in raw mode; source analysis defaults to fat-pointer mode.

The server accepts:

| Option | Meaning |
| --- | --- |
| `--stdio` | Use the stdio JSON-RPC transport. |
| `--compiler-root PATH` | Use a checkout root for compiler and standard-library sources. Omit this for an installed toolchain. |
| `--raw-pointers` | Analyze workspace sources in raw-pointer mode. |
| `--log-level {DEBUG,INFO,WARNING,ERROR}` | Set the server's stderr log threshold. |
| `--log-file PATH` | Append server logs to a file as well as stderr. |
| `--version` | Print the installed server version. |

The extension starts `yian-lsp` by default. It can also use a configured absolute path. The server writes protocol frames to stdout and logs to stderr or the configured log file.

Remove only the language server while keeping the shared toolchain, or remove the complete managed installation:

```bash
scripts/uninstall.sh --lsp-only --prefix "$HOME/.local"
scripts/uninstall.sh --prefix "$HOME/.local"
```

`--lsp-only` removes only a `yian-lsp` binary whose digest matches its install record and leaves `share/yian` untouched. The default uninstaller removes the managed compiler, package manager, formatter, language server, and shared resources; it retains resources needed by a preserved or unmanaged command.

Server removal also deletes digest-matching `.build-info` and its install record, then removes the empty `share/yian-lsp` directory. Modified, unrecorded or symlinked build information is preserved with its install record and causes a nonzero uninstall status. Other files in that directory are retained.

When compatible native `anx` and `yianc` commands are already available, `scripts/refresh_toolchain.sh` rebuilds and installs the compiler, package manager, formatter, shared resources, and the raw/O2 language server in one transaction. It verifies the server against staged resources before publishing and does not start Python or fall back to the cold path:

```bash
scripts/refresh_toolchain.sh --anx "$HOME/.local/bin/anx" --yianc "$HOME/.local/bin/yianc" --prefix "$HOME/.local"
```

## Features

The server supports diagnostics, definition, hover, document symbols, semantic tokens, references, document highlights, inlay hints, whole-document formatting, document synchronization, and watched-file updates. It does not declare completion, signature help, prepare-rename, rename, code actions, range formatting, or on-type formatting. Requests for those methods return `MethodNotFound` (`-32601`) without starting analysis. Capabilities are negotiated during `initialize`; server identity is reported as `yian-lsp` with its version.

Formatting reads the current in-memory document, including unsaved edits, and sends that text to one `yian-fmt --stdin --stdin-filepath` child process; the returned whole-buffer `TextEdit` carries the child's canonical output. Already formatted text and text that does not lex or parse return an empty array, so the buffer is never partially rewritten; `FormattingOptions` are ignored because the formatter has one canonical style. The request does not wait for analysis, so a semantic failure in the current unit does not block it; text that does not parse produces no edit. A missing or failing formatter writes a server-side stderr diagnostic and also returns no edit. The command is selected by nonempty `YIAN_FMT`, then the server executable's directory, then `PATH`.

Inlay hints show the inferred type of a variable binding that has no written annotation. A hint is placed at the end of the binding name and renders `: <type>` with `InlayHintKind.Type`; `let v = 1.0;` therefore reads as `let v: f64 = 1.0;`. Bindings covered are simple `let`, destructuring `let`, `for`, `match`, `if let`/`while let`, closure captures, and closure-typed variables. A binding with an explicit annotation, a declared function/method/closure/pattern parameter (whose type is always written), or an analyzed type without a stable display form produces no hint; integer/float literal types (`IntLiteralType`, `FloatLiteralType`) are context-dependent and are not displayed. A closure variable uses the compiler's closure display form, such as `|captured: i32| (value: i32) -> i32`; that text is not a writable annotation, so hints carry no `textEdits` and never modify source. Results are limited to the requested range and are emitted in source order.

A navigation result requires the current complete analysis input to pass strict frontend and semantic analysis. Inputs include open document text, standard-library sources, package dependencies and the package map. A missing `main` does not fail analysis. Any preparation, type, constant, coverage or definite-assignment error makes the current analysis unit fail: the server publishes the first root diagnostic and does not serve navigation from the previous version. Separate server instances are independent. Fixing the input triggers a fresh analysis automatically.

While the failed state is current, definition and hover return `null`, document symbols return an empty array, references, highlights and inlay hints return an empty array, and semantic tokens return `{"data": []}`. Pending requests may wait for the current analysis; an outdated response is rejected with `-32801` and a client cancellation with `-32800`. Internal index failures are reported as service errors and never rewritten as a source diagnostic.

The server keeps open-document contents and versions, reloads package inputs when manifests or source topology change, and discards results for outdated unit revisions or routes. It sends at most one synchronization to its worker at a time. Each analysis unit retains only its latest dirty revision and debounce deadline; due units are scheduled in rotation. Ordinary updates send that unit's open documents, while a topology change sends the open set once so the worker can refresh routing. Package workspaces use their `package.anx` metadata. Standalone files are analyzed with the standard library. Unsaved editor text takes precedence over disk contents.

Each server loads at most the project discovered from the initialized workspace root. Files in that project's source and actual dependency roots use the project analysis unit. Every other opened `.an` file uses its own single-file analysis unit with the standard library; the server does not discover or load that file's project manifest, sibling sources, dependencies, or project cache. This rule also applies when the file is inside another package project. Without a discovered main project, each opened `.an` file is analyzed separately with the standard library. Diagnostics and document revisions are isolated by unit, and a main-project topology change updates routing for affected open files. Unopened unrelated source files are not analyzed.

The server identifies each in-memory input by its unit/configuration, ordered source paths and SHA-256 digests. It confirms a candidate hit with exact path and text comparison before reusing the current ready or failed snapshot. Project identity also includes the package map and the text of each reachable package manifest; standalone identity includes only its file and the standard-library configuration. A changed input replaces that unit's current snapshot.

Successful memory snapshots contain a detached query view rather than a live compiler session. After strict analysis the worker copies declarations (including inferred-type hint text), occurrences, reference lists, file text, line indexes, semantic token data and detached warning locations into `QuerySnapshot`, then releases the compiler output, session, source index and semantic index. Definition, hover, document symbols, semantic tokens, references, highlights and inlay hints read only that snapshot; they do not re-run analysis or rebuild indexes.

A project snapshot whose complete input set matches disk is published to `<project-root>/build/lsp/analysis-v1.json`. The record includes the running executable's SHA-256, the LLVM target triple, data layout and version, pointer mode, the exact analysis configuration digest, ordered input paths and SHA-256 digests, declarations (with inferred-type hint text), occurrences, semantic token data and warning locations. A subsequent process accepts the record only when every field and input digest matches exactly; missing, corrupt, truncated, incompatible or mismatched records fall back to strict analysis. Unsaved overlays are never published. Saving an already analyzed overlay republishes its existing result without a new strict analysis, and a later disk edit that no longer matches the recorded digest is rejected.

Publishing uses `std.core.fs.write_atomic`: a unique temporary file is created in the cache directory, fully written, closed, and renamed over the target. A failed write retains the previous cache file and leaves the in-memory snapshot usable; the failure is logged and reported in the worker trace. Cache reads and writes never use FFI directly in the language server. The server excludes `build/lsp/` from watched-input scheduling, so cache publication does not invalidate itself.

After a unit's analysis completes and its diagnostics are published, the server requests `workspace/semanticTokens/refresh` and, when the client advertises `workspace.inlayHint.refreshSupport`, `workspace/inlayHint/refresh`. A client that does not advertise a refresh capability receives no corresponding request.

When the client supports relative watched-file patterns, the server registers the primary source roots, reachable manifest directories, standard-library root and directories of open standalone files. Notifications are filtered against active input units; unrelated paths and `build/lsp/` cache files do not schedule analysis. A client that lacks relative-pattern support can monitor workspace-relative files only, so external roots may not be observed. If watcher registration is rejected, the server logs that changes may remain stale until a later input event or restart. The server does not poll for missed changes; an external edit without a watcher notification can remain stale until another relevant event or restart.

For a new input, the native compiler performs one strict analysis. The language server parses the same frozen text without desugaring to build its source view, constructs declaration, occurrence, token and reference data, and extracts those values into the owning `QuerySnapshot`. Compiler symbol, definition, member and HIR results supply semantic targets during extraction; query code never re-runs type inference or touches compiler IDs. A valid disk-cache record restores the same snapshot representation directly, so requests use one query path whether the snapshot came from analysis or restore.

The server trace records each queued synchronization with its unit key, unit revision and whether it refreshes routing. Worker trace events report per-unit `reuse_kind`, `cache_state`, `cache_hit`, `session_released`, and strict-analysis/source-index/semantic-index/query-index build counts; `analysis_completed` also reports analysis phase durations. Cache states distinguish restored (`disk`), published, ineligible, write failure and disabled standalone units.

LSP positions use UTF-16 code units. Compiler source positions use Unicode scalar columns; the protocol boundary converts between them using the current source text.

## Manual editor verification

The automated protocol checks do not replace testing in the editor. Build the extension package with `npm run package` from `ide-support/vscode/`; the generated file is `ide-support/vscode/yian-language-support-0.8.0.vsix`. Install that VSIX manually. Set `yian.languageServer.command` to the absolute path of the installed binary, for example:

```json
{
  "yian.languageServer.command": "/home/you/.local/bin/yian-lsp",
  "yian.languageServer.args": []
}
```

Then verify the installed binary:

1. Open both a standalone `.an` file and a package workspace. Check the YIAN output channel for a matching server version and confirm diagnostics appear.
2. Make an unsaved edit. Check definition, hover, references, document highlights and semantic highlighting against the current buffer. Confirm that unannotated bindings show `: <type>` inlay hints while explicitly annotated bindings do not, then toggle `editor.inlayHints.enabled` and confirm the hints hide and reappear.
3. In a multi-file project, check definitions and references across files. Confirm that completion, rename and code-action requests are rejected, that Format Document reformats the unsaved buffer, and that no stale navigation survives an intentionally invalid edit.
4. Type continuously, save, add and remove a source file, and repair a temporarily invalid manifest. Confirm current diagnostics replace old ones and no stale result appears after a newer edit.
5. To check raw analysis, set `yian.languageServer.args` to `["--raw-pointers"]`, restart the server, and repeat representative queries.
6. Close the workspace and confirm the server and its worker have exited. For example, inspect `ps -eo pid,ppid,args | grep '[y]ian-lsp'` and ensure no process for that workspace remains.

Build the extension package without starting the editor:

```bash
cd ide-support/vscode
npm ci
npm run compile
npm run package
```

The package command writes a `.vsix` in `ide-support/vscode/`. Install it manually in the editor for the interaction checks above.

## Automated protocol checks

The minimal navigation probe opens a small project fixture (two source files plus `package.anx`) and a typed fixture and checks retained capabilities, closed methods, definition/reference/hover/symbols/tokens, whole-document formatting of an unsaved buffer, inlay hints for every inferred binding form, hint suppression for annotated bindings, hint range filtering, the `workspace/inlayHint/refresh` request, the valid to invalid to repaired transition, and UTF-16 positions. It uses only `StdioSession` and does not run the protocol matrix:

```bash
PATH="$HOME/.local/bin:$PATH" \
  conda run --no-capture-output -n yian-env python scripts/probe_lsp_navigation.py
```

`scripts/probe_lsp_cache.py` exposes exact cases for input isolation, primary-project routing, unchanged-input reuse, invalidation/recovery, in-flight synchronization coalescing, watched input roots, detached query stability, UTF-16 positions, restart restoration, cache rejection and publication eligibility, cache identity/atomic-publication primitives, plus the native SHA-256 implementation. The restart and detached-query comparisons include a `textDocument/inlayHint` request, so restored hint data must match the analyzed snapshot. Each case creates one temporary fixture and exits after that case. The protocol cases require a `yian-lsp` built from the current LSP sources; `fingerprint` compiles and runs only the hash module, its standard-library sources, and a two-vector caller. For example:

```bash
conda run --no-capture-output -n yian-env python scripts/probe_lsp_cache.py \
  --case unchanged --native "$HOME/.local/bin/yian-lsp" --yianc "$HOME/.local/bin/yianc"
```

The Python protocol script is a test and measurement client; it starts only the installed native service. It supports protocol replay, benchmarking, native event-trace profiling, and infrastructure checks:

```bash
PATH="$HOME/.local/bin:$PATH" \
  conda run --no-capture-output -n yian-env python scripts/check_lsp.py --mode check

PATH="$HOME/.local/bin:$PATH" \
  conda run --no-capture-output -n yian-env python scripts/check_lsp.py --mode benchmark

PATH="$HOME/.local/bin:$PATH" \
  conda run --no-capture-output -n yian-env python scripts/check_lsp.py --mode profile
```

The infrastructure mode requires an existing native `yianc`, `anx`, `yian-lsp`, and shared resources. It does not install or refresh tools; missing components produce an explicit cold/warm setup hint. When prerequisites exist, it runs bootstrap package tests, all unit tests, formatter checks, and runtime normal/sanitized checks. This is a broad infrastructure run; repository verification must inspect those indirect effects and use an explicitly authorized scope. It does not start VS Code.

`--mode check` runs the protocol scenarios (standalone, JSON project, and compiler project by default) in both fat and raw modes; it does not run the infrastructure command list above. This is six protocol combinations by default. Repository checks should select the exact scenario and pointer mode; the full matrix requires explicit authorization. Benchmark and profile modes are measurements rather than default local acceptance checks.
