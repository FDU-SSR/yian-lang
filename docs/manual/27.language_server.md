# 27 语言服务器

> `lsp/` 是 YIAN 的协议服务层：把 LSP 消息翻译成对分析会话
> （[26 分析接口](26.analysis_interface.md)）与 `anx` 项目模型的调用。它自己不含语言规则，
> 依赖方向单向：`ide-support/vscode/ → lsp/ → compiler/ + anx/`。

对应源文件：`lsp/__init__.py`、`main.py`、`__main__.py`、`server.py`、`workspace.py`、
`diagnostics.py`、`navigation.py`、`completion.py`、`semantic_tokens.py`、`refactor.py`、
`formatting.py`、`ide-support/vscode/src/extension.ts`

## 进程形态与命令行

服务器是一个独立的 stdio 进程：**stdout 是 JSON-RPC 通道，任何人类可读的输出一律走 stderr**
（或日志文件）。扩展用 stdio transport 启动它，分析在服务器进程内经库调用完成，不为单个请求
起子进程。stdin 关闭即进程退出，所以关掉编辑器窗口不会留下孤儿。

```bash
# 已把 yian-lsp 装进 PATH
yian-lsp --compiler-root /path/to/yian --log-level DEBUG

# 用指定解释器启动（多环境机器推荐）
/path/to/env/bin/python -m lsp --log-level DEBUG --log-file /tmp/yian-lsp.log
```

| 选项 | 含义 |
| --- | --- |
| `--compiler-root PATH` | YIAN 检出根，用来定位标准库（等价于 `yianc --compiler-root`） |
| `--raw-pointers` | 以 raw 指针模式分析，匹配 `yianc --raw-pointers` |
| `--log-level {DEBUG,INFO,WARNING,ERROR}` | stderr 日志级别；缺省 `$YIAN_LSP_LOG`，再缺省 `INFO` |
| `--log-file PATH` | 同时把日志追加到文件；缺省 `$YIAN_LSP_LOG_FILE`，未设则只写 stderr。文件打不开时打印原因并以退出码 2 结束 |
| `--stdio` | 兼容项：客户端（如 `vscode-languageclient`）会追加它，但它不选择任何东西，stdio 是唯一传输方式 |
| `--version` | 打印 `yian-lsp <服务器版本>` |

`yian-lsp` 与 `python -m lsp` 是同一个入口（`lsp.main:main`），`lsp/__main__.py` 只是转调。

## 工作区与快照

`lsp/workspace.py` 把「一个编辑器窗口看到的世界」放在 Python 侧：打开文档的覆盖层、`anx` 项目
模型、由这两者推出的分析快照。它不 import LSP，位置与 uri 的转换都在协议边界做。

```python
class Workspace:
    def open(self, path: Path, text: str, version: int | None = None) -> None: ...
    def change(self, path: Path, text: str, version: int | None = None) -> None: ...
    def close(self, path: Path) -> None: ...
    def is_open(self, path: Path) -> bool: ...

    @property
    def documents(self) -> DocumentStore: ...
    @property
    def project(self) -> Project | None: ...
    @property
    def project_root(self) -> Path | None: ...
    @property
    def std_root(self) -> Path: ...

    def use_directory(self, start: Path) -> LoadResult | None: ...
    def use_project(self, root: Path) -> LoadResult: ...
    def files(self) -> tuple[Path, ...]: ...

    @property
    def snapshot(self) -> Snapshot: ...          # 完整前缀，缓存仍匹配时复用
    @property
    def syntax_snapshot(self) -> Snapshot: ...   # 只跑前端
    @property
    def fresh_snapshot(self) -> Snapshot | None: ...  # 缓存不匹配就返回 None
    def invalidate(self) -> None: ...
```

### 两种模式

模式由**工作区目录**决定，在 `initialize` 时判定一次；之后用户打开哪个文件都不会切换模式。

| | package 模式 | standalone 模式 |
| --- | --- | --- |
| 触发 | 工作区是（或位于）含 `package.anx` 的目录 | 不是项目 |
| 项目模型 | `anx.project.load`，失败时 `project is None` 但工作区继续 | `project is None` |
| 分析文件 | `Project.files`（全部索引到的文件，含未被 import 的包），再补上不属于索引的已打开文档 | 已打开文档 + 标准库 |
| 包解析 | 用 `PackageMap.from_document(project.compiler_package_map())` | 无包映射 |

依赖环（`CycleError`）没有有意义的局部图，`anx` 把它抛成异常；`use_project` 在这里把它转成一条
`AX006` 诊断，因为语言服务器不能因为项目坏掉而崩溃。

### Snapshot

```python
@dataclass(frozen=True)
class Snapshot:
    generation: int
    project_root: Path | None
    project: Project | None
    files: tuple[Path, ...]
    result: AnalysisResult

    @property
    def index(self) -> DeclarationIndex | None: ...
    def declarations_in(self, path: Path) -> tuple[Declaration, ...]: ...
```

快照只被替换、从不打补丁；`generation` 在进程内单调递增，让持有旧快照的调用方能认出它已经过期。
`invalidate()` 丢弃两级缓存，下一次请求重新分析。

三个入口的差别只在缓存与 `syntax_only`：

- `snapshot`：若缓存的完整快照的键与文件列表都没变就复用，否则跑**完整前缀**；
- `syntax_snapshot`：同上，但跑 `syntax_only=True`（只 lex → parse → desugar）；
- `fresh_snapshot`：只读缓存，键不匹配或从未跑过返回 `None`——它绝不触发分析。

## 服务器与已注册能力

`lsp/server.py` 的 `YianLanguageServer` 继承 pygls 的 `LanguageServer`。两个刻意的选择：

- **`max_workers=1`**：分析是 CPU 密集的，工作区又是有状态的，因此请求按客户端发送顺序串行执行。
  没有开始的请求仍可被 `$/cancelRequest` 取消（pygls 取消尚未出队的工作）。
- **`text_document_sync_kind = Full`**：分析永远从整份文本重新开始，增量文本 diff 没有收益。

`initialize` 只在 `serverInfo` 里回报 `SERVER_NAME` / `SERVER_VERSION`；能力由注册的 feature 决定：

| LSP 方法 | 实现 |
| --- | --- |
| `textDocument/publishDiagnostics` | 编译诊断按文档分组后发布（`lsp/diagnostics.py`） |
| `textDocument/definition` | `Navigator.resolve` → `Location` |
| `textDocument/hover` | 声明种类/名称/签名 + 表达式类型，Markdown |
| `textDocument/documentSymbol` | 声明索引按容器嵌套成符号树 |
| `textDocument/semanticTokens/full` | `semantic_tokens.py`：读分析事实分类（token 类型是编辑器词汇），再按 LSP delta 编码 |
| `textDocument/completion` | 触发字符 `.`、`:`、`<`；项带 kind/detail/snippet/textEdit |
| `textDocument/signatureHelp` | 触发字符 `(`、`,`；标记当前参数 |
| `textDocument/references` | 按符号身份的引用列表 |
| `textDocument/documentHighlight` | 只取当前文件的引用，声明为 write、使用为 read |
| `textDocument/prepareRename` / `textDocument/rename` | 重命名或拒绝；`WorkspaceEdit` 一次提交 |
| `textDocument/codeAction` | `refactor.py`：删除无法成立的 import（编辑策略在 LSP 侧，语句范围来自分析） |
| `textDocument/formatting` | `formatting.py`：`compiler.format.format_text` 的整文件编辑，返回一个覆盖全文的 `TextEdit` |
| `workspace/didChangeWatchedFiles` | 动态注册 `**/*.an` 与 `**/package.anx` |
| `textDocument/didOpen` / `didChange` / `didSave` / `didClose` | 文档同步与调度 |
| `initialize` / `initialized` / `shutdown` | 生命周期 |

重命名被拒绝时抛 `JsonRpcException(refusal, code=REQUEST_FAILED)`，`REQUEST_FAILED = -32803`
（LSP 的 `RequestFailed`）：请求被理解、但无法完成，客户端显示可读消息而不是应用半截修改。

`report_server_error` 把协议层异常记进日志而不是弹消息框：一次内部异常不该接管编辑器。

## 调度与性能

这是两条不同路径，对应「惰性优先于增量」：

**打字路径（每敲一个字符）。** `didChange` 只做三件事：记录新文本、`invalidate()`、重新武装一个
`DEBOUNCE_SECONDS = 0.2` 的定时器。连击被合并成一次分析，0.2 秒内没有新输入才真正开跑，而且跑的是
`syntax_snapshot`；若当前输入已经有一份完整快照（例如刚保存过），这一趟直接复用它、什么都不算。所以
打字期间 Problems 面板里只有词法/语法诊断——半成品代码不会刷出一片「未定义标识符」。

**完整路径（打开、保存、语义请求）。** `didOpen` 与 `didSave` 直接 `analyze_now`（保存是用户的明确
停顿，不等防抖）；悬停、补全、跳转、引用、重命名、文档符号这些语义请求走 `snapshot`，必要时跑完整
前缀。分析一旦落地，`notify_analysis` 会顺带发布完整诊断，且**每个 generation 只发布一次**，所以
Problems 面板跟着最新分析走，而不是等下一次按键。

**语义 token 是被动特性。** `textDocument/semanticTokens/full` 客户端在每次可见编辑后都会重新拉取，
所以这个 handler 只读 `fresh_snapshot`：文本已经改动就返回空数组，客户端保留 TextMate 着色。等完整
分析落地后，服务器在客户端声明了 `workspace.semanticTokens.refreshSupport` 时发
`workspace/semanticTokens/refresh`，让客户端重新拉取一次真正带类型的 token。

**取消与关闭。** `$/cancelRequest` 取消尚未开始的工作；`shutdown` 取消已排定的分析，防止客户端已经
离开后定时器才触发。`workspace/didChangeWatchedFiles` 里 `package.anx` 的变化会重新加载项目模型并
立即完整分析，其他 `.an` 变化只失效快照并走防抖。两种情况下文档覆盖层都不动：未保存的缓冲区仍然
优先于磁盘。

**发布范围。** 只给客户端打开过的文档发诊断：整工程发布会把标准库的噪音塞满 Problems 面板。上一轮
发布过、这一轮没有覆盖的文档会收到空列表，这是关闭文件或修好错误后条目消失的方式。

## 日志

日志级别映射到输出通道：`DEBUG` 与 `INFO` 走 debug/info，`WARNING` 走 warn，`ERROR` 与 `CRITICAL`
走 error。扩展读取每行的级别前缀（`vscode-languageclient` 默认把 stderr 的每一行都报成 error，会把
普通进度行埋掉真正的失败），Traceback 起始行及其续行按 `ERROR` 处理。

**`DEBUG` 记录每条 JSON-RPC 载荷；每次分析的耗时行在 `INFO` 级别输出。载荷包含源码文本**，
把它贴进问题报告前先确认内容可以公开。每次分析记一行「generation、触发原因、full/syntax/reused、
文件数、诊断数、毫秒」；`reused` 一行没有毫秒字段。声明索引是首次被查询时才构建的，所以
`N declarations` 只在索引已经建好之后的分析行里出现。

`--log-file` 是**追加**的第二个 handler，不替代 stderr，因此扩展的输出通道仍然拿到全部内容；文件更
适合长时间挂机排查。日志文件打不开时服务器打印原因并返回退出码 2。

## 版本匹配与分发

`SERVER_VERSION` 与 VS Code 扩展的 `package.json` 版本**同号**（当前 0.7.0），两者从同一仓库一起发布。
服务器在 `initialize` 的 `serverInfo` 里回报版本；扩展比对不一致时在输出通道写一行 warning 并弹提示，
但功能本身继续可用——不匹配几乎总是因为启动服务器的解释器里装的是另一份 `yian`。

分发采用「依赖本机 Python 环境」方案：

- 扩展默认命令是 `yian.languageServer.command: "yian-lsp"`，即 PATH 上的脚本；
- 多环境机器推荐把它设为具体解释器的绝对路径，并把 `yian.languageServer.args` 设为 `["-m", "lsp"]`，
  这样切换解释器只是改设置，不用重装；
- 在该解释器里执行 `pip install -e '.[lsp]'`。`lsp` extra 只装 `pygls`；`llvmlite` 由基础依赖提供，
  所以服务器所在的解释器需要完整安装 YIAN（`yianc` / `anx` 也在这个解释器里）。

扩展还提供 `yian.languageServer.logLevel`（作为 `--log-level` 传入）与 `yian.languageServer.logFile`
（作为 `--log-file`，其中 `${workspaceFolder}` 展开为第一个工作区目录）。

## 实测性能

在 34 / 39 / 95 / 285 个文件（标准库加生成工程）上，用 `AnalysisSession` 与 `Workspace`
实测，同一台机器：

| 指标 | 34 | 39 | 95 | 285 |
| --- | --- | --- | --- | --- |
| 首次打开（完整前缀） | 106 ms | 132 ms | 263 ms | 582 ms |
| 打字路径（只前端，冷盘） | 76 ms | 78 ms | 103 ms | 198 ms |
| 打字路径（只前端，热态） | 约 74 ms | 约 77 ms | 约 92 ms | 约 145 ms |

空转复用快照约 2–11 ms；悬停（热）约 10–20 ms；补全（热）约 2–17 ms；常驻内存约 32–56 MB。

结论：打字反馈在 100 个文件以内低于 100 ms，285 个文件时约 145 ms，仍在 200 ms 的不可接受线以内；
悬停与补全远低于 100 ms。标准库只有 33 个文件，却占掉前端耗时的大头（约 60–76 ms）。当前粒度是
去抖 + 取消 + 每次空闲最多分析一次，语义请求按需跑完整前缀；不跨快照复用 stdlib 结果、不做 parse
缓存、不做细粒度增量。

## 故障排查

| 症状 | 原因 | 处理 |
| --- | --- | --- |
| 扩展没有任何反应，弹出 `could not start '…'` | 命令不在 PATH，或该解释器没装服务器 | 按提示 `pip install -e '.[lsp]'`；多环境机器把 `yian.languageServer.command` 设为该解释器、`args` 设为 `["-m", "lsp"]` |
| 输出通道警告「language server X does not match extension Y」 | 启动的解释器里是另一份（通常是旧的）安装 | 在**那个**解释器里重新 `pip install -e '.[lsp]'`，或改设置指向正确的解释器 |
| 没有任何诊断 | 文件不在任何工作区/项目里，或打开的目录不是项目根 | 用「打开文件夹」打开项目根；日志会说明进入了 package 还是 standalone 模式 |
| 语义高亮没有颜色 | 完整分析还没落地（文本刚改过），或客户端不支持刷新 | 先停下等一次保存；确认客户端声明了 semantic tokens 与 refresh 支持 |
| 跳转不到标准库 | 标准库根没解析对，或 `lib/src` 不在分析文件集合里 | 传 `--compiler-root`（或设 `YIAN_LIB` / `YIAN_ROOT`）；`initialize` 后日志会打印项目与文件数 |
| 需要一份 DEBUG 日志 | — | 设 `yian.languageServer.logLevel: "DEBUG"`，或用 `--log-level DEBUG --log-file <路径>`；注意载荷含源码文本 |
| 服务器异常退出 | 编译器内部错误 | 扩展把 stderr（含 Traceback）收进输出通道并记日志，VS Code 本身不受影响；report 时附上这段日志 |

## 能力范围

服务器提供：文档同步与防抖、实时诊断（含恢复后的多诊断）、跳转定义、悬停、文档符号、语义 token、
补全、签名提示、查找引用、文档高亮、prepareRename/rename、import 快速修复、格式化、watched files、
`$/cancelRequest`、日志级别与日志文件、扩展与服务器版本比对。

不提供：内联提示（inlay hints）、折叠范围（folding ranges）、选择范围（selection ranges）、
文档链接（document links）、工作区符号搜索（`workspace/symbol`）、
`declaration` / `typeDefinition` / `implementation`、模糊匹配补全、doc 注释补全、自动补 import。
重命名在无法确认符号身份时拒绝执行，不做字符串级全局替换。

其它限制：多根工作区只分析第一个工作区文件夹；分析在服务器的单 worker 上同步执行，第一次打开很大
的项目会阻塞后续请求；`$/cancelRequest` 只能取消尚未开始的请求。
