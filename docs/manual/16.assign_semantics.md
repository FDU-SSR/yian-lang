# 16 赋值语义实现

## 实现边界

赋值 lowering 只承担两项职责：确认目标是可写 place，并把来源值强制为目标类型。它不再根据类型类别限制来源表达式，也不会插入资源清理。

核心入口位于 `compiler/analysis/lowering/assign_check.py`：

```python
def build_assign(type_ctx, coerce, span, target, value) -> HIR.Binary:
    check_assign_target(target, span)
    if value.type_id != type_ctx.never_id:
        value = coerce(value, target.type_id)
    return HIR.Binary(
        span=span,
        op=BinaryOperator.Assign,
        left=target,
        right=value,
        type_id=target.type_id,
        is_place=False,
    )
```

因此，删除旧复制限制并不等于删除赋值检查。不可写目标和类型不兼容仍由此处及强制转换逻辑报告；未初始化读取仍由确定赋值分析拒绝。

## 统一的传值路径

以下 lowering 路径都直接保留表达式值，并按目标类型进行必要的统一或强制转换：

| 场景 | 主要位置 |
| --- | --- |
| 变量、字段、数组元素和解引用位置赋值 | `assign_check.py`、`expr_checker.py` |
| 普通函数、函数值和闭包实参 | `call_dispatcher.py` |
| 方法接收者与方法实参 | `call_dispatcher.py` |
| struct 字段和 enum payload | `call_dispatcher.py` |
| 数组、重复数组和元组元素 | `expr_checker.py` |
| `return`、尾表达式和带值 `break` | `expr_checker.py` |
| 闭包捕获 | `closure.py` |

这些路径不维护“简单类型”集合，也不区分变量、构造表达式和函数返回值。后端可以用寄存器、聚合 load/store 或其他等价方式实现复制，只要保持浅复制的可观察行为。

## Clone 分派

`Clone` 是标准库定义的普通 trait。`ImplRegistry` 只根据显式 impl 和泛型条件判断是否满足 `Clone`，不会因为类型被判定为“简单”而自动成功；`CallDispatcher` 也不会把名为 `clone` 的方法直接改写为恒等表达式。

标准库为标量提供显式实现，并为数组、元组和拥有型容器提供组合实现。用户定义的同名固有方法或其他 trait 方法仍走普通方法查找。

原始指针的方法查找有一个 Clone 边界：标准库 `Clone` 不能仅通过解引用指针而被视为指针本身的实现。因此 `ptr.clone()` 被拒绝，`(*ptr).clone()` 才表示克隆指向值。该判断依据解析到的标准库 trait 实现，而不是仅比较方法名称。

## 已删除的编译器机制

实现中不再包含：

- `TypeCtx.is_simple_type` 及相关缓存；
- 赋值来源分类和 `check_simple_assign_source`；
- `Move` 的自动实现和方法调用捷径；
- `bitcopy` builtin、HIR 节点及 CFG lowering；
- `@BitCopy` 的词法、语法、AST 和类型元数据；
- 仅供失效操作使用的 `HIR.Nop`。

## 资源管理不由赋值 lowering 完成

编译器不会为赋值覆盖、传参、返回和作用域退出生成 `Drop` 调用。`del` 仍直接 lowering 为释放目标分配块的操作，不遍历对象成员。标准库容器的 `clear`、`truncate`、`remove` 和 `drop` 等显式方法负责按接口约定清理有效元素和缓冲区。

验证这一区分时，应同时检查运行结果和生成 IR：普通复制路径不应出现隐式 `drop`、额外分配或来源失效写入；显式清理路径则应只处理当前有效成员。
