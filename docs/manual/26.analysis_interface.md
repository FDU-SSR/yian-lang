# 26 分析接口

> `compiler/analysis/` 里的分析会话是编辑器功能（导航、补全、语义高亮、重命名）与命令行共用的
> 引擎侧接口。它只接受文本、只返回结构化结果，不认识任何编辑器协议；`lsp/` 只是它最外层的
> 薄适配（[27 语言服务器](27.language_server.md)）。

对应源文件：`compiler/analysis/session.py`、`documents.py`、`positions.py`、`index.py`、
`view.py`、`navigation.py`、`completion.py`、`refactor.py`、`diagnostics.py`、
`package_map.py`、`source_provenance.py`

## 分层与依赖方向

| 层 | 位置 | 内容 | 消费者 |
| --- | --- | --- | --- |
| 语言引擎 | `compiler/analysis/` | 分析会话、位置转换、声明索引、导航/补全/语义/重命名查询 | `yianc`、`lsp/` |
| 项目模型 | `anx/` | 项目发现、依赖与导入规则、v2 包图 | `anx`、`lsp/` |
| 协议服务 | `lsp/` | 协议适配、进程形态、文档版本与请求调度 | 所有 LSP 客户端 |

依赖方向单向：`lsp/ → compiler/ + anx/`。`compiler/analysis/` 不 import `lsp/`，`anx/` 不 import
`compiler/`（唯一的例外是 `anx/main.py` 使用 `source_provenance.resolve_stdlib_root`，那是纯路径
解析）。这条约束使分析会话可以在编辑器进程里长期驻留，而不把协议或命令行拖进去。

## 流水线前缀

`AnalysisSession.analyze()` 只运行编译管线的前缀，跑完类型检查就停：

```text
lex
→ parse
→ desugar
→ prelude 注入
→ 受限操作检查
→ 全局解析（GlobalResolve）
→ type_ctx.finalize()
→ 类型检查（TypeCheck）
```

**不跑**的部分：comptime 条件特化、闭包下降、确定赋值分析、CFG 下降、LLVM 下降与生成。因此一次
分析不会调用 clang、不会链接、不产生任何产物。

前缀的终点不是随意选的：`TypeCtx` 在 `GlobalResolve` 之后才封闭类型与 impl 注册，`finalize()` 是
「注册已封闭、查询缓存已启用」的干净边界，正好可以冻结成一个快照。

## 文档与会话

分析不读文件，它读**文档**：

```python
@dataclass(frozen=True)
class Document:
    path: Path
    text: str
    version: int | None = None

class DocumentStore:
    def add(self, document: Document) -> None: ...
    def remove(self, path: Path) -> None: ...
    def text(self, path: Path) -> str: ...        # 覆盖层优先，否则读盘
    def version(self, path: Path) -> int | None: ...
    def versions(self) -> Mapping[Path, int | None]: ...
```

`DocumentStore` 是「内存文本盖在磁盘之上」的覆盖层：编辑器打开的缓冲区进覆盖层，标准库和未被
打开的依赖仍从磁盘读。`collect_an_files(paths, overlay=…)` 把路径展开成文件列表——文件按原样接受，
目录递归搜索，只存在于覆盖层里的新文件也被接受，其余情况抛 `FileNotFoundError` 而不是退出进程。

```python
class AnalysisSession:
    def __init__(self, *, compiler_root: Path | None = None,
                 packages: PackageMap | None = None,
                 raw_pointers: bool = False) -> None: ...

    @property
    def std_root(self) -> Path: ...

    def analyze(self, paths: Sequence[Path], *,
                documents: DocumentStore | None = None,
                require_entry: bool = False,
                syntax_only: bool = False) -> AnalysisResult: ...

    def snapshot_key(self, paths: Sequence[Path], *,
                     documents: DocumentStore | None = None) -> tuple[object, ...]: ...
```

- 会话很便宜：标准库根、包映射与指针模式在构造时解析一次，之后每次 `analyze()` 都从文本重新开始。
- `packages` 给出 `PackageMap` 时进入包模式，标准库根取 `packages["std"].source_root`；否则用
  `resolve_stdlib_root(compiler_root)`（见「项目模型与包映射」）。
- `require_entry=True` 才要求包声明程序入口；编辑器默认 `False`。类型检查固定以
  `entry_optional=True`、`recover=True` 运行：缺少 `main` 或存在多个 `main` 都不致命，恢复粒度定在
  顶层定义，一个坏掉的定义不会阻止其余定义被检查，也不会阻止索引建立。

## AnalysisResult 与快照键

```python
@dataclass
class AnalysisResult:
    diagnostics: tuple[Diagnostic, ...] = ()
    sources: Mapping[Path, str] = ...
    tokens: Mapping[Path, tuple[Token, ...]] = ...
    units: Mapping[int, UnitData] = ...
    type_ctx: TypeCtx | None = None
    def_points: Mapping[int, DefPoint] = ...
    index: Index | None = None
    versions: Mapping[Path, int | None] = ...
    key: tuple[object, ...] = ()
    failed_stage: Stage | None = None
    syntax_only: bool = False

    def ok(self) -> bool: ...          # 没有 error 级诊断
    def formatted(self) -> str: ...    # 对着各自的文本渲染诊断
```

几个容易忽略的性质：

- **失败的运行也带 `tokens` 与 `key`。** 词法成功、后续阶段失败时，结果仍然携带词法 token（降级
  回答要用）和完整的快照键，因此编辑器不会对同一个坏文件在每个请求上重新分析。
- **`index` 与 `type_ctx` 只有跑完前缀才有。** 中途停止的运行 `index is None`，查询模块据此返回空
  结果而不是猜测。
- **`def_points` 覆盖检查器真正跑过的每个定义**，包括 `main` 从没调用的库函数：导航要能回答它们，
  重命名要据此判断引用集合是否完整。

快照键的形状是：

```python
(ANALYSIS_FORMAT, 排序后的 (str(路径), 文本 sha256, 编辑器版本), raw_pointers)
```

`ANALYSIS_FORMAT` 是分析语义的格式号；`raw_pointers` 是编译旗标；每条输入用它**当前文本的 sha256**
和文档版本参与。`snapshot_key()` 返回「此刻 analyze 会产生的键」，调用方把它和自己持有的
`result.key` 比较，相等就复用旧结果。文本、版本或旗标任何一项变化，键都不可能相等。

### 为什么不会返回陈旧结果

三个事实合起来让「陈旧」没有表达方式：

1. **快照不可变**：一次 `analyze()` 的结果不再被修改，查询只读它。
2. **失效永远是整快照重建**：不做 `parse` 缓存、不做 stdlib 复用、不做细粒度增量；文本一变就重新
   从文本开始。
3. **pass 原地改 AST**（`inject_prelude` 等直接重写自己拿到的单元），因此同一份 AST 不能分析两次。

第 3 条本来是个限制，但它和 1、2 一起把「复用半成品 AST」这条路彻底封死：每次分析都从当前文本
重新解析，得到的一定是最新文本的结果。编辑器要做的只有一件事——文本变了就把旧快照丢掉。

### syntax_only

`syntax_only=True` 只做 lex → parse → desugar，然后返回。这是「边打字只跑前端」的实现：

- 成功时 `diagnostics` 为空，`index is None`、`type_ctx is None`，`syntax_only=True`；
- 前端任一阶段失败时，返回的仍是那条带位置的结构化诊断，并且同样带 `tokens` 与 `key`（分析在
  第一个错误处停止，所以一次运行最多带一条诊断）；
- 前端的词法/语法诊断是打字期间唯一可以信任的诊断，语义查询与保存才需要完整前缀。

## 位置模型

编译器内部的位置不动：`SrcPosition(row 0 基, col 1 基、按代码点计数, Path)`，`SrcSpan` 由两个
`SrcPosition` 组成。编辑器说 LSP：行 0 基、字符按 UTF-16 代码单元、`file://` uri。

`compiler/analysis/positions.py` 是**唯一**同时认识两套坐标的模块：

```python
def utf16_length(text: str) -> int: ...
def to_lsp_position(row: int, line_text: str, col: int) -> dict[str, int]: ...
def to_compiler_column(line_text: str, character: int) -> int: ...
def to_lsp_range(span: SrcSpan, text: str) -> dict[str, dict[str, int]]: ...
def path_to_uri(path: Path) -> str: ...
def uri_to_path(uri: str) -> Path: ...
```

列转换需要整行文本，因为 UTF-16 代码单元和代码点在第一个非 BMP 字符之后就分道扬镳。`to_lsp_range`
用的文本是**文档当前文本**，不是磁盘上的版本，所以未保存缓冲区的范围依然正确。其余模块只使用
其中一套坐标，只在边界上调用这里。

## 名字引用表

导航、补全、语义高亮、查找引用/重命名都基于两张表，而不是重新从文本里猜：

| 表 | 生产者 | 内容 |
| --- | --- | --- |
| 名字引用 | 类型检查/解析阶段调用 `TypeCtx.record_name_ref(span, target, expression_type=None)` | `NameRef(span, target, expression_type)`，`target` 是 `Symbol \| StructField \| EnumVariant \| int`（`int` 是类型 id） |
| 声明索引 | 分析结束后 `build_index(...)` | 每个声明的名字 span、种类、容器、可见性 |

`record_name_ref` 对同一个位置只记一次（同一个泛型定义被多次实例化时不重复），零宽/合成 span 直接
跳过。`TypeCtx.name_refs()` 按首次出现顺序返回全部记录。引用表负责「这个名字用在哪、指的是谁」，
声明索引负责「这个名字在哪声明」。

## 查询模块

查询层只读**事实**：`AnalysisView` 是唯一接触编译器内部（`TypeCtx` 与声明索引）的只读层，
`Navigator` 在它之上只加一件事——把位置解析成声明。其余查询模块（补全、引用、重命名）都经过这两
者，不直接访问 `TypeCtx`（生产者 `session.py`、`index.py` 例外，它们本来就在构建这些结构）。

```python
class AnalysisView:                       # compiler/analysis/view.py
    def __init__(self, result: AnalysisResult) -> None: ...
    # 文本与词法
    def text_of(self, path) -> str: ...
    def tokens_of(self, path) -> tuple[Token, ...]: ...
    # 声明与模块
    def declarations_in(self, path) -> tuple[Declaration, ...]: ...
    def declarations_by_name(self, name) -> tuple[Declaration, ...]: ...
    def declaration_starting_at(self, path, row, col) -> Declaration | None: ...
    def module_of(self, path) -> str | None: ...
    def module_file(self, dotted: str) -> Path | None: ...
    def package_names(self) -> tuple[str, ...]: ...
    def module_names(self) -> tuple[str, ...]: ...
    def import_statements(self, path) -> tuple[SrcSpan, ...]: ...
    # 记录过的名字
    def name_refs(self) -> tuple[NameRef, ...]: ...
    def reference_starting_at(self, path, row, col) -> NameRef | None: ...
    def references_of(self, path) -> tuple[NameRef, ...]: ...
    def reference_in_span(self, span) -> NameRef | None: ...
    # 单元、符号与定义体
    def unit_of(self, path) -> UnitData | None: ...
    def has_symbols(self, path) -> bool: ...
    def symbols_in(self, path) -> tuple[Symbol, ...]: ...
    def definition_bodies_in(self, path) -> tuple[tuple[int, SrcSpan], ...]: ...
    def procedures(self) -> tuple[tuple[int, AST.Block, int], ...]: ...
    # 类型空间
    @property
    def has_types(self) -> bool: ...
    def type_of(self, type_id) -> Type.Ty | None: ...
    def type_name(self, type_id) -> str | None: ...
    def canonical_type(self, type_id) -> int: ...
    def deref_type(self, type_id) -> int | None: ...
    def fields_of(self, type_id) -> tuple[StructField, ...]: ...
    def variants_of(self, type_id) -> tuple[EnumVariant, ...]: ...
    def methods_of(self, type_id) -> tuple[tuple[str, int], ...]: ...
    def parameters_of(self, type_id) -> tuple[tuple[str, str], ...]: ...
    def return_type_name(self, type_id) -> str | None: ...
    def callable_name(self, type_id) -> str: ...
```

它只读不写，答不出来就返回 `None` 或空元组（未知类型 id、没解析过的名字、parser 没见过的 span），
绝不给一个看起来合理的默认值。视图按请求创建，因此它的有效期和它基于的快照一样长。

### Navigator

```python
class Navigator:
    def __init__(self, result: AnalysisResult, *, std_root: Path | None = None) -> None: ...
    def text_of(self, path: Path) -> str: ...
    def declarations_in(self, path: Path) -> tuple[Declaration, ...]: ...
    def module_of(self, path: Path) -> str | None: ...
    def enclosing_definition_name(self, path: Path, row: int, col: int) -> str | None: ...
    def resolve(self, path: Path, row: int, col: int) -> Resolution | None: ...
    def reference_starting_at(self, path: Path, row: int, col: int) -> NameRef | None: ...
    def declaration_starting_at(self, path: Path, row: int, col: int) -> Declaration | None: ...
    def target_of(self, target: NameTarget) -> Target | None: ...
    def target_of_declaration(self, declaration: Declaration, path: Path) -> Target | None: ...
    def all_references(self) -> tuple[NameRef, ...]: ...
    def reference_in_span(self, span: SrcSpan) -> NameRef | None: ...
```

`resolve()` 是核心：先在引用表里找覆盖该位置的最内层名字，找不到再退到声明索引（声明处是「名字
被引入」而不是「被使用」）。它返回 `Resolution(target, expression_type)`——`target` 回答跳转，
`expression_type` 回答悬停里的表达式类型。位置在注释、空白或分析没检查过的定义里时返回 `None`，
而不是跳到无关位置。

`Target` 携带名字、`DeclarationKind`、名字 span、渲染后的类型或签名、容器名，以及 `stdlib` 标志；
签名是从实例化后的类型渲染的，所以 `Pair<f64>.of` 显示 `f64` 而不是声明处的 `T`。

`Navigator(result, ...)` 内部的读取全部委托给视图（`navigator.view` 就是它），自己只保留解析逻辑；
按请求创建，因此它的有效范围和它基于的那个快照一样长。

定义体的范围是 parser 记下的事实：`AST.Block.span` 只有开括号（错误信息指那里），所以 parser 另外
记录 `end`（闭括号之后），`full_span()` 给出整段；`AST.Import` 同理记录语句的结束位置。上层据此判断
"某个引用是否在某个定义体内"，不再到 token 流里数花括号。

### 声明索引

```python
class DeclarationKind(Enum):
    MODULE, IMPORT, FUNCTION, METHOD, STRUCT, ENUM, TRAIT,
    ALIAS, FIELD, VARIANT, PARAMETER, VARIABLE

@dataclass(frozen=True)
class Declaration:
    name: str
    kind: DeclarationKind
    path: Path
    span: SrcSpan | None      # 名字 span；模块与合成声明为 None
    container: str | None = None
    type_name: str | None = None
    module: str | None = None
    public: bool = False

def build_index(units, type_ctx, import_edges=None, packages=None) -> Index: ...
```

`Index` 提供 `in_file(path)`、`by_name(name)`、`dependents_of(path)`（直接导入该文件的所有文件），
以及 `declarations`、`imports`、`packages`、`modules` 四个映射。索引覆盖整个被分析的文件集合，
包括 `main` 不可达的库函数。

会话交给调用方的是**未构建**的索引（`LazyIndex`）：它只是 `units`、类型空间、import 边与包映射的
投影，第一次有人提问时才构建并缓存（`built` 说它是否已经建好）。理由是只有编辑器读它：
`yianc --analyze` 从不读，一次没有后续查询的保存也不需要它，而建索引在 39/95/285 文件上要
7/17/59 ms。`build_index(...)` 仍是立即构建的入口，供测试与一次性脚本使用。

类型空间里才有的东西（结构体字段、枚举成员）从类型空间取，它们的 span 是声明时登记的；函数体内的
`let`、`for` 变量、match 载荷绑定、闭包参数与捕获也进索引，统一挂在所在函数名下（块级嵌套不建模）。

### 语义高亮与呈现层

语义分类不在这一层：它属于编辑器词汇（LSP 的 token 类型），住在
`lsp/semantic_tokens.py`，读的正是上面的视图与导航（`reference_starting_at`、`target_of`、
`declaration_starting_at`）。判断一个名字是什么颜色是呈现，判断它"指向哪个声明"才是分析。
同理，删除无效 import 的编辑范围在 `lsp/refactor.py`，补全项的插入文本（snippet 占位符）在
`lsp/completion.py`：分析层报告候选、参数名与事实，编辑器决定怎么写进缓冲区。

### 补全与签名提示

```python
def complete(result: AnalysisResult, path: Path, row: int, col: int, *,
             std_root: Path | None = None) -> CompletionResult: ...
def signature_help(result: AnalysisResult, path: Path, row: int, col: int, *,
                   std_root: Path | None = None) -> SignatureInfo | None: ...
```

补全从 token 流判断位置期望什么：`value`（可见符号、局部变量、基本类型）、`member`（`.` 左侧表达式
的静态类型，先自动解引用再列字段与方法）、`type`、`import_path`（包与模块名）、`import_name`
（目标模块的 `pub` 声明）。局部变量遮蔽模块名，同名项按先到者胜出去重。分析没走到符号表时
（语法错误在前端就停了），退化为「文件里出现过的标识符」，不带种类与类型，只求可用。

可调用项的 `detail` 是渲染好的签名，`parameters` 是参数名列表；插入什么文本（`name(${1:x})` 这样的
snippet）由 LSP 层决定。

### 引用、重命名与快速修复

```python
def find_references(result, path, row, col, *,
                    include_declaration: bool = True,
                    std_root: Path | None = None) -> ReferenceResult | None: ...
def rename(result, path, row, col, new_name: str, *,
           std_root: Path | None = None) -> RenameResult: ...
```

全部基于**符号身份**：引用算数当且仅当它和当前位置解析到同一个声明，所以不同作用域的同名符号
不会混在一起。重命名会拒绝而不是做一半：

- 新名字不是合法标识符、位置没有可重命名的东西；
- 目标是标准库符号；
- 分析没检查过的定义（例如从未实例化的泛型体）里出现了同名的名字——无法保证引用集合完整。

拒绝时 `RenameResult(refusal=…)`，LSP 层把它变成 `RequestFailed`（`-32803`）。别名导入只改导入语句
里的原名，使用处写的是别名，保持不动。拒绝判定留在这一层是有意的：它是数据完整性问题（改一半比
不改更糟），不是显示策略。

"删除无效 import"的快速修复在 `lsp/refactor.py`：它用视图给出的语句范围（`import_statements`）与
词法 token 决定删整条语句还是只删某一项与相邻分隔符。哪些诊断码该给动作、删多少字节，都是编辑
策略；诊断本身与语句范围是分析给出的事实。

## 项目模型与包映射

- 项目发现、加载、导入规则来自 `anx`：`Project.discover` / `load` / `files` / `resolve_import`。
- `PackageMap.from_document(raw, *, source=…)` 直接接收 `Project.compiler_package_map()` 的 v2 载荷，
  不需要写文件再读回；`PackageMap.parse(path)` 读 `--packages` 文件。两种入口共用同一份校验，未知
  版本直接报错。
- 标准库根用 `resolve_stdlib_root(compiler_root=None)` 定位，优先级是 `--compiler-root`（检出根）、
  `YIAN_LIB`（源码根本身）、`YIAN_ROOT`（检出根），最后回退到本模块所在的检出（editable 安装走这
  一条）。包模式下以 `packages["std"].source_root` 为准。根**从不**从输入路径推断。

## 最小用法

直接用 `AnalysisSession` 对一段未保存文本做一次分析，再取该文件的声明：

```python
from pathlib import Path

from compiler.analysis.documents import Document, DocumentStore
from compiler.analysis.session import AnalysisSession

source = """\
pub struct Point {
    x: i32,
    y: i32,
}

pub fn origin() -> Point {
    return Point(0, 0);
}
"""

scratch = Path("scratch.an")
documents = DocumentStore([Document(path=scratch, text=source, version=1)])

session = AnalysisSession()
result = session.analyze([Path("lib/src"), scratch], documents=documents)
print("ok:", result.ok(), "diagnostics:", len(result.diagnostics))
if result.index is not None:
    for declaration in result.index.in_file(scratch):
        print(declaration.kind.value, declaration.qualified_name)
print("key reusable:", result.key == session.snapshot_key(
    [Path("lib/src"), scratch], documents=documents))
```

输出（在仓库根运行，`lib/src` 是标准库源码根）：

```text
ok: True diagnostics: 0
module scratch
struct scratch.Point
field scratch.Point.x
field scratch.Point.y
function scratch.origin
key reusable: True
```

`scratch.an` 只存在于覆盖层，磁盘上没有这个文件；标准库仍从磁盘读。最后一行说明键没有变化，
调用方可以直接复用这次的结果。

命令行有一个同源的出口：`yianc --analyze [--json] <路径…>` 用同一个 `AnalysisSession` 跑一次前缀，
不开代码生成、不写 `build/`。`--json` 时 stdout 只有一个 JSON 对象（位置已经是 LSP 形状），其余
情况把诊断渲染到 stderr；退出码只区分成功与失败。它是调试与验收手段，不是第二套分析实现。
