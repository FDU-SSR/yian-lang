# 04 · 项目测试

`anx test` 运行**项目自己**的测试：`<项目根>/tests/` 下的每个 `.an` 文件都是一个用例。
需要运行的用例是带 `fn main()` 的完整程序；`.err.an` 用例只编译并匹配诊断子串。

## 布局与期望文件

```text
<项目根>/tests/
├── smoke.an                  # 用例：期望正常退出
├── output/
│   └── smoke.an.ans          # 期望 stdout（首行可为 "Exit code <N>"）
├── error/
│   └── bad.err.an            # 用例：期望编译失败
├── output/error/
│   └── bad.an.ans            # 必须出现的诊断子串
└── input/
    ├── args.args             # args.an 的命令行参数（按空白切分）
    └── args.stdin            # args.an 的标准输入
```

| 用例 | 期望文件 | 内容 |
| --- | --- | --- |
| `foo.an` | `output/foo.an.ans` | 期望输出；若首行是 `Exit code <N>`，则指定期望退出码，其余行是期望输出 |
| `foo.err.an` | `output/foo.an.ans` | 必须出现的诊断子串（编译必须失败） |
| 没有期望文件 | — | 只要求退出码为 0，不比对输出 |

- 比对时**两边都去掉首尾空白**，并且把程序的 stdout 与 stderr 合并后比较——所以
  panic / 断言消息也可以写成期望输出。
- `.args` / `.stdin` 按用例名（去掉 `.an` / `.err.an`）放在 `tests/input/` 下，
  例如 `tests/foo.an` → `tests/input/foo.args`。
- `.err.an` 只要求「编译失败 + 输出里含该子串」，不比对编译器的退出码。

## 用例是怎么编译的

每个用例都以 **package 模式**编译，并且 `anx` 会为该用例临时注册一个**合成测试包**：

```json
"__anx_test": {
  "sourceRoot": "<项目根>/tests",
  "kind": "bin",
  "entry": "<当前用例文件>",
  "ffi": "<根包的 ffi 布尔值>",
  "dependencies": ["<根包（仅 lib/hybrid）>", "<根包的依赖>…", "<根包的 dev 依赖>…"]
}
```

由此得到三条规则：

1. **用例可以像项目代码一样导入项目**：`from <包名>.<模块> import …`。
2. **可见性照常生效**：根包的直接依赖与 dev 依赖可见；**传递依赖不可见**（导入报 `E309`）；
   任何包的**入口模块不可导入**（导入报 `E307`）。
3. **根包是 `bin` 时，用例不能导入根包**——bin 没有库接口，这与 Cargo 一致（bin-only crate
   的 `tests/` 没有 library 可链接）。此时导入报 `error[E309]`。把根包声明成
   `kind = "hybrid"`（相当于 Cargo 里加 `src/lib.rs`），或把可复用代码放进一个 lib 依赖，
   即可暴露库接口。

合成测试包继承根包的 `ffi` 权限，因此 `ffi = true` 的项目测试可以定义 `ffi fn`。依赖包的 FFI 权限保持各自的声明，测试包不会因为导入某个 FFI 依赖而自动获得权限。

程序入口就是当前用例文件，所以项目自己的 `main`（`bin` / `hybrid` 的入口）只是一个普通函数，
不会和用例冲突。

## 输出与退出码

```console
$ anx test

Pointer mode: fat
  [ok] error/bad.err.an
  [ok] exit_code.an
  [ok] hello.an
  [ok] uses_project.an

4 passed, 0 failed, 4 total

Pointer mode: raw
  [ok] error/bad.err.an
  [ok] exit_code.an
  [ok] hello.an
  [ok] uses_project.an

4 passed, 0 failed, 4 total
```

失败的用例会在汇总之后再打印一份「期望 vs 实际」或编译器输出。

- `0`：全部通过
- `1`：有用例失败、`tests/` 下没有用例、项目加载有诊断、或标准库定位不到

`anx test` 默认按 fat、raw 顺序各运行一遍，并将中间产物和 package map 分别放在
`<项目根>/build/test/fat/` 与 `<项目根>/build/test/raw/`。`--pointer-mode fat|raw|both`
可选择一个或两种模式；`--raw-pointers` 保留为 raw 别名。两种参数同时出现时返回参数错误 2。
`-O` / `--release` 对选中的每个模式生效；一侧失败不会跳过另一侧，最终任一模式失败都会返回 1。

## 限制

- 没有「只跑匹配某个名字的用例」或并行开关：按名字排序、逐个编译并运行。
- 用例之间不共享编译产物：每个用例都会独立编译一次它用到的代码。
- **用例之间不能共享辅助模块**。`tests/` 下的每个 `.an` 文件都会被当成一个用例，因此：
  - 放一个没有 `main()` 的 `helper.an` 进去，它自己会作为一个用例失败
    （`No 'main' function found in the program entry`）；
  - 而且它也不会被传给编译器，所以 `from helper import …`（`E308`）与
    `from __anx_test.helper import …`（`E304`）都无法解析。

  对照 Cargo：`tests/common/mod.rs` 放在**子目录**里就不会被当作测试目标；anx 递归发现
  `tests/**/*.an`，没有这个逃生口。共享代码要放进 `src/`（用 `lib` / `hybrid` 根包）或放进
  一个依赖/dev 依赖。

## 与仓库自测的关系

仓库的四个套件（`basic` / `safety` / `package` / `bootstrap`）由 `scripts/run_tests.py` 驱动，只运行 native
`yianc`。`--pointer-mode both|fat|raw` 默认选择两种模式；`safety` 的 raw 项显示为 N/A，原因是该套件验证
fat 指针运行时检查。N/A 不计通过；若 raw-only 选择得到的用例全部 N/A，runner 返回 1。`package` 和
`bootstrap` 都使用同一个安装的 native `anx`，由 `YIANC` 指向规范化后的原生 compiler。
运行器只使用指定 prefix 中已有的工具，不安装或刷新；所选工具必须是可执行 ELF。旧参数
`--implementation python` 和 `--implementation both` 在选工具前报错，恢复入口是
`scripts/bootstrap_toolchain.sh`。`package` 套件用 `anx build` / `check` / `test` / `graph`
跑 `tests/package/` 下的项目 fixture；`bootstrap`
套件运行 `yianc`、`bootstrap/json`、`bootstrap/toml`、`bootstrap/jsonrpc` 和
`bootstrap/lsp_protocol` 的包级测试。外层 runner 每次为 `anx test` 指定单一模式，避免与 `anx test`
自身的默认 Both 展开叠乘；`graph` 不编译，只运行一次。
仓库 fixture runner 与 `anx test` 使用相同的 `.ans` / `.err.an` / `Exit code N` 约定，但职责不同：
`scripts/` 驱动仓库 package fixtures，`anx test` 驱动用户项目自己的测试。
