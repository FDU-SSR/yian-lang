# YIAN 开发计划

YIAN 迭代计划，以统一的语言语义、标准库和测试体系为基础，完善语言工具链与内存安全机制。工具链部分
（`anx` 包管理器、语言服务器与格式化器）已经落地，见手册 20–28；当前重点是胖指针性能优化与自举准备。
胖指针实现作为独立安全机制维护，其代码审查与正确性验证已告一段落，后续单独进行性能评估与优化。

## 计划语言特性

### 扩展 `comptime if` 常量求值

当前 `comptime if` 已支持布尔值、整数值、`@sizeof`、已实例化常量泛型值、整数和布尔转换，以及无副作用的整数与布尔运算。后续仅在出现明确使用需求时扩展可求值的 HIR 节点，并为新增表达式定义类型、溢出和失败诊断语义；该机制不扩大为可执行任意函数或副作用操作的完整编译期执行系统。

这项扩展作为按需能力维护，不纳入固定实施顺序。

## 开发实用性

### VS Code 插件与语言服务器

插件（`ide-support/vscode/`）提供语言注册与编辑体验：TextMate 语法高亮、注释切换、括号匹配与自动
闭合、缩进规则、代码片段、折叠标记，以及 `.an` 的默认编辑器设置。

语言服务器（`lsp/`，Python，stdio）已经提供：

- 实时诊断：词法、语法、名称/导入/可见性、类型与成员错误，带稳定错误码与文档版本号；
- 语义高亮：按符号索引给标识符分类，声明处加 `declaration`、标准库符号加 `defaultLibrary`；
- 补全与参数提示：按上下文区分值/成员/类型/导入位置，可调用项带签名与参数占位符；
- 导航：跳转定义、悬停（含实例化后的类型与签名）、文档符号（大纲）；
- 引用与重构：查找引用、当前文件引用高亮、重命名（无法保证完整时拒绝）、删除无效导入的快速修复；
- 格式化：`textDocument/formatting`，与 `yianc --format`、`anx fmt` 共用同一实现（手册 28）。

编辑器与命令行共用 `compiler/analysis/` 的分析接口：`yianc --analyze`、语言服务器看到的是同一份诊断、
符号与类型信息（手册 26、27）。插件启动本机已有的 `yian-lsp`，不随扩展打包 Python 运行时；扩展与服务
器版本同号，不一致时扩展在输出通道给出提示。

暂不提供：工作区符号搜索、`declaration`/`typeDefinition`/`implementation`、内联提示、折叠范围、选择
范围、文档链接、模糊匹配/snippet/文档注释补全、自动补 import；格式化不折行、不做列对齐、只支持整文件，
f-string 内部逐字保留。

语言服务器与 anx 共用项目配置和依赖解析规则，保证编辑器与命令行对同一项目的理解一致。

### anx 包管理器

anx 是 Python 实现，提供 `new`（`--kind bin|lib|hybrid`）、`build`、`run`、`check`、`test`、`fmt`、
`graph` 七个子命令：

- 项目模型：`package.anx` 声明元数据与依赖，`[dependencies]` 按包名参与构建，`[dev-dependencies]`
  只在 `anx test` 中可见；源码、测试与构建产物的目录规范由 `new` 的模板确定（手册 21、22）；
- 导入与依赖：导入路径按包名解析，`anx build` 生成 v2 包图 `build/pkg.json`，编译器据此解析跨包导入；
  依赖环、缺失依赖、入口缺失与可见性错误都有稳定诊断码（手册 23）；
- 流程：`anx build` / `run` / `check` 以项目为单位调用编译器，`anx test` 运行项目自己的测试
  （`<项目>/tests/` 下每个 `.an` 是一个程序），`anx graph` 输出依赖图与诊断，`anx fmt` 格式化根包
  自己的源码（手册 24、25）；
- 仍未做：远程依赖与版本解析。是否纳入后续开发范围待评估。

anx 继续使用 Python 开发。

## 安全机制

胖指针安全机制作为独立实现维护，不改变共同语言章节中的类型和赋值语义。

### 实现的完善

胖指针机制已有独立实现。围绕代码可维护性的实现审查与独立验证已告一段落，模块职责、安全检查插入点和运行时约束已经梳理。后续围绕性能开销继续优化实现方案。

**性能开销**：优化指针表示、运行时检查和内存池方案，同时考虑执行时间与内存占用。当前为保持生命周期锁槽可访问而采用的内存池仍需完善，应重点分析锁槽保留、堆块复用和碎片化对长期内存占用的影响，评估内存占用是否随重复工作负载趋于稳定。

### 安全机制真的安全吗?

可以参考的两类生命周期管理思路包括：

- 运行时自动内存管理，通过管理对象的存活与回收，避免仍被使用的对象提前释放；
- 编译时所有权和生命周期检查，通过限制引用与释放的关系，排除不合法的生命周期用法。

当前胖指针机制通过运行时检查，在非法内存操作实际执行前终止程序，以避免内存被破坏。但程序中的错误访问意图仍然可能出现，检查失败也会导致程序终止。这样的安全保证是否符合 YIAN 的目标，以及是否需要进一步减少错误访问的产生或提供其他处置方式，仍有待讨论。

这一部分暂时保留为开放问题，待与其他人讨论后，再确定是否以及如何调整语言设计和安全机制。

### 与 CHERI 的结合

CHERI 的内存保护机制可以从以下三个方面理解：

- 访问权限：通过能力指针（capability）携带的权限信息，限制允许执行的内存操作；
- 空间安全：通过 capability 携带的边界信息，限制内存访问范围；
- 时序安全：需要在基础 CHERI 机制之上引入额外的生命周期管理与撤销机制。

CHERI 主要通过运行时检查，在非法访问实际执行前将其阻止。它并不从语言层面排除错误访问的产生，检查失败后的程序处置仍是需要讨论的问题。

#### 空间安全

其核心思想是让指针携带访问边界和权限信息，并由硬件执行检查。这一机制已有较多研究与实现，但仍需关注以下问题：

1. 子对象（subobject）的边界：结构体成员等子对象有各自的访问范围，仅限制整个分配对象的边界，未必能阻止子对象之间的越界访问。如何设置和维护子对象边界，需要结合语言语义与编译器策略处理。
2. 边界的精确性：压缩边界编码对可表示的范围和对齐有一定要求，并非任意边界都能精确表示，需要编译器与分配器配合处理。

#### 时序安全

堆时序安全已有较为系统的研究，其中具有代表性的一项工作是：

Nathaniel Wesley Filardo et al. *Cornucopia: Temporal Safety for CHERI Heaps*. IEEE Symposium on Security and Privacy 2020. DOI: [10.1109/SP40000.2020.00098](https://doi.org/10.1109/SP40000.2020.00098)

其基本思路是延迟复用已释放对象的内存，并在复用前撤销旧引用：

1. 对象被 `free` 后，底层内存先进入隔离状态，暂不用于新的分配；
2. 撤销过程扫描可能保存 capability 的内存，并配合处理寄存器中的引用，使指向待回收对象的旧 capability 失效；
3. 完成必要的撤销后，再允许相应内存被重新分配。

后续工作进一步优化了撤销与扫描的开销。阅读这些方案时，需要区分“释放后立即阻止访问”和“复用前使旧引用失效”这两类保证。

栈时序安全方面，2026 年 8 月公开的 FRESCO 预印本提出了一种面向 CHERI 应用级处理器的方案：

*FRESCO: Complete and Scalable Temporal Safety for CHERI Application Processors*. arXiv: [2608.26353](https://arxiv.org/abs/2608.26353)

其中，栈着色机制的基本思路如下：

1. 为需要保护的函数调用分配生命周期标识，称为颜色（color）；
2. 从该栈帧派生出的 capability 继承对应的颜色；
3. 函数返回时，使对应颜色失效；
4. 使用 capability 访问内存时，由硬件检查颜色是否仍然有效，拒绝通过失效引用访问已退出的栈帧。

从“为栈帧分配生命周期身份，并在函数返回时使其失效”这一思路看，FRESCO 与 YIAN 的栈时序安全方案具有相似性。两者在标识表示、检查方式和标识复用等方面的差异，以及能否结合，仍需进一步分析。

## 自举

目标是用 YIAN 编写 YIAN 编译器，并使生成的编译器能够再次编译自身。以当前已经稳定的语言语义和标准库为基础，需要推进以下准备工作：

- 标准库哈希表与集合已有实现（`lib/src/collections/`），测试覆盖字符串键、容量与增长、克隆和资源管理；
  按编译器实际使用场景继续补充复合键等用例；
- 平台接口目前只有 `env.args` 与 `env.exit`，目录遍历、路径规范化、创建目录和启动子进程尚缺；
  初期可以由构建脚本承担部分工作；
- AST、类型信息和 IR 的数据表示及内存管理方式尚未确定，Arena 和节点 ID 等方案可作为候选，不预先限定；
- 脱离 Python `llvmlite` 的代码生成路径尚未开始。可以考虑直接生成文本 LLVM IR，再由外部 LLVM/clang
  工具完成后续编译和链接，不要求先实现 YIAN 版 llvmlite。

自举可按以下阶段推进，各阶段用于明确进展和完成判据：

| 阶段       | 完成判据                                                                                   |
| ---------- | ------------------------------------------------------------------------------------------ |
| 前端原型   | 能解析自举编译器源码，输出可与参考结果比较的 AST                                           |
| 编译器原型 | 能编译约定的语言子集，并通过相应的正例和错误诊断测试                                       |
| 自举闭环   | Python 版编译器生成第一代 YIAN 编译器，第一代能够编译自身源码并生成第二代                  |
| 稳定自举   | 两代编译器通过同一套测试，并在固定输入和构建条件下比较规范化 IR 或目标程序行为，确认一致性 |
