# 学期开发计划

本学期 YIAN 迭代计划，以 `develop` 分支为开发基线。胖指针实现位于 `secl` 分支，完善后合入 `develop`。

## 底层内存管理模型

目标是采用显式内存管理和按位复制语义，具体规则如下：

- 赋值、函数传参和返回值传递采用**按位复制**（bitwise copy）。
- 内存的分配和释放由程序员自行管理，编译器不会自动释放内存，也不会自动调用析构函数。
- `del` 仅释放目标内存，不递归释放成员所引用的内存。
- 容器按位复制后，副本共享底层存储。任意副本释放底层存储后，其他副本对应的存储也不可再使用；释放协调和后续访问产生的后果由程序员承担。
- 标准库通过 `Clone` trait 提供深拷贝接口，由程序员显式调用；赋值、传参和返回不会自动触发深拷贝。

以上是目标语义。当前 `develop` 中仍使用显式复制、移动等机制，需要同步调整编译器、标准库、测试和语言文档，使其符合上述规则。

- 代码补全；
- 实时语法与类型诊断；
- 悬浮类型信息；
- 定义跳转和引用查找；
- 重命名及其他代码重构功能。

Language Server 暂定使用 Python 开发。详细阶段、技术选项和验收标准见 [IDE 支持开发计划](plan/ide-support-plan.md)。现阶段保留完整功能目标，后续根据实际进度调整。

语言服务器与 anx 应共用项目配置和依赖解析规则，保证编辑器与命令行对同一项目的理解一致。

## 安全机制

目前的安全机制见 [YIAN 内存安全机制概述](security.md)。

### 实现的完善

胖指针机制已经在 `secl` 分支实现，后续围绕代码可维护性和性能开销两个方向优化实现方案。

**代码可维护性**：现有实现中包含大量 AI 生成代码，需要审查代码结构与质量，梳理模块职责、安全检查插入点和运行时约束，改善可读性，并补充支持后续修改的回归验证。

**性能开销**：优化指针表示、运行时检查和内存池方案，同时考虑执行时间与内存占用。当前为保持生命周期锁槽可访问而采用的内存池仍需完善，应重点分析锁槽保留、堆块复用和碎片化对长期内存占用的影响，评估内存占用是否随重复工作负载趋于稳定。

完善并验证后，将胖指针机制合入 `develop`。

### 安全机制真的安全吗?

可以参考的两类生命周期管理思路包括：

- 运行时自动内存管理，通过管理对象的存活与回收，避免仍被使用的对象提前释放；
- 编译时所有权和生命周期检查，通过限制引用与释放的关系，排除不合法的生命周期用法。

当前胖指针机制通过运行时检查，在非法内存操作实际执行前终止程序，以避免内存被破坏。但程序中的错误访问意图仍然可能出现，检查失败也会导致程序终止。这样的安全保证是否符合 YIAN 的目标，以及是否需要进一步减少错误访问的产生或提供其他处置方式，仍有待讨论。

这一部分暂时保留为开放问题，待与其他人讨论后，再确定是否以及如何调整语言设计和安全机制。

### 与 CHERI 的结合

CHERI 的内存保护机制可以从以下三个方面理解：

- 访问权限：通过能力指针（capability）携带的权限信息，限制允许执行的内存操作；
- 空间安全：通过 capability 携带的边界信息，限制内存访问范围；
- 时序安全：需要在基础 CHERI 机制之上引入额外的生命周期管理与撤销机制。

CHERI 主要通过运行时检查，在非法访问实际执行前将其阻止。它并不从语言层面排除错误访问的产生，检查失败后的程序处置仍是需要讨论的问题。

#### 空间安全

其核心思想是让指针携带访问边界和权限信息，并由硬件执行检查。这一机制已有较多研究与实现，但仍需关注以下问题：

1. 子对象（subobject）的边界：结构体成员等子对象有各自的访问范围，仅限制整个分配对象的边界，未必能阻止子对象之间的越界访问。如何设置和维护子对象边界，需要结合语言语义与编译器策略处理。
2. 边界的精确性：压缩边界编码对可表示的范围和对齐有一定要求，并非任意边界都能精确表示，需要编译器与分配器配合处理。

#### 时序安全

堆时序安全已有较为系统的研究，其中具有代表性的一项工作是：

Nathaniel Wesley Filardo et al. *Cornucopia: Temporal Safety for CHERI Heaps*. IEEE Symposium on Security and Privacy 2020. DOI: [10.1109/SP40000.2020.00098](https://doi.org/10.1109/SP40000.2020.00098)

其基本思路是延迟复用已释放对象的内存，并在复用前撤销旧引用：

1. 对象被 `free` 后，底层内存先进入隔离状态，暂不用于新的分配；
2. 撤销过程扫描可能保存 capability 的内存，并配合处理寄存器中的引用，使指向待回收对象的旧 capability 失效；
3. 完成必要的撤销后，再允许相应内存被重新分配。

后续工作进一步优化了撤销与扫描的开销。阅读这些方案时，需要区分“释放后立即阻止访问”和“复用前使旧引用失效”这两类保证。

栈时序安全方面，2026 年 8 月公开的 FRESCO 预印本提出了一种面向 CHERI 应用级处理器的方案：

*FRESCO: Complete and Scalable Temporal Safety for CHERI Application Processors*. arXiv: [2608.26353](https://arxiv.org/abs/2608.26353)

其中，栈着色机制的基本思路如下：

1. 为需要保护的函数调用分配生命周期标识，称为颜色（color）；
2. 从该栈帧派生出的 capability 继承对应的颜色；
3. 函数返回时，使对应颜色失效；
4. 使用 capability 访问内存时，由硬件检查颜色是否仍然有效，拒绝通过失效引用访问已退出的栈帧。

从“为栈帧分配生命周期身份，并在函数返回时使其失效”这一思路看，FRESCO 与 YIAN 的栈时序安全方案具有相似性。两者在标识表示、检查方式和标识复用等方面的差异，以及能否结合，仍需进一步分析。

## 自举

目标是用 YIAN 编写 YIAN 编译器，并使生成的编译器能够再次编译自身。以 `develop` 为基础，需要推进以下准备工作：

- 完善并充分测试标准库哈希表和集合，覆盖字符串键、复合数据、扩容、删除和资源管理等编译器使用场景；
- 补充目录遍历、路径规范化、创建目录和启动子进程等平台接口；初期可以由构建脚本承担部分工作；
- 确定 AST、类型信息和 IR 的数据表示及内存管理方式，Arena 和节点 ID 等方案可作为候选，不预先限定；
- 设计脱离 Python `llvmlite` 的代码生成路径。可以考虑直接生成文本 LLVM IR，再由外部 LLVM/clang 工具完成后续编译和链接，不要求先实现 YIAN 版 llvmlite。

自举可按以下阶段推进，各阶段用于明确进展和完成判据：

| 阶段       | 完成判据                                                                                   |
| ---------- | ------------------------------------------------------------------------------------------ |
| 前端原型   | 能解析自举编译器源码，输出可与参考结果比较的 AST                                           |
| 编译器原型 | 能编译约定的语言子集，并通过相应的正例和错误诊断测试                                       |
| 自举闭环   | Python 版编译器生成第一代 YIAN 编译器，第一代能够编译自身源码并生成第二代                  |
| 稳定自举   | 两代编译器通过同一套测试，并在固定输入和构建条件下比较规范化 IR 或目标程序行为，确认一致性 |

在大规模编写自举编译器前，应先明确赋值与释放语义，并使依赖的标准库与之保持一致，以减少后续迁移工作。
