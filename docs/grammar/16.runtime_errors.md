# 16 运行时错误与安全终止

本章规定 YIAN 对不可恢复运行时错误的统一报告和进程终止约定。它的目标是让安全检查失败成为一种确定、可识别的 fail-stop 行为：危险操作不会执行，程序不会进入不安全状态，并且调用方能够通过稳定的退出状态和错误编号识别失败原因。

## 错误类别

YIAN 将失败分为以下几类：

| 类别 | 处理方式 |
| --- | --- |
| 编译错误 | 编译器向标准错误输出诊断并返回非零状态；不生成可执行程序 |
| 可恢复错误 | API 使用 `Option` 或 `Result` 返回，由程序显式处理 |
| `@panic` | 报告程序逻辑错误并立即终止进程 |
| 安全错误 | 在非法内存操作执行前报告错误并立即终止进程 |
| 运行时资源错误 | 在无法维持语言运行条件时报告错误并立即终止进程 |

I/O 失败、解析失败、键不存在等预期内的业务错误不应自动变成安全错误。只要调用方能够合理恢复，就应优先使用 `Option` 或 `Result`。

## Fail-stop 语义

安全错误和不可恢复的运行时资源错误遵循同一终止规则：

1. 在危险读取、写入、指针运算或释放真正发生前完成检查。
2. 检查失败时向标准错误输出一条诊断。
3. 不继续执行当前表达式、后续用户代码或其他可能依赖无效状态的操作。
4. 不展开调用栈，不自动调用 `Drop`，也不运行语言级清理逻辑。
5. 以进程退出码 `1` 终止。
6. 即使标准错误不可写，进程也必须终止。

退出码只区分成功和失败；具体失败种类由诊断中的稳定错误编号表示。这样可以避免让调用方依赖平台相关的信号编号。

正常触发的安全检查不得以 SIGILL、SIGSEGV 或 SIGABRT 作为规定行为。这些信号若出现，应视为编译器、运行时或外部本机代码的实现错误，而不是 YIAN 安全错误协议的一部分。

安全错误不可被用户代码捕获。需要恢复的条件必须在危险操作之前通过普通控制流、`Option` 或 `Result` 表达。

## 诊断格式

安全错误使用以下格式：

```text
yian: safety error [S001]: out-of-bounds memory access
```

不可恢复的运行时资源错误使用：

```text
yian: runtime error [R001]: allocation size overflow
```

显式 `@panic` 使用：

```text
yian: panic: <message>
```

诊断格式遵守以下规则：

- 输出到 `stderr`，并以换行结束；
- 错误编号和对应的规范英文名称属于稳定接口；
- 初始协议不输出对象地址、生命周期键、锁值或其他安全元数据；
- 第一版不携带源码位置；
- 实现不能为了生成诊断而分配内存、访问待检查指针或调用可能再次失败的 YIAN 标准库代码。

## 安全错误编号

第一版协议采用下列安全错误编号：

| 编号 | 规范名称 | 适用场景 |
| --- | --- | --- |
| `S001` | `out-of-bounds memory access` | 数组、切片、字符串或对象访问超出有效范围 |
| `S002` | `invalid memory access` | 生命周期和空间条件被合并检查，无法进一步区分具体失败条件 |
| `S003` | `dangling reference access` | 指针或引用指向的生命周期已经失效 |
| `S004` | `invalid pointer arithmetic` | 指针偏移超出对象范围或计算发生整数回绕 |
| `S005` | `invalid cross-object pointer operation` | 对不同对象的指针执行没有定义的排序或求差 |
| `S006` | `invalid deallocation` | 双重释放、释放栈地址、释放内部地址或释放非完整堆对象视图 |
| `S007` | `empty slice cannot form a reference` | 尝试将不含元素的切片转换成单元素引用 |

`S002` 有意保持为较粗粒度的类别。一次合并检查可能同时验证生命周期和边界；如果不能在不重复检查或增加正常路径开销的情况下确定具体原因，实现可以报告 `S002`。

## 运行时资源错误编号

| 编号 | 规范名称 | 适用场景 |
| --- | --- | --- |
| `R001` | `allocation size overflow` | 分配数量与元素大小的计算无法由目标地址空间表示 |
| `R002` | `memory allocation failed` | 底层分配器无法提供所需存储 |
| `R003` | `safety metadata exhausted` | 生命周期键、帧锁槽或其他保证安全性所必需的有限元数据耗尽 |

这些错误不是非法访问本身，但程序已经无法继续维持规定的安全不变量，因此采用与安全错误相同的立即终止规则。

## `@panic` 与安全错误的区别

`@panic(message)` 由程序显式调用，也用于 `assert`、失败的 `unwrap` 和部分不可恢复的标准库前置条件。它表示程序逻辑无法继续，不表示运行时已经发现非法内存操作。

`@panic` 与安全错误都以退出码 `1` 终止，区别由诊断前缀表示：

```text
yian: panic: assertion failed
yian: safety error [S001]: out-of-bounds memory access
```

两者都不触发栈展开或隐式 `Drop`。如果某项失败属于 API 的预期结果，API 应返回 `Option` 或 `Result`，而不是依赖 `@panic`。

标准库可以使用内部形式 `@runtime_fail("S001")` 报告固定的安全或资源错误。它只接受一个指定编号的字符串字面量，由编译器在编译期转换为错误码；普通用户代码不能调用它。

## 编译模式

统一错误协议只规定实际执行的检查如何失败，不要求所有编译模式生成同一组检查：

- 默认 fat 模式生成的边界、生命周期、指针运算和释放检查必须遵守本协议；
- `--raw-pointers` 模式不携带胖指针元数据，也不提供胖指针内存安全保证，不能承诺
  报告 fat 模式才会生成的检查；
- 分配大小溢出、分配失败等独立于胖指针表示的致命错误，只要相应检查存在，就应使用同一运行时资源错误协议。

## 测试约定

预期发生安全错误的运行时测试应同时记录退出码和规范诊断。例如：

```text
Exit code 1
yian: safety error [S001]: out-of-bounds memory access
```

测试至少应验证：

- 退出码为 `1`；
- 错误编号和规范消息正确；
- 诊断写入 `stderr`；
- 危险操作之后的代码没有执行；
- 不以 `Exit code -4` 或其他平台信号状态表示正常安全失败。

## 当前实现状态

本章定义的协议已覆盖 `panic`、编译器插入的安全检查、标准库边界检查、分配失败和安全元数据耗尽。它们都通过不分配内存且不可返回的底层失败入口输出诊断，并以退出码 `1` 终止。
