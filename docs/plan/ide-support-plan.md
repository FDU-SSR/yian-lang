# YIAN IDE / VS Code 支持开发计划

### IDE / VS Code 支持开发计划

#### 1. 目标、范围与基本原则

##### 1.1 总体目标

为 YIAN 提供一套可安装、可调试、可回归测试的编辑器支持，使开发者在编辑 `.an` 文件时能够完成以下工作：

- 识别 YIAN 文件并提供注释、括号、折叠和自动闭合等基础编辑行为；
- 对关键字、字符串、数字、类型、函数、变量和运算符进行基础语法高亮；
- 在代码未保存、尚未完整输入时给出尽可能稳定的语法和语义诊断；
- 跳转到函数、结构体、枚举、类型别名、变量、字段和方法的定义；
- 查看当前符号的类型、签名和文档；
- 根据作用域、导入关系和接收者类型提供上下文相关的代码补全；
- 区分声明、引用、类型、函数、变量、参数、字段和枚举成员等语义对象的颜色；
- 为后续的查找引用、重命名、格式化和代码操作留下接口。

##### 1.2 暂不纳入第一阶段的范围

- 调试器、断点、单步执行和变量查看；
- 自动修复所有类型错误；
- 完整的 IDE 项目管理界面；
- 为了编辑器支持而改变 YIAN 的语言语义；
- 在没有性能数据的情况下直接引入增量编译器、增量解析器或新的类型系统。

##### 1.3 基本原则

1. 编译器前端是语言规则的主要来源，插件中不重复实现一套独立的 YIAN 语法和类型规则。
2. 编辑器分析与 LLVM、clang、可执行文件生成解耦；编辑器功能只需要进行词法、语法、符号和类型分析。
3. 先定义稳定的分析数据模型和功能边界，再决定采用哪种 VS Code API、通信协议和实现语言。
4. 所有功能都必须考虑未保存文本、半成品代码、错误恢复和跨文件依赖。
5. 每个阶段都必须有自动化验收用例，不能只以“在本机看起来能用”为完成标准。

#### 2. 当前基础与主要问题

##### 2.1 已有基础

当前仓库中的 `ide-support/yian-language-support-0.0.10.vsix` 已包含一个基础扩展，能够：

- 将 `.an` 文件注册为 `yian` 语言；
- 通过 `language-configuration.json` 配置注释、括号和自动闭合；
- 通过 TextMate grammar 对关键字、字符串、数字、函数调用、类型和运算符进行词法级高亮。

当前 VSIX 没有语言服务器，`extension.ts` 也没有实现补全、跳转定义、悬停信息或诊断逻辑。因此，现阶段的高亮主要依据正则表达式和命名习惯，无法可靠判断跨文件符号和真实类型。

##### 2.2 编译器中可复用的能力

现有编译器已经具备实现语言工具所需的大部分基础构件：

- `compiler/frontend/lex/`：词法分析和 token 的源码范围；
- `compiler/frontend/parse/`：AST 以及 AST 节点的源码范围；
- `compiler/analysis/passes/global_resolve.py`：跨文件导入、符号和类型的解析；
- `compiler/analysis/symbol/`：作用域和符号表；
- `compiler/analysis/ty/`：类型表示、类型解析和方法查找；
- `compiler/analysis/unit/hir.py`：带有 `symbol_id`、`type_id` 和源码范围的语义节点；
- `compiler/analysis/error.py`、词法错误和语法错误：可转换为编辑器诊断。

##### 2.3 需要优先解决的问题

当前编译器主要为“一次性编译文件”设计，而编辑器需要“持续分析内存中的半成品文件”，主要差异包括：

1. Lexer 当前以文件路径为输入，语言工具需要直接接收编辑器内存中的文本。
2. Parser 遇到错误时可能立即停止，编辑器需要错误恢复并尽量继续产生 AST。
3. 编译器的源码位置和编辑器的 `Position` 坐标约定不同，需要统一行、列和 Unicode 字符计数方式。
4. 符号对象需要能够追溯到声明位置；引用对象需要能够追溯到同一个符号。
5. 当前类型检查流程从 `main` 出发处理可达定义，编辑器还需要分析没有被 `main` 调用的辅助函数和库文件。
6. 编辑器需要维护项目根目录、标准库、包依赖和导入图，并在文件变化后只重新分析受影响的内容。

#### 3. 功能分层与阶段总览

下面的阶段是能力依赖关系，不是固定工期。每个阶段完成后才能进入下一阶段；如果验收发现性能或架构问题，应允许在当前阶段回退或调整技术路线。

| 阶段 | 名称 | 主要交付物 | 阶段门槛 |
| --- | --- | --- | --- |
| P0 | 需求、样例和验收基线 | 功能矩阵、测试项目、坐标约定、性能指标草案 | 所有人对“支持什么”和“如何验收”达成一致 |
| P1 | 基础扩展整理 | 可编译、可安装的扩展源码；语言注册、基础高亮和编辑行为 | 新环境安装后 `.an` 文件可正常识别和编辑 |
| P2 | 编译器分析接口 | 面向内存文本的分析会话、统一位置模型和结构化诊断 | 不生成 LLVM/可执行文件也能得到稳定分析结果 |
| P3 | 工作区与符号索引 | 项目发现、依赖解析、跨文件索引和缓存失效 | 能在多文件项目中定位符号和依赖变化 |
| P4 | 实时诊断 | 词法、语法、导入、名称、类型诊断 | 修改未保存文本后诊断及时更新且不残留旧结果 |
| P5 | 导航与类型查看 | 跳转定义、文档符号、工作区符号、悬停信息 | 本地、跨文件、标准库和成员符号均可验证 |
| P6 | 补全与语义高亮 | 作用域补全、成员补全、导入补全、语义 token | 补全结果与当前作用域和类型一致 |
| P7 | 高级编辑能力 | 查找引用、重命名、格式化、代码操作 | 修改范围准确，不能误改无关文本 |
| P8 | 性能、打包与发布 | 回归套件、性能报告、VSIX 发布流程和用户文档 | 新用户可以独立安装、运行和反馈问题 |

#### 4. 各阶段详细计划与验收标准

##### P0：需求、样例和验收基线

**目标**：在写语言服务器之前，明确支持范围、测试方法和最低质量标准。

**工作内容**：

- 建立一个最小 YIAN 示例工程，至少包含主文件、辅助模块、标准库导入、结构体、枚举、类型别名、泛型、方法和错误代码；
- 为每项功能准备正例、负例、跨文件例和未完成输入例；
- 明确扩展支持的 VS Code 最低版本、Python 运行环境和项目打开方式；
- 记录 YIAN 源码位置与编辑器位置之间的转换规则，特别是 0/1 基坐标和 Unicode 字符；
- 定义交互性能指标草案，例如小型项目中诊断、补全和跳转的目标响应时间；指标在 P2 完成后根据实测结果冻结；
- 建立问题分类：编译器前端问题、分析模型问题、协议适配问题、扩展打包问题和性能问题。

**交付物**：

- 功能支持矩阵；
- `ide-fixtures/` 或等价的测试工程；
- 每个用例的期望诊断、定义位置、补全项和语义 token；
- 坐标转换和性能指标说明。

**验收标准**：

- 任何一项计划功能都能对应至少一个可重复的测试场景；
- 测试场景包含预期结果，而不仅是“插件不崩溃”；
- 明确哪些功能在第一版中不保证支持；
- 在不安装语言服务器的情况下，现有编译器测试仍能独立运行。

##### P1：基础扩展整理

**目标**：把当前只存在于 VSIX 中的基础能力整理为可维护、可构建的扩展工程。

**工作内容**：

- 建立扩展源码目录、构建脚本、调试配置和 README；
- 保留现有语言 ID `yian`、`.an` 文件关联和语言配置；
- 继续使用词法级语法高亮覆盖关键字、注释、字符串、数字、类型、函数、变量和运算符；
- 增加最小 snippets、括号匹配、注释切换和折叠配置；
- 添加语法高亮样例和 VS Code scope 检查方法；
- 不在这一阶段实现复杂的类型推导或跨文件分析。

**验收标准**：

- 在干净环境构建扩展并生成 VSIX；
- 安装后打开 `.an` 文件，语言模式自动识别为 YIAN；
- 注释切换、括号匹配、自动闭合和基础高亮均可工作；
- 使用 VS Code 的 token/scope 检查工具能看到预期 scope；
- 修改 grammar 后可以重复构建，不依赖开发者机器上的隐藏文件；
- 现有编译器全量测试结果不因扩展工程变化而改变。

##### P2：编译器分析接口

**目标**：从一次性 CLI 编译流程中抽出可被编辑器重复调用的分析接口。

**工作内容**：

- 设计与具体通信协议无关的分析会话，例如 `DocumentStore`、`AnalysisSession`、`AnalysisSnapshot` 和 `Diagnostic` 等概念；
- 支持以 `uri/path + text + version` 作为输入，不要求先保存到磁盘；
- 支持只运行 Lexer、Parser、导入解析、名称解析和类型分析，不启动 LLVM/clang；
- 统一源码范围、编辑器范围和诊断范围的转换；
- 为词法错误、语法错误和分析错误定义结构化错误格式，包括严重级别、消息、范围和错误码；
- 研究错误恢复策略：局部恢复、占位 AST、保留上一次有效 AST，或多种策略组合；
- 添加分析接口单元测试，确保 CLI 编译路径和编辑器分析路径共享语言规则。

**验收标准**：

- 给定一段未保存文本，可以在不生成可执行文件的情况下返回分析结果；
- 输入缺少括号、缺少分号、正在输入标识符等半成品代码时，分析服务不会退出；
- 同一个错误可以稳定映射到编辑器正确的行和列；
- 包含非 ASCII 字符的注释或字符串不会导致后续位置整体偏移；
- 分析接口出现错误时返回结构化结果，而不是依赖解析终端输出；
- 原有 `python3 scripts/run_tests.py` 全量测试继续通过。

##### P3：工作区、项目模型与符号索引

**目标**：让编辑器理解“当前打开的是一个项目”，而不是孤立地分析单个文件。

**工作内容**：

- 识别工作区根目录和 YIAN 项目配置；
- 发现项目源文件、标准库和路径依赖；
- 复用或适配 `anx` 的包名、依赖和导入解析规则；
- 建立文件、模块、导入边、声明、作用域和符号之间的索引；
- 为函数、结构体、枚举、trait、类型别名、变量、字段、方法和枚举成员记录声明位置；
- 明确文件变化后的失效范围：当前文件、直接依赖者、反向依赖者或整个项目；
- 设计缓存生命周期和取消旧分析请求的机制。

**验收标准**：

- 一个文件可以引用另一个文件中的公开函数、类型和结构体字段；
- 标准库和路径依赖能够被定位；
- 导入不存在、导入私有符号和循环依赖能够产生可定位诊断；
- 修改被依赖文件后，依赖它的文件重新分析，不需要重启服务；
- 未被 `main` 调用的库函数也能进入符号索引；
- 重复打开同一项目不会产生重复符号或重复诊断。

##### P4：实时诊断

**目标**：实现编辑器中最先可感知的语言服务功能。

**工作内容**：

- 接收打开、修改、保存和关闭文档事件；
- 对当前内存版本执行分析，并把错误发布到对应文档；
- 覆盖词法、语法、未定义符号、重复定义、导入错误、类型不匹配和成员不存在等类别；
- 支持一份文档的多个诊断，而不是只返回第一个错误；
- 新版本分析完成后清理旧版本诊断；
- 加入防抖、版本号检查和旧请求取消，避免慢请求覆盖新结果；
- 诊断中保留错误码和可选的相关位置，为以后代码操作做准备。

**验收标准**：

- 打开含错误的文件后出现红色波浪线和 Problems 面板条目；
- 修复错误后对应诊断消失；
- 连续快速输入时不会出现旧诊断覆盖新诊断；
- 关闭文件或删除文件后不会保留孤立诊断；
- 同一文件出现多个独立错误时，至少能报告预先定义的多个错误；
- 诊断过程不调用 LLVM、clang 或链接器；
- 小型测试工程的响应时间达到 P0 冻结的目标指标。

##### P5：导航与类型查看

**目标**：使符号能够在项目中被可靠地查找和解释。

**工作内容**：

- 实现跳转定义：局部变量、参数、函数、类型、字段、方法、枚举成员和导入符号；
- 实现文档符号：列出当前文件的顶层定义和嵌套成员；
- 视性能和项目规模决定是否实现工作区符号搜索；
- 实现悬停信息，至少显示符号种类、完整名称和解析后的类型/函数签名；
- 对标准库符号标记来源，必要时提供源文件位置；
- 对解析失败、重载歧义和不完整输入返回空结果或降级结果，不误跳到无关位置。

**验收标准**：

- 在声明和引用位置按“跳转到定义”都能得到同一个定义位置；
- 跨文件、跨包和标准库符号的跳转结果正确；
- 方法调用能够跳转到对应方法，而不是只跳到接收者类型；
- 文档符号树中的范围与源码结构一致；
- 悬停信息中的类型来自分析结果，不是通过字符串猜测；
- 删除或重命名定义后，旧位置不会继续作为有效结果返回。

##### P6：代码补全与语义高亮

**目标**：在已有可靠的符号表和类型分析基础上提供上下文补全及准确着色。

**工作内容**：

- 实现普通标识符补全：当前作用域、外层作用域、模块公开符号和预定义类型；
- 实现成员补全：根据 `.` 左侧表达式的类型列出字段和方法；
- 实现类型位置补全、函数调用参数提示和导入路径/导入名称补全；
- 为补全项提供种类、详细类型、文档、插入文本和必要的参数占位符；
- 去除同名重复项，并处理局部符号遮蔽；
- 根据符号索引产生语义 token，区分类型、函数、方法、变量、参数、字段、枚举成员、声明和标准库符号；
- 确保语义高亮失败时仍保留 P1 的基础语法高亮。

**验收标准**：

- 在文件开头、函数体内、类型位置、导入语句和成员访问位置分别得到预期候选；
- 补全结果不会包含不可见的私有符号；
- 成员补全与接收者的静态类型一致；
- 泛型、指针、切片和别名等至少覆盖 P0 中明确支持的类型场景；
- 输入未完成表达式时，补全仍能返回合理的降级结果；
- 语义 token 的范围不越过标识符，也不覆盖字符串和注释；
- 关闭语义高亮后，基础 TextMate 高亮仍然可用。

##### P7：高级编辑能力

**目标**：在符号身份和源码范围已经可靠的基础上，增加会修改代码的能力。

**工作内容**：

- 查找引用和当前文件引用高亮；
- 基于符号身份的安全重命名，覆盖跨文件引用和导入别名；
- 格式化策略评估：编写独立 formatter、复用解析树，或暂不提供格式化；
- 代码操作和快速修复，例如补充导入、删除无效导入或展示相关诊断；
- 对无法确认符号身份的情况拒绝批量修改，而不是按字符串全局替换。

**验收标准**：

- 查找引用不会把同名但不同作用域的符号混在一起；
- 重命名后项目内所有预期引用同步变化，字符串、注释和无关同名变量不被修改；
- 重命名操作可撤销，且修改范围可在编辑器预览；
- 格式化至少满足幂等性：连续执行两次结果相同；
- 任何代码操作都有对应的正例、歧义例和拒绝例。

##### P8：性能、回归、打包与发布

**目标**：把实验性功能整理为其他开发者可以安装和使用的版本。

**工作内容**：

- 建立编译器分析单元测试、协议测试、扩展宿主测试和人工验收清单；
- 为不同规模项目记录初始化、修改后重分析、补全和跳转的耗时与内存；
- 增加日志级别、日志文件和故障排查说明，但避免把调试信息显示为普通诊断；
- 确定语言服务器的分发方式：随 VSIX 打包、依赖本地 Python 环境，或提供独立可执行文件；
- 增加版本号、变更日志、安装说明、兼容性说明和卸载/回滚说明；
- 发布前运行编译器全量测试、IDE fixture 测试和 VSIX 安装冒烟测试。

**验收标准**：

- 干净环境能够按照 README 完成安装并打开示例工程；
- VSIX 安装后语言识别、基础高亮、诊断、导航和已承诺的补全功能全部可用；
- 语言服务器异常退出时，扩展能够记录可读日志，且不会让 VS Code 崩溃；
- 编译器原有测试、包管理器测试和 IDE 测试均通过；
- 发布版本、源码版本和测试版本的功能矩阵一致；
- 已知限制和未实现功能在文档中明确列出。

#### 5. 暂不锁定的技术路线与决策节点

本计划只固定功能边界、数据模型和验收标准，不预先固定具体实现。以下决策在获得原型和性能数据后再确定：

##### 5.1 VS Code 直接 API 还是语言服务器

- 直接使用 VS Code 的 `languages.*` API，适合只支持 VS Code、功能规模较小的实现；
- 使用 Language Server，适合复用现有 Python 编译器，并为其他编辑器保留可能性；
- P1 只要求扩展可维护，P2 先定义与 VS Code 无关的分析接口，P3 再根据复用成本、调试难度和性能决定最终接入方式。

##### 5.2 语言服务器的实现方式

候选方案包括：

- 直接在现有 Python 编译器进程中增加服务入口；
- 将分析逻辑和协议适配分成两个模块或两个进程；
- 使用其他语言重写编辑器侧索引，但继续复用 YIAN 的语法和类型定义；
- 先通过外部命令验证功能，再逐步改为结构化库调用。

选择标准是：能否复用编译器语义、能否处理未保存文本、启动和增量分析性能、安装复杂度、错误恢复能力以及未来支持其他编辑器的成本。

##### 5.3 解析与缓存策略

第一版可以从“打开文件后完整重分析”开始，先保证正确性；只有在 P0 的性能指标无法满足时，才考虑增量解析、增量类型检查或更细粒度缓存。缓存必须有明确的失效规则，不能因为速度优化而返回过期的定义、类型或诊断。

##### 5.4 高亮策略

TextMate grammar 继续作为基础回退方案；真实类型、函数、变量和字段的区分可以由语义 token 提供。两者应当能够同时存在，语义分析失败时不影响基础高亮。

##### 5.5 项目配置策略

优先复用现有 `anx` 的项目和依赖模型；如果编辑器启动时无法可靠发现项目，再评估是否增加单独的 YIAN 工具配置文件。新的配置文件必须说明与 `package.anx`、`--packages` 和标准库路径的关系，避免出现两套互相矛盾的项目规则。

#### 6. 测试与验收方法

每项功能至少通过以下三层测试中的两层，涉及代码修改的功能必须通过全部三层：

1. **分析单元测试**：直接输入源码文本，验证 token、AST、符号、类型、诊断和源码范围。
2. **协议集成测试**：模拟打开文档、修改文档、请求补全/定义/悬停并检查结构化响应。
3. **VS Code 冒烟测试**：安装 VSIX，在 Extension Development Host 或真实 VS Code 中验证用户可见行为。

重点回归场景包括：

- 空文件、只有注释的文件和只有半行代码的文件；
- 缺少括号、缺少分号、未完成泛型和未完成成员访问；
- 同名局部变量、嵌套作用域和参数遮蔽；
- 跨文件公开/私有符号、别名导入、标准库导入和循环依赖；
- 修改依赖文件后，依赖者的诊断、补全和跳转是否刷新；
- 中文注释、Unicode 字符串和多行文本后的源码位置；
- 大量诊断、快速连续编辑、文件关闭和语言服务器重启。

#### 7. 阶段完成的统一定义

一个阶段只有同时满足以下条件才算完成：

- 该阶段列出的功能已经实现或明确记录为不支持；
- 自动化验收用例通过；
- 没有已知的高优先级数据错误，例如跳转到错误定义、旧诊断残留或重命名误改文本；
- 相关文档、日志和故障排查方式已经补齐；
- 下一阶段所依赖的接口和限制已经记录；
- Git diff 只包含本阶段范围内的修改，生成的 VSIX、日志和缓存文件不会污染源码提交。
