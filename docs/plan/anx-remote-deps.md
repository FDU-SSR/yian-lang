# anx 远程依赖与版本：结论文档

本文件是 anx 中「远程依赖与版本」这一项的结论文档：**只出结论，不写实现**。范围限定为
「远程依赖下载」「版本约束与求解」「锁文件」三件事，结论按「纳入 / 不纳入 / 什么条件下重审」
给出，并说明理由与代价。

## 1. 结论摘要

| 事项 | 结论 | 何时重审 |
| --- | --- | --- |
| 远程依赖下载（URL / git / tarball） | **本阶段不纳入**，`[dependencies]` 只有 `path` | 出现「多个项目复用同一个包、且不想手工 `git clone`」的真实需求时 |
| registry（中心仓库）+ 发布流程 | **不纳入**，且不列入近期计划 | 有稳定的语言与 stdlib 版本、且有第三方愿意发布包时 |
| 版本约束（`^1.2`、`>=1.0,<2` 等范围） | **不纳入**；`version` 只做格式校验，不参与求解 | 远程依赖落地后，作为它的配套 |
| 锁文件（`anx.lock`） | **暂不纳入**；当前用「精确版本字符串 + 路径绝对化」即可复现 | 远程依赖落地时**必须**同时落地锁文件 |
| 内容哈希校验（完整性/供应链） | **不纳入**；路径依赖由文件系统权限与版本控制负责 | 远程依赖落地时**必须**同时落地 |
| 语义化版本（SemVer）语义 | 只在**文档层面**沿用「主版本不兼容」的约定 | 与版本约束同时 |

一句话：**anx 的依赖模型停在「路径依赖 + 精确版本记录」这一档，是有意的**；远程、求解、
锁文件是一组必须同时到来的东西，缺任何一个都会得到比现在更差的模型。

## 2. 判断前提

结论依赖四条现况，任何一条变化都应重新评估：

1. **编译单元是整个程序**。一次 `yianc` 调用把所有包的源码和 `lib/` 一起编译，
   单 `TypeCtx`、单 LLVM module、单一顶层命名空间。
2. **包之间传递的是源码，不是接口产物**：没有 `rlib` / `.swiftmodule` 这类可分发的稳定接口，
   也没有 ABI 兼容性概念。因此「同一个包的两个版本同时存在于依赖图」在源码整体编译下会
   直接撞名——这正是「YIAN 属于永远从源码一起构建这一档」的直接后果。
3. **没有版本求解**：`version` 目前只做格式校验，依赖图是纯路径图。
4. **生态规模**：目前没有第三方发布者，也没有 registry。依赖只发生在同一个开发者/团队自己的
   目录之间。

## 3. 逐项分析

### 3.1 远程依赖：为什么现在不做

远程依赖不是「加一个 `url` 字段」，它会连带引入一串必须同时决定的问题：

| 连带问题 | 不做的话会怎样 |
| --- | --- |
| 缓存放哪、怎么失效 | 每次构建重新下载，或缓存无限增长且无版本键 |
| 完整性校验 | 上游 force-push / 篡改无人察觉 |
| 离线与可复现构建 | 网络不可用时 `anx build` 直接失败 |
| 依赖的依赖如何声明 | 远程包自己也需要 `path` 之外的来源 |
| 传输协议与凭据 | 私有仓库需要 token，就得有配置文件与权限模型 |
| 供应链信任 | 谁有权发布、如何撤包/改名 |

这些正是 registry 需要回答的问题。在语言与 stdlib 还在演进、且没有第三方发布者的阶段，
把这些问题一次性做对的可能性很低；做一半（例如只支持 git URL）会得到一个比路径依赖
**更难排查**的模型：构建结果取决于远端默认分支的当前状态，而 manifest 里看不出来。

> Cargo 的文档把这件事讲得很直白：只写 `git = "..."` 意味着「使用默认分支上的最新提交」，
> 于是今天和明天构建出不同的东西；要可复现就必须手工写 `rev`，或者让锁文件替你记下来
> （[Cargo Book · Cargo.toml vs Cargo.lock](https://doc.rust-lang.org/cargo/guide/cargo-toml-vs-cargo-lock.html)）。
> 也就是说，**远程依赖与锁文件是同一件事的两半**。

### 3.2 版本约束与求解：为什么现在不做

版本选择问题在一般形式下是 **NP-完全的**：只要满足「依赖可以指定具体版本 / 版本之间可以
冲突 / 同一包的两个版本不能共存」这几条最小假设，就能把 3-SAT 归约到它
（Russ Cox, [Version SAT](https://research.swtch.com/version-sat)，2016）。Cargo 用回溯求解器、
Dart pub 也是，而 Debian/OPAM/Fedora 直接上 SAT 求解器——不是因为喜欢复杂度，而是没有别的选择。

YIAN **恰好满足**其中的「同一包的两个版本不能共存」：整体源码编译、单一顶层命名空间意味着
不能把同一个包的两份源码同时编进来并各自改名。所以如果引入版本范围，就必然引入求解，
以及求解失败时「为什么装不上」的解释问题。

Cox 给出的三条逃生路线，对应到 YIAN：

| 路线 | 代表 | 对 YIAN 的适用性 |
| --- | --- | --- |
| 只允许「最低版本」约束，取满足约束的最新版本 | Go modules 的 MVS | **可行**：算法线性且结果确定；代价是上游必须严格遵循 SemVer，且没有「排除某个坏版本」的表达能力 |
| 允许多版本共存，各自改名 | Cargo（同一个 crate 可链接两份） | **不可行**：与「整体源码编译 + 单一命名空间」冲突；要可行先得有按包产物（见 §3.4） |
| 主版本视为不同包 | SemVer 约定 | **可行但与第 1 条绑定**：`foo` 1.x 与 2.x 视为两个包名 |

结论：**不引入版本范围**。现在保留 `version` 字段只是一次「写下来」的动作，它的价值在于
将来若要落地 MVS，历史 manifest 不需要改。

### 3.3 锁文件：为什么暂不单独做

锁文件解决的是「约束 → 精确版本」这一步的确定性。当前的依赖模型**没有这一步**：

- 依赖来源是本地路径，`path` 已经精确到目录；
- 没有远程来源，也就没有「最新版本」这种东西会漂移；
- `version` 字段不参与任何决策。

所以现在生成一个 `anx.lock` 只会把 manifest 里已经有的信息抄一遍，多一份需要维护、
需要解释、可能与 manifest 漂移的文件。**得不偿失。**

一旦引入远程依赖，锁文件立刻从「冗余」变成「必需」：它必须记录来源 URL、解析出的
精确修订（commit / tarball 哈希）、内容哈希，以及每个包的直接依赖边；
`anx build` 默认只读锁文件，更新是显式动作（Cargo 的 `cargo update`、
Go 的 `go get`/`go mod tidy` 分工）。这一条应当与远程依赖放进**同一次设计**。

### 3.4 与自举、增量编译的关系

按包产物（本仓库尚未实现）有四条前置约束：产物必须含泛型定义与 trait impl、
泛型实例要内容寻址命名、失效分 iface/impl 两层、产物键必须含编译配置。这四条与
远程依赖是**独立**的两件事，但共享一个前提：**依赖的边界要能被内容唯一确定**。
按包产物需要内容寻址的实例名，远程依赖需要内容寻址的来源——两者都指向
「包身份 = 名字 + 内容哈希」，而不是「名字 + 版本范围」。这进一步说明：
**先把内容寻址的包身份想清楚，再谈远程与版本**，顺序反了要返工。

## 4. 建议路线

| 阶段 | 内容 | 触发条件 |
| --- | --- | --- |
| **P0（现在）** | 路径依赖 + 精确 `version` 字符串；`anx graph --json` 输出依赖图供脚本消费 | — |
| **P1** | 依赖来源扩展为「路径 \| git（带 `rev`）」，**同时**引入 `anx.lock`（记录来源与内容哈希）与完整性校验 | 出现跨项目复用同一个包的真实需求 |
| **P2** | 版本约束（只允许「最低版本」语义，Go MVS 路线）+ 锁文件更新命令 | P1 稳定，且确实需要「跟随上游新版本」 |
| **P3** | registry、发布流程、撤包与信任模型 | 有第三方发布者，且语言进入稳定期 |

P1 的验收标准应当是三条，而不是一条：**离线可构建、内容哈希可校验、锁文件与 manifest
不一致时有明确诊断**。只做到「能从网上下载」不算完成。

## 5. 明确不在范围内

- 不实现 SAT/回溯求解器，也不引入「版本范围」语法；将来若要做，也只做 MVS 式的线性算法。
- 不实现依赖重命名：依赖键必须等于被依赖包的规范名（`AX005`）。远程依赖落地后若要
  支持 vendoring fork，按「规范名解析 + 别名可读」的前提实现，不要绕过。
- 不做「同一包多版本共存」——它要求先有按包产物与内容寻址命名（见 §3.4）。
- 不做构建缓存本身；本项与缓存是两件事。
