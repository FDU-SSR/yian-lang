# 胖指针表示与 ABI 优化计划（方向 B）

本文件是胖指针性能优化的方向 B 细化（主计划见 `docs/plan/fat-pointer-performance-plan.md` 的
§4B 与 P2）。目标只有一个：降低**胖值本身**的成本——结构体/数组里的胖字段占用、按值拷贝、
节点尺寸与视图构造。

已经关闭的方案不在这里保留文本：32 位打包、统一锁表与 8 B 块头、按标量传参的调用约定、
16 B 打包字、8 B 字变体、检查层融合等，要么已经进了实现，要么已经实测否决，结论在提交历史
里。下面只留**尚未做**的候选、度量口径与验收方式。

## 0. 现状

| 类型 | 字段 | 尺寸 |
| --- | --- | --- |
| `T*` | data, word, index:u32, size:u32 | **24 B** |
| `T[]` / `str` | data, word, size:u64 | **24 B** |
| `T&` | data, word | **16 B** |
| 堆块头 | `{extent:u32, pad:u32}` | **8 B** |

`word = ⟨key:32 | lock:32⟩`；身份（key）在全局表 `__secl_lock_table` 的表项 `{key:u32, anchor_lo32:u32}`
里，`live = word ≠ 0 ∧ load32(表项.key) == key`；释放把表项 key +1 换代，帧退出把帧锁槽写成
`SENTINEL`。字段下标与谓词在 `compiler/codegen/cfg/lockmech.py`，LLVM 类型映射在
`compiler/codegen/llvm/types.py`。

**参数传递没有可动空间**：LLVM 的 x86-64 后端本就把一等聚合参数按八字节拆进整型寄存器序列
（`{ptr,i64,i32,i32}` 落 4 个寄存器），所以"胖值怎么传"这一项已经到底；返回值仍走 sret。

**已知取舍**：相对 32 位打包 + 块头锁槽的旧布局，`towers` +8.6%、`chase` +10.6%、
`churn_single` +14.3%。这三项与 16 B 指针布局绑定，换回去会重新输掉 `json` −18.8% /
`churn_mixed` −33.2%，属已接受的取舍，不再跟踪。

**表示线的状态**：尺寸相关的候选已全部关闭或收益缩水（§3），剩下值得做的是**视图构造与转换的
消解**（§3.3）这类不改变布局的代码形状优化。

## 1. 范围与不可动的不变量

下列语义与可观测行为**不动**，任何候选设计都要逐条对照：

| 不变量 | 内容 |
| --- | --- |
| 时序语义 | `live(p)` = 锁表项键比较（含空锁短路为假）；释放换代、键单调不回绕（R003）；帧退出写 `SENTINEL` |
| 空间语义 | 访问前检是**视图相对**的：`index < size`（切片子视图的越界必须失败），one-past 允许存在但不可解引用 |
| 指针运算与比较 | 算术只更新位置分量并检查良构/无回绕；相等按 `(data, 位置)`；序比较要求 `data` 相等；差要求 `data` 相等 + 良构 + 可表示 |
| 错误码 | S001/S002/S003/S004/S007 与 R001/R002 的触发条件与消息不变 |
| niche 布局 | `Option<T>`（T 为单字段包装的指针/切片/引用/字符串/函数指针）与 T 同尺寸，用全零 data 表示空 |
| ZST / raw | ZST 擦除规则不变；`--raw-pointers` 仍是 8 B 裸指针，不参与任何新表示 |
| 分配器边界 | 运行时只认块头 8 B `{extent, pad}` 与锁表项 `{key, anchor_lo32}`；表示改动不得要求分配器改变这些以外的语义（B3 见 §3.1 是例外——它要改块头与"地址 → 块"的反查） |
| 文档与测试可观测项 | `@sizeof` 的结果、`docs/grammar/02.type_system.md`、`docs/manual/12.llvm_codegen.md` 里的尺寸描述、`tests/` 里的 niche/布局断言必须同步 |

## 2. 度量基线

### 2.1 节点尺寸 → cache 足迹（C 微基准）

同一条链、只加 padding，2000 万节点取最小：

| 节点尺寸 | ns/节点 | 相对 16 B |
| --- | ---: | ---: |
| 16 B | 5.51 | — |
| 24 B | 7.42 | +35% |
| 32 B | 9.25 | +68% |
| 40 B | 10.99 | +99% |
| 64 B | 16.35 | +197% |

这条曲线解释了对象密集型基准为什么贵：把 8 B 的裸字段换成 16 B 的 `Option<T&>` 或 24 B 的
`Option<T*>`，节点尺寸直接决定追逐成本。**尺寸本身就等于 cache 足迹**，与检查开销独立。

### 2.2 静态计数（`-t ll`）——表示改动的下游面

改动面集中在少数中心函数（`__build_fat`、`__extract_fat_field`、`__fat_data`、`__fat_addr`、
`__stable_layout`），但下游代码量很大。热点基准里胖值的静态出现次数（下表列名是计划起点的
尺寸：`T*` 40 B / `T[]` 32 B / `T&` 24 B，与今天的 24/24/16 B 不同，仅用于看量级）：

| 基准 | 含胖值的函数定义 | 传胖值的调用点 | `extractvalue` | `insertvalue` | 40 B / 32 B / 24 B |
| --- | ---: | ---: | ---: | ---: | ---: |
| havlak | 179 | 438 | 6710 | 4531 | 8665 / 279 / 4824 |
| deltablue | 69 | 236 | 3835 | 3313 | 6535 / 113 / 2588 |
| json | 120 | 355 | 3969 | 2752 | 5289 / 466 / 2671 |
| richards | 43 | 100 | 1895 | 1104 | 2140 / 23 / 1629 |
| list | 10 | 34 | 152 | 44 | 94 / 13 / 346 |
| queen | 7 | 13 | 355 | 202 | 541 / 117 / 57 |
| towers | — | — | — | — | 253 / 13 / 249 |

对象图里 `T&`（16 B，`Option<T&>` 走 niche 不加 tag）与 `T*`（24 B，`dyn T(...)` 与指针算术）
同时密集，切片在 json/queen 这类数组负载里占多数。任何表示改动都会整体改变生成代码的形状——
必须用整基准的墙钟验收，不能只看单点。

## 3. 未做的候选

### 3.1 B3：更小的指针（⟨data, key⟩ + 地址反查）——收益已缩水，代价最大

**想法**：指针不再携带锁址（甚至不再携带 `index`/`size`），`live` 通过"地址 → 块"反查得到锁表项
再比较键；边界可以从块容量与视图本身取。反查需要分配器配合：块必须能从任意内部地址定位，
例如按页（4 KiB）维护"页 → 块"的边表，或把块按尺寸对齐让 `data & ~mask` 直接落到块首。

**按现状重算收益**（原计划里的 40 → 16 / 32 → 24 / 24 → 16 B 是按 32 位打包之前的基线算的，
现在不成立）。只把 64 位锁字换成 32 位 key、`index`/`size` 仍随指针走时：

| 类型 | 新形状 | 尺寸 | 相对现状 |
| --- | --- | ---: | --- |
| `T*` | `{data, key:u32, index:u32, size:u32}` | 20 → 对齐 **24 B** | **不变** |
| `T[]` / `str` | `{data, key:u32, size:u64}` | 20 → 对齐 **24 B** | **不变** |
| `T&` | `{data, key:u32}` | 12 → 对齐 **16 B** | **不变** |

继续减下去要动语义：`T*` 去掉 `index`/`size`（边界改从块容量取）才到 `{data, key}` = **16 B**，
切片要把 `size` 也压到 32 位才到 **16 B**。也就是说 B3 今天要拿收益，必须同时换掉边界来源或
接受 32 位长度上限——这两件事都比"省 8 B"大。

**代价**：`live` 从"1 次 load（锁表项通常与负载同 cache line）"变成"1–2 次额外依赖 load + 表格维护"；
分配器要维护边表（free 时清理），`madvise` 退页与悬垂读的语义（S003/S006）要重新论证；视图相对
越界语义要在新边界来源下逐条对齐。

**结论**：仍列为**可行性原型**，但优先级下调到"先证明它还有收益"这一步（§5）。启动前必须测
"当前 `live` 的实际命中率与延迟占比"，否则可能用一个更贵的检查换一个已经缩水的尺寸收益。

### 3.2 B4：用"末端地址"取代 `index` + `size`（备选）

**布局**：`{data:ptr, end:ptr, word:u64}` = **24 B**——与现状同尺寸，所以**没有尺寸收益**；它的
价值只剩两点：边界检查少一次"取 size + 乘"，以及用地址天然表达任意大的视图。

**代价**：切片的 `len()` 需要除法（或切片另存元素数）；与今天的 `index`/`size` 语义逐条对齐要
重写检查与文档；比较/差值的语义要重推。

**结论**：列为**备选**——只有当"32 位长度上限"这条语义收缩变得不可接受时才重新考虑。默认不做。

### 3.3 B5：视图构造与转换的消解（不是表示改动）

`T[] → T&` 退化、`ptr()`/`as_slice()` 往返、`Option` 解包处的 `insertvalue`/`extractvalue` 密集
（见 §2.2 的计数）本身有成本。先做度量（§5），再决定是否在 CFG 层消解冗余构造（例如同一视图
在同一块内反复退化只做一次）。收益不确定但风险低。

## 4. 度量与验收

### 4.1 微基准（`bench/fatptr/`）

方向 B 的效果在 shootout 里会被检查开销与算法结构淹没，用三件专项基准单独读：

| 基准 | 形态 | 观测目标 |
| --- | --- | --- |
| `copy_struct` | 结构体数组，每个元素含 `T*`/`T[]`/`T&` 字段，逐元素拷贝与传参 | 表示尺寸带来的拷贝/带宽差 |
| `call_abi` | 函数体大到不内联的被调者反复接收胖参，fat 与 raw 两态 | 每次调用的检查开销与传参档位 |
| `chase` | 链表/树节点追逐，节点里放 1 个胖引用，fat 与 raw 两态 | 节点尺寸 → cache 足迹 |

三件都已落地并进 `micro` 集合（`--set micro`）：
- `copy_struct`（`bench/fatptr/an/copy_struct.an`）与 `chase`（`chase.an`）用 `T&` 字段（16 B），
  因此对"引用尺寸"敏感；"结构里放 `T*`"的字段变体仍未加（并需同步提高规模，full 档读数原本偏小）。
- `call_abi`（`call_abi.an`）的调用次数与实参由 `env.args()` 派生，两个被调者一个收 1 个 24 B
  胖参、一个收 2 个，函数体大到三态都不内联（C 侧显式 `noinline`），因此三态跑的都是真实调用。
  基线（pin 4、min-of-5、`CALLS=4096`）：C 3.2ms / raw 3.3ms / fat 7.1ms（52.4 万次调用
  ≈ 6.1 / 13.4 ns 每调用）。
- **不要用递归做调用微基准**：线性递归加常量内存会被 `-O2` 归纳成循环（fat 态因为检查带副作用
  反而保得住调用），三态的跨态比值就失去意义；要"函数体大到不内联的调用循环"。

三件都遵守现有协议：`-O2`、绑核、min-of-N、峰值 RSS、fat/raw 比值；产物与运行器沿用
`bench/bench_three_way.py` 的形态（如需要可加 `--names` 的分组，不要另起一套）。

### 4.2 现有基准

`bench/results/full.csv`（22 项）与 `bench_allocator.py`（分配器）每次改动都要重跑：**整基准不退化**
是硬门槛，单点的改善不算数。本机口径：同一份代码两次全量跑的逐项差 ≤±0.5%，但**不同二进制之间**
（哪怕只差几条指令）会因布局/对齐产生 ±3–6% 的稳定差异，raw 态（不受表示改动影响）是同轮噪声对照。
因此单项 ±3% 以内先当前者之外的因素，±5% 以上必须用 equal-length 路径的交替 A/B 逐项复核，
并同时看中位数与分类（`T*` 密集 / 循环密集 / 分配密集）。

### 4.3 语义验收清单

除三套件（756/156/99，两种指针模式）与 `runtime/build.py --check --asan` 外，每项候选都要跑
现有安全语料里与表示相关的部分并逐条对照：

- one-past：`tests/safety/fat_oob_*`、`tests/basic/pointer/*one_past*`；
- 视图与子视图越界：`tests/safety/` 的 view/slice 用例、`check_view_access` 相关；
- 指针比较/差值/算术：`tests/basic/pointer/*`（含 `fat_ptr_diff`、`fat_arith_underflow`）；
- niche 与布局：`tests/basic/enum/niche_*`（`@sizeof(Option<T>) == @sizeof(T)`）、`tests/basic/zst/*`；
- 释放与复用：`tests/safety/fat_del_*`、`fat_dangle_after_rekey`、`fat_uaf`；
- raw 往返：`--raw-pointers` 下的全部 basic/safety 用例。

## 5. 余下的工作

### P2.5 迁移与文档（尾项）

**待办**：`docs/manual/12.llvm_codegen.md`、`docs/grammar/02.type_system.md` 里用户可见的尺寸描述
要逐处核对（是否还停在 40/32/24 B 与 16 B 块头的叙述），`docs/security.md` 与 `lockmech.py` 的
机制叙述保持一致；`bench/results/full.csv` 在干净提交上重跑并记录。
**验收**：文档与实测一致；仓库里没有互相矛盾的尺寸描述。

### B3 的前置度量（决定是否启动）

1. 测**当前 `live` 的实际成本占比**：检查点里锁表项 load 的命中率、与负载是否同 cache line、
   在 `towers`/`json`/`churn_single` 这些对检查敏感项上的延迟占比。
2. 按 §3.1 的表**重算收益**：只有在同时接受"边界改从块容量取"或"32 位长度"时才拿得到 16 B。
3. 两条都过关才做反查表原型；否则 B3 与 B4 一起关闭。

### B5 的度量与决定

在现有微基准里加"视图转换"项（同一视图反复 `T[] → T&`/`ptr()`/`as_slice()`），先读出现有构造/
提取成本；若占比可观，再在 CFG 层做同块内去重（只消解冗余构造，不动语义）。

## 6. 风险与开放问题

- **收益可能被高估**：§2.1 的曲线是"纯追逐"，真实基准里追逐与计算交织，节点尺寸的敏感度会低一些。
- **32 位长度上限是语义收缩**：`index`/`size` 压 32 位让"单对象 > 4 GiB 元素跨度"从可用变成报错，
  这是当前实现的对外可见限制；若要撤销，只有 B4（末端地址）这条路（§3.2）。
- **B3 会改动机制**：`live` 的实现方式、分配器的元数据、悬垂读语义都要重新论证；它是本计划里
  唯一还要动分配器的候选，必须先过 §5 的前置度量。
- **`-O0` 未纳入**：本计划与主计划一样只以 `-O2` 基线验收；如果 `-O0` 也需要，验收要分档。
- **C↔YIAN 的口径差**：`§2.1` 的曲线来自 C 微基准，只用于判断方向与量级，不作为 YIAN 的收益承诺。
  C 的结构体参数经 clang 变成 `byval`（强制按内存传），而 YIAN 传的是 LLVM 一等聚合（后端按八字节
  拆进寄存器）——凡涉及调用约定/参数传递的结论，必须在 `-t asm` / `-t bc -O2` 上复核，不能借 C 侧
  读数外推。
