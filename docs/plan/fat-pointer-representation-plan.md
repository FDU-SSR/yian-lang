# 胖指针表示与 ABI 优化计划（方向 B）

本文件是胖指针性能优化的方向 B 细化（主计划见 `docs/plan/fat-pointer-performance-plan.md` 的
§4B 与 P2）。方向 A 已经把"恒真的时序检查"消解掉一轮，剩下的开销分成两半：**每次访问的检查**
（方向 A 继续做）与**胖值本身的驻留、搬运与传参**（本文件）。

## 0. 状态（截至当前 HEAD）

**当前实现 = 变体 B（8 B 块头 + 全局锁表）+ 三处修复**（§3.7，采纳提交 `e0c5294`）。计划里其余候选的
最终裁定：

| 候选 | 裁定 | 依据 |
| --- | --- | --- |
| B1（32 位打包，锁字在块头） | **被变体 B 取代**（曾长期作为基线） | §3.7 修复后重测：19/22 项 ≤ B1、中位数约 −3%、最大项 −51% |
| B6（锁址+键打包成一个字，16 B 引用） | 否决并回退 | §3.6/§3.7：每检查点重建锁址压过"指针小 8 B"的带宽收益 |
| 变体 A（kind 在字里，8 B 头） | 否决并回退 | §3.7：32 位比较不是瓶颈，锁址重建才是 |
| B2（调用约定，不动布局） | **实测否决**（只做了参数侧原型） | §5 P2.2：LLVM 后端本就把一等聚合参数按八字节拆进整型寄存器序列（C 侧的"超 16 B 走栈"是 `byval` 语义），改签名后机器码逐指令相同 |
| B3（16 B 指针 + 地址反查） | 未做（只有 C 原型层评估） | §2.3/§3.3：机制改动最大、收益也最大，风险等级最高 |

**当前布局**（与 §2.1 的"计划起点"已不同）：

| 类型 | 字段 | 尺寸 |
| --- | --- | --- |
| `T*` | data, word, index:u32, size:u32 | **24 B** |
| `T[]` / `str` | data, word, size:u64 | **24 B** |
| `T&` | data, word | **16 B** |
| 堆块头 | `{extent:u32, pad:u32}` | **8 B** |

`word = ⟨key:32 | lock:32⟩`；身份（key）在全局表 `__secl_lock_table` 的表项 `{key:u32, anchor_lo32:u32}`
里，`live = word ≠ 0 ∧ load32(表项.key) == key`；释放把表项 key +1 换代（不再写块头 SENTINEL，
帧退出仍写帧锁槽）。

**已知回退（变体 B vs B1）与后续结论**：`towers` +8.6%、`chase` +10.6%、`churn_single` +14.3%。
之后做过专项调研（三条路逐个实测，记录在 §3.7 末尾）：CFG 层检查融合、LLVM 发射层分支融合、
以及"锚定指针直接读块头 key"的表示改动——**全部零收益或不可行**（前两者 LLVM 已自行等价化；
后者要动 ABI 且拿不到 B1 的便宜 `live`）。结论：这三项与 B1 的布局绑定，要拿回只能整体回到
B1 的 16 B 指针布局，代价是重新输掉 `json` −18.8% / `churn_mixed` −33.2%。

**阶段状态**：P2.1 ✅（三件微基准 `copy_struct`/`chase`/`call_abi` 均已落地并进 `micro` 集合）｜
P2.2 ✅ **实测否决**（详见 §5 P2.2）｜P2.3 ✅（后由变体 B 取代）｜P2.4 ✅（以变体 B 达成 16 B `T&`；
B6/A 否决）｜P2.5 部分（机制常量与 `lockmech` 注释已同步；`docs/manual/12.llvm_codegen.md` 等
用户可见的尺寸描述待核对）。

## 1. 范围与不可动的不变量

目标是降低"胖值本身"的成本：结构体/数组里的胖字段占用、按值拷贝、函数传参与返回、视图构造。
下列语义与可观测行为**不动**，任何候选设计都要逐条对照：

| 不变量 | 内容 |
| --- | --- |
| 时序语义 | `live(p)` = 锁槽键比较（含空锁短路为假）；释放换代、键单调不回绕（R003）。**载体可变、语义不变**：计划起点是块头锁槽 + 释放写 `SENTINEL`，变体 B 是全局表项按块换代（帧退出仍写 `SENTINEL`） |
| 空间语义 | 访问前检是**视图相对**的：`index < size`（切片子视图的越界必须失败），one-past 允许存在但不可解引用 |
| 指针运算与比较 | 算术只更新位置分量并检查良构/无回绕；相等按 `(data, 位置)`；序比较要求 `data` 相等；差要求 `data` 相等 + 良构 + 可表示 |
| 错误码 | S001/S002/S003/S004/S007 与 R001/R002 的触发条件与消息不变 |
| niche 布局 | `Option<T>`（T 为单字段包装的指针/切片/引用/字符串/函数指针）与 T 同尺寸，用全零 data 表示空 |
| ZST / raw | ZST 擦除规则不变；`--raw-pointers` 仍是 8 B 裸指针，不参与任何新表示 |
| 分配器边界 | 运行时只认当前块头（**计划起点**是 16 B `lock@0`/`active_size@8`；变体 B 落地后是 8 B `{extent, pad}` + 全局锁表项 `{key, anchor_lo32}`）；表示改动不得要求分配器改变块头以外的语义（B3 见 §3.3、B6 见 §3.6 是例外——两者都要改块头） |
| 文档与测试可观测项 | `@sizeof` 的结果、`docs/grammar/02.type_system.md`、`docs/manual/12.llvm_codegen.md` 里的尺寸描述、`tests/` 里的 niche/布局断言必须同步 |

## 2. 现状与度量

### 2.1 计划起点的布局（B1 时期）

> 本节是计划写就时的基线（B1）：`T*` 40 B / `T[]`·`str` 32 B / `T&` 24 B / 块头 16 B。
> **当前实现是变体 B，尺寸已不同——见 §0。** 下面保留原文，因为 §2.2 的度量与 §3 的候选
> 都是相对这个基线评估的。

| 类型 | 字段（下标） | 尺寸 | 说明 |
| --- | --- | --- | --- |
| `T*` | data(0), lock_ptr(1), key(2), index(3), size(4) | **40 B**，align 8 | 指针带完整视图（位置 + 视图长度） |
| `T[]` / `str` | data(0), lock_ptr(1), key(2), size(3) | **32 B** | 切片无 index（恒从视图起点算） |
| `T&` | data(0), lock_ptr(1), key(2) | **24 B** | 引用恒指单个元素，无空间分量 |
| raw 指针 | — | **8 B** | 诊断模式，无检查 |
| `Option<T*>` 等 | 同 T | 同上 | 全零 data 作 niche，不加 tag |

定义位置：字段下标与谓词在 `compiler/codegen/cfg/lockmech.py`；LLVM 类型映射在
`compiler/codegen/llvm/types.py`（`__handle_pointer/__handle_ref/__handle_slice`、`__stable_layout`）；
构造、字段提取与地址折算在 `compiler/codegen/llvm/builder.py`（`__build_fat`、`__extract_fat_field`、
`__fat_data`、`__fat_addr`）与 CFG 下降（各 `IR.*` 节点的合成/分解：`codegen/cfg/lower/` 各簇，
由 `codegen/cfg/passes/translator.py` 逐函数装配）。

改动面集中在这些中心函数，但**下游代码量很大**：热点基准里胖值的静态出现次数（`-t ll` 计数，
"40/32/24" 列是该尺寸的聚合类型在 IR 文本里出现的行数）：

| 基准 | 含胖值的函数定义 | 传胖值的调用点 | `extractvalue` | `insertvalue` | 40 B / 32 B / 24 B |
| --- | ---: | ---: | ---: | ---: | ---: |
| havlak | 179 | 438 | 6710 | 4531 | 8665 / 279 / 4824 |
| deltablue | 69 | 236 | 3835 | 3313 | 6535 / 113 / 2588 |
| json | 120 | 355 | 3969 | 2752 | 5289 / 466 / 2671 |
| richards | 43 | 100 | 1895 | 1104 | 2140 / 23 / 1629 |
| list | 10 | 34 | 152 | 44 | 94 / 13 / 346 |
| queen | 7 | 13 | 355 | 202 | 541 / 117 / 57 |
| towers | — | — | — | — | 253 / 13 / 249 |

两种形态在所有热点基准里都大量共存：对象图里 `T&`（24 B，`Option<T&>` 走 niche 不加 tag）与
`T*`（40 B，`dyn T(...)` 与指针算术）同时密集，切片（32 B）在 json/queen 这类数组负载里占多数。
所以任何表示改动都会整体改变生成代码的形状——必须用整基准的墙钟验收，不能只看单点。

### 2.2 尺寸的两种代价（新增微基准实测）

**(a) 按值传结构体的调用成本**（C，`-O2`，noinline 被调函数，4 亿次调用取最小；同机同核）：

| 被传形状 | ns/调用 | 相对 8 B |
| --- | ---: | ---: |
| 8 B 结构体 | 0.36 | — |
| 16 B 结构体 | 0.36 | 0% |
| 24 B 结构体 | 0.48 | +33% |
| 32 B 结构体 | 0.54 | +50% |
| 40 B 结构体 | 0.60 | +67% |
| 40 B 拆成 5 个标量 | 0.53 | +47%（比 40 B 结构体省 ~10%） |
| 32 B 拆成 4 个标量 | 0.49 | +36%（比 32 B 结构体省 ~9%） |

SysV 的分档是硬的：**≤16 B 走寄存器，>16 B 走内存**（调用者把聚合写到栈上、传指针，被调用者再读）。
所以 40 → 32 B 只能省一点拷贝，**换不到寄存器档**；要落到 16 B 档才有质变。

**(b) 指针追逐的节点尺寸成本**（C，同一条链，只加 padding，2000 万节点取最小）：

| 节点尺寸 | ns/节点 | 相对 16 B |
| --- | ---: | ---: |
| 16 B | 5.51 | — |
| 24 B | 7.42 | +35% |
| 32 B | 9.25 | +68% |
| 40 B | 10.99 | +99% |
| 64 B | 16.35 | +197% |

这条曲线解释了对象密集型基准为什么贵：把 8 B 的裸字段换成 24 B 的 `Option<T&>`，节点从
16 B 涨到 32 B 左右，追逐成本接近翻倍。**尺寸本身就等于 cache 足迹**，这与检查开销独立。

### 2.3 已排除的方向（先记下来，免得反复评估）

- **去掉 `key`**：`key` 是复用后旧指针不复活的唯一依据（`docs/security.md` §4），去掉等于放弃 ABA 保护，不做。
- **去掉 `lock_ptr`**：`live` 要读锁槽，锁槽地址必须能从指针得到。引用（`T&`）是重锚定的，
  `data` 与块起点没有固定关系，去掉 `lock_ptr` 就得引入"地址 → 块"的反查（见 B3），属于机制改动，
  不是省 8 B 的小事。
- **16 B 指针（⟨data, key⟩ + 反查）**：见 B3，收益最大但代价在每次检查。
- **16 B 指针（把锁址与键打包成一个字）**：见 B6——同样落到 16 B，但锁字仍在块头、不需要反查表；
  代价是每个检查点几条 ALU 与键位宽/对象跨度两处语义上限。这是 16 B 家族的另一个实现（§3.3 讲的是
  反查形态，§3.6 讲打包形态）。
- **TBAA/别名元数据让 LLVM 提升锁槽 load**：负载 store 与锁槽 load 都是 opaque pointer，
  别名信息可以补，但 LICM 还要求锁槽 load 可无条件解引用，证明不成立（方向 A 已评估）。

## 3. 候选设计

### 3.1 B1：`index`/`size` 压到 32 位（`T*` 40 → 32 B）

**布局**：`{data:ptr, lock_ptr:ptr, key:u64, index:u32, size:u32}` = 8+8+8+4+4 = **32 B**，align 8。
切片与引用不变（32 / 24 B）。

**改动**：字段下标不变；`index`/`size` 的读写处加截断/扩展；检查用 32 位比较（`icmp ult i32`）；
指针算术的良构/无回绕在 32 位域上做，另加一次"和不超过 2^32-1"的检查或把溢出归入 R001。
视图构造时校验 `size ≤ 2^32-1`（元素数与字节跨度都要能表示）。

**收益**：`T*` 及其所在结构小 8 B；追逐曲线 40 → 32 B 约 −16%；调用侧只有拷贝收益（仍在内存档）。
受影响的基准主要是 `permute`/`storage`/`towers` 与任何 `T*` 字段密集的结构。

**风险**：单对象元素数/字节跨度 > 4 GiB 的程序会从"能跑"变成"报错"（需要显式定义上限与
R001 诊断）；指针算术与 one-past 的边界条件要在 32 位域上重新逐条对照；`index`/`size` 参与
比较/差值的语义要与 u64 版逐项等价。

**工作量**：小到中（中心函数少，但 `-t ll` 的形状与全部检查都要重测）。

### 3.2 B2：胖值按标量传参的调用约定（不动布局）

**做法**：把胖值的**参数**从"按值聚合"改成"按字段拆成多个标量"（返回值不变，见下）：
`f(s: T[])` 的 LLVM 签名从 `({ptr,ptr,i64,i64})` 变成 `(ptr, ptr, i64, i64)`；
形参在函数体内重新合成聚合（`insertvalue`），调用点拆分（`extractvalue`）。

**收益依据**：§2.2(a) 里 40 B 拆标量省 ~10%、32 B 拆标量省 ~9%；更重要的是**≤16 B 档才是质变**
（+0% vs +33%），而拆标量后 24 B 的 `T&` = 3 个寄存器、32 B 切片 = 4 个寄存器，
都落在寄存器窗口内（SysV 整数寄存器 6 个）。

**必须处理的细节**：
- **寄存器窗口**：一个调用点里所有整数参数共享 6 个寄存器；胖参数多了会溢出到栈，可能比
  聚合传参更差。需要按签名决定：整数参数总数（含拆分后的字段）≤ 阈值（4–5）才拆，否则
  维持聚合传参（调用者与被调用者用同一个判定，签名由类型 id 唯一决定，天然一致）。
- **返回**：SysV 只给 2 个返回寄存器，24/32/40 B 的返回值仍必须走 sret（内存）。**返回不做改动**，
  这一条要写进计划，避免期待落空。
- **函数指针/`fn` 类型**：拆分会改内部 ABI 签名，所有 call/invoke/间接调用与函数类型构造要一起改；
  `Option<fn(...)>` 的 niche、函数指针比较等不受影响，但签名必须全局一致。
- **stdlib 边界**：`@sys_write` 这类内建与标准库里手工合成的胖值要按新约定处理。

**收益估计**：调用密集的基准（havlak/json/deltablue/richards/list 的调用点分别是 438/355/236/100/34）
受益最大；预期是"每个含胖参的调用省 10–40% 的传参成本"，整基准量级待原型测量。

**风险**：中。语义零变化（纯粹是内部调用约定），但生成代码形状变化大，需要全量基准与三套件回归；
LLVM 是否把拆分后的参数保持在寄存器里要靠实测确认（`-O2` 的寄存器分配可能又塞回栈）。

**工作量**：中（签名构造/调用下降/定义下降/stdlib 边界四处，判定逻辑集中）。

**实测结论（否决）**：原型按上面的设计落地了参数侧（24 B 的 `T*`/`T[]`/`str` 拆成字段、
16 B 的 `T&` 不动、按签名整型槽数 ≤ 6 决定拆或整块传、call/定义/间接调用三处共用同一份判定），
三套件全绿；但**生成的机器码与聚合传参逐指令相同**（`call_abi` 与 `list.an` 的指令助记符
多重集完全一致，二进制只差 2 条寄存器分配），交替 A/B 实测也是 0（−0.1%~+0.1%）。

原因是**收益依据本身不成立**：§2.2(a) 的曲线来自 C 微基准，而 C 的结构体参数经 clang 下降为
`byval`（强制按内存传，`movl 24(%rsp)` 一类）。LLVM IR 的**一等聚合参数**走的是另一条路——
x86-64 后端把它按八字节逐个拆进 SysV 的整型寄存器序列（`{ptr,i64,i32,i32}` 落 4 个寄存器，
`{i64×10}` 落 6 个寄存器 + 4 个栈槽），根本不经过"超 16 B 一律 MEMORY"那条规则。也就是说
YIAN 今天传胖值**已经是**寄存器传参，B2 只是把后端已经在做的事在 IR 上又写了一遍。
（返回值一侧 LLVM 确实走 sret，与计划的判断一致；但那是另一条规则。）

### 3.3 B3：16 B 指针（⟨data, key⟩ + 地址反查）——最大收益，最大代价

**想法**：指针只留 `data` 与 `key`（16 B，进寄存器档），`lock_ptr` 不再随指针走；`live` 通过
"地址 → 块"反查得到锁槽，再比较键。反查需要分配器配合：块必须能从任意内部地址定位，
例如按页（4 KiB）维护"页 → 块"的边表，或把块按尺寸对齐让 `data & ~mask` 直接落到块首。

**收益上限**：`T*` 40 → 16 B、`T[]` 32 → 24 B（还要留 size）、`T&` 24 → 16 B。
按 §2.2(b) 的曲线，对象节点 32 → 24 B 约 −20%、24 → 16 B 约 −26%，且所有胖值进寄存器档；
这是唯一能同时改善"驻留 + 传参"的方案。

**代价**：`live` 从"1 次 load（锁槽通常与负载同 cache line）"变成"1–2 次额外依赖 load + 表格维护"；
分配器要维护边表（free 时清理），`madvise` 退页与悬垂读的语义（S003/S006）要重新论证；
`T&` 的 `size`/`index` 语义要在新布局下重新定义（引用无空间分量，切片要带 size）。

**结论**：作为**可行性原型**排在 B1/B2 之后，只有前两项的实测收益明显不足、且对象密集型基准
的瓶颈被确认为"节点尺寸"时才启动。启动前要先测"当前 `live` 的实际命中率与延迟占比"，
否则可能用一个更贵的检查换一个更小的指针。

### 3.4 B4：用"末端地址"取代 `index` + `size`（32 B）

**布局**：`{data:ptr, end:ptr, lock_ptr:ptr, key:u64}` = 32 B；访问检查变成
`data + |T| ≤ end`（含无回绕），算术只更新 `data`，比较/差值直接用地址。

**优点**：边界检查少一次"乘/取 size"；比较语义更直接；`T*` 从 40 → 32 B。
**缺点**：切片的 `len()` 需要除法（或切片另存元素数，则切片仍 32 B）；与今天的
`index`/`size` 语义逐条对齐要重写检查与文档；收益与 B1 同量级而风险更高。

**结论**：列为 B1 的备选（若 B1 的 32 位上限不可接受，再考虑 B4）。默认不做。

### 3.5 B5：视图构造与转换的消解（不是表示改动）

`T[] → T&` 退化、`ptr()`/`as_slice()` 往返、`Option` 解包处的 `insertvalue`/`extractvalue` 密集

### 3.6 B6：锁址与键打包成一个字 + 32 位元数据（16 B 引用，无侧表）

**原型实测（已完成，见 §5 P2.4）**：C 原型用**随机链序**让追逐成为延迟受限（4M 节点、5 轮取最小）：

| 形态 | 节点 | ns/节点 | 相对 today |
| --- | ---: | ---: | ---: |
| 无检查（chase 本身） | 32 B | 19.01 | +1.0% |
| today（锁址在指针里，1 次 load + 比较） | 32 B | 18.83 | — |
| B6 全 kind 分派 | 24 B | 17.24 | **−8.4%** |
| B6 只算 slab kind（分派成本下界） | 24 B | 17.29 | −8.2% |
| 证书/槽表（16 B 指针 + 8 B/对象侧表） | 24 B | 19.20 | **+2.0%** |

同构的拷贝负载（DRAM 规模，4M 元素）：32 B/元素 0.310 ns vs 24 B/元素 0.220 ns（**−29%**，约等于尺寸之比）。

结论：**延迟受限时检查本身是免费的**（无检查 19.01 ≈ today 18.83），B6 的收益来自每节点少 8 B；
kind 分派只占 ~1.4%；**证书/槽表方案反而更慢**（侧表多出的 8 B/对象流量吃掉指针变小的收益），
因此按原设计走"打包锁址"，不做侧表。真实每对象足迹还要算块头（仍 16 B —— 缩小它已被实测否决，见下节），
实际差距比原型更大。

口径提醒：只有 4M 节点（超出 LLC）那一档可信；把工作集缩到 L2/L3 之后 C 原型里整条链会被
优化器折叠（读数降到 0.1 ns/节点以下，不可能是真实追逐），小工作集的结论交给端到端的 YIAN
基准（`--set micro` / `--set ptr`）来出。

**编码（实现基线）**

```
word   = ⟨kind:2 | field | id⟩                  ; 16 B 引用的第二个字
lock   = <按 kind 重建: 堆 = (data & ~mask) | field; 帧 = arena + depth*8; 字面量 = 常量>
live   = load64(lock) == word                   ; 块头/槽里存**整字**, 比较与今天同价
is_heap= (word >> 62) == KIND_HEAP              ; 只有堆对象带块头（视图/删除检查的开关）
块头   = { word:u64 @0, extent:u64 @8 } = 16 B  ; 首字放整字; extent 是负载字节数
```

**块头保留 16 B**（不缩到 8 B，理由见下节实测）：首字存完整 word，于是 `live` 仍是"一次 64 位
load + 一次 64 位比较"，与今天同价；缩小指针靠的是把 `lock_ptr + key` 两个字并成 word 一个字，
而不是缩小块头。代价只是块头里多存了一份从地址可推导的 field 位。

| 来源 | kind | field | 槽在哪 | 谁维护 |
| --- | --- | --- | --- | --- |
| 堆对象（slab 与大对象） | 11 | 块首地址低位（窗口内） | 块首 16 B 首字 | 分配时写整字（新代），释放时换代（旧指针立刻失配） |
| 函数帧 | 10 | 影子栈深度（20 位，id 42 位） | arena 8 B 槽（不变） | 帧进入写新字，全部返回路径写 SENTINEL |
| 字符串字面量 | 01 | — | 全局字面量锁槽（不变） | 常量，永不过期 |
| 环境/进程参数 | 00 | — | 全局环境锁槽（不变） | 常量，永不过期 |

帧与字面量**不改机制**（影子栈与全局槽都保留），只有"槽里存什么、指针怎么找到它"变了：
堆/帧/字面量三条地址公式由 kind 选，字面量/环境的比较是常量，因此重建是一段 3~4 路的
选择或分支（原型实测这部分 ~1.4%）。

为什么不用"按 kind 分派重建"（上一版）：待重建的公式有 4 个、位宽还各不相同，热路径上是一条
~13 条 ALU 的选择链（分支版则会切基本块，B1 已经证明检查引入的额外块会扰动优化）。改成
"**把所有锁槽都放到与数据同一个 4 GiB 窗口内**"之后，地址重建退化为 `and / or` 两条，检查回到
"1 次 load + 1 次 32 位比较 + 2~3 条位运算"，与今天（1 load + 1 比较）几乎持平。

**随之改变的机制（都要同步文档）**

1. **锁槽位置不动**：堆块头首字、帧锁影子栈 arena、字面量与环境的两个全局锁槽都保留。
   变的只是"指针里存什么、怎么从 data 找到锁槽"。
2. **分配 ABI 不动**：分配器仍返回块基址；编译器仍自己写块头（现在写整字 word + extent），
   `data = block + 16`。块头字段含义变化（首字从"键"变成"整字 word"，其中已含键/代）。
3. **地址重建按 kind**（三条公式，不是一条）：堆 = `(data & ~mask) | field`（分配器保证对象不跨
   窗口，大对象已按此落点）；帧 = `arena + depth*8`；字面量/环境 = 两个链接期常量。
   `is_heap` 只用来开关"视图/删除要不要读块头"。
4. **代（id）语义**：堆的 id 32 位、**按块换代**（分配与释放各 +1，悬垂指针立刻失配）；
   帧的 id 42 位来自全局单调计数器（耗尽报 R003，与今天一致）；字面量/环境是常量。
   因此 §4.4 只在"同一个块被复用 2^32 次且旧指针一直存活"这一点上需要放宽说明，
   帧与字面量保持"不回绕"。
5. **负载长度仍是块头里的 extent（u64 不变）**：不需要新的字节上限，B1 的
   "元素数 ≤ 2^32-1"照旧。

### 3.7 8 B 字的两个变体（A：kind 在字里；B：统一槽下标表）

用户口径：**key 与 lock 严格同宽**（不再出现"堆 32 位代号 / 帧 64 位键"的混合宽度），块头 8 B，
extent 记**元素数**（沿用 B1 的"单对象 ≤ 2^32−1 个元素"，不引入新的字节上限）。
8 B 块头在 YIAN 里不损失对齐：语言只有 i8..i64 / u8..u64 / f32 / f64 与指针，
最大对齐 8，负载锚 `block+8` 恒 8 对齐（§3.6 的 16 B 块头只为放整字而存在）。

**变体 A（kind:2 | key:30 | lock:32）**

```text
word  = ⟨kind:2 | key:30 | lock:32⟩            ; 指针第二字（8 B）
块头  = { key:u32 @0, extent:u32 @4 } = 8 B    ; 负载从 block+8 开始（8 对齐）
lock  = 堆: (data & ~0xFFFFFFFF) | lock32      ; 4 GiB 窗口（运行时已按 4 GiB 落点）
        帧: arena + lock32*4                    ; lock32 = 影子栈槽下标
        literal/env: 两个链接期常量槽
live  = load32(lock) == key                    ; 恒 32 位比较（无宽度分派）
key   = 堆: 每块 30 位换代（分配/释放各 +1）；帧: 30 位全局计数器（耗尽 R003）；literal/env: 常量
```

**变体 B（统一槽下标表，零分派）**

```text
word   = ⟨lock:32 | key:32⟩                    ; 指针第二字（8 B）
表项   = { anchor_lo32:u32 @0, key:u32 @4 }    ; 全局表，8 B/活对象
块头   = { extent:u32, pad:u32 } = 8 B         ; 载负载元素数；负载锚 = block + 8（8 对齐）
live   = load32(TABLE + lock*8 + 4) == key     ; 一次 load32 + 一次比较：无 kind、无窗口
帧槽   = 保留下标段 [0, 2^20)（下标 = 影子栈深度，项里存帧 key）
字面量/环境 = 保留固定下标，项里存常量 key
堆     = 下标 ≥ HEAP_LOCK_BASE（由分配器发放；释放时把下标还回空闲链）
```

**为什么表项是 8 B 而不是 4 B**：4 B 只装得下 key，`del` 就找不到块首（指针里只有
下标，而 `data` 对重锚定引用不等于 `block + H`）；把 `anchor_lo32`（负载锚地址低 32 位）
一并存进表项后，`live` 仍是"表里读一次 + 比较"（热路径无窗口、无 kind），
而 `del` 的锚点/整块判定走冷路径、用已提交的 4 GiB 窗口公式还原块首。
表项与块头合计 16 B/对象（与今天的 16 B 块头相同），换来指针小 8 B 与零分派；
代价是每次检查多碰一个独立数组（多一条 cache line）。

**共同点**：`T&` 16 B、`T[]`/`str` 24 B、`T*` 24 B。
**差异**：A 每次检查仍要按 kind 选锁址公式（`icmp×3 + select×3` + `ptrtoint` 往返），B 只查表；
A 每对象无额外内存，B 每对象多 4 B 表项；A 带 4 GiB 窗口与 30 位 key 两处语义上限，B 无窗口约束、key 32 位。
**A 实测记录（已实现、已跑完 micro/ptr/full/alloc）**

帧锁槽存 32 位 key（arena 仍是 8 B 槽，读低 32 位比较）、key 上限 2^30 → R003。

8 B 头本身没有带来结构性改善——`live` 确实回到了 32 位同宽比较，但比较不是瓶颈，重建才是。
A 代码回退，数据留在上表。

**B 实现记录（已实现、门槛全过）**

- 锁表：`__secl_lock_table`（`[LOCK_TABLE_SLOTS x i64]`，BSS，页按触达常驻）。
  下标区间自带 kind：[0, 2^20) 帧槽（下标 = 影子栈深度）、字面量/环境两个常量槽（key = 0，
  即 BSS 初值，无需运行期初始化）、其余由 `__secl_lock_new` 发放给堆对象。
- 表项 = `{key:u32 @0, anchor_lo32:u32 @4}`；空闲链串在 anchor 字段（值 = 下一空闲下标 + 1）。
  发放与释放都把 key +1，因此"释放后未再发放"的窗口里悬垂指针也已失配。
- 指针 word = ⟨key:32 | lock:32⟩；块头 8 B 只剩 extent（元素数）；`live` = `word ≠ 0 ∧
  load32(表项.key) == key`（一条 GEP + 一次 32 位 load + 一次 32 位比较，无 kind、无窗口）。
- 冷路径（删除/整块视图）用表项 anchor_lo32 + data 高 32 位还原负载锚，再 -BYTES 得块首。
- 空数组字面量槽改指锁表的字面量段（原先借 `__yian_lit_lock` 的地址，B 里已无此全局）。

落地中修掉三处错：`__load_active_size` 仍把 lock 当块首（B 的 lock 是表项，必须从还原出的块头读
extent）、`delete` 还原块首时漏减 `BYTES`、切片语义下标 3 未折到 3 字段布局（提取端与 `sys_read`
构造端，与 A 同源）。门槛：三套件 756/156/99 全绿（fat 与 raw）、`runtime/build.py --check --asan`
通过、三个最小复现用例（堆/帧/字面量）通过。

**B 实测记录（已跑完 micro/ptr/full/alloc）**

**B 否决，保留 B1。** 读数把代价与收益分得很清楚：

- **收益是"内存足迹"**：指针小 8 B 在指针/堆密集且工作集大的负载上直接兑现（`list` −51%、
  `json` −11%、`storage` −12%、`queen`/`binarytree` −8%）。
- **代价是"每次检查多一次表 load + 每次分配多一次表项发放"**：紧循环里每次检查都要碰一个
  独立数组（`copy_struct` +116%、`chase` +15%），分配密集负载还要为每个对象发放/回收表项
  （`churn_*` +86~108%、`grow_free` +521%，而 RSS 没涨，说明不是内存而是指令/访存路径）。
- 中位数虽然只有 −0.1%，但分布是双峰的：一批 −3%~−51% 与一批 +9%~+116% 并列。按 §4.4 的
  验收口径（单项不得越出噪声带），B 不通过；它要成立需要先去掉"每次检查一次表 load"，
  那是另一个设计（例如把锁槽留在块头、只把身份放进表，或降低检查频次），不是这一版。

**B 最小修复重测（第 9 轮：三处修复后 B 反超 B1）**

根因（callgrind + 反汇编 + 优化 IR）：B 的失败不是"多几条 ALU"，而是**表示改动把优化器的
折叠/提升/内联/向量化整条链掐断**——

- B1 里锁槽与负载是**同一个分配的两个常量偏移**（`block` 与 `block+16`），BasicAA 能证明不别名，
  刚分配后的 `live` 检查被 store-to-load 折叠、批量初始化得以向量化（`movups`）；B 的锁槽在
  **全局数组**里，payload store 与它"可能别名" → 循环里的锁表 load 既不能提升也不能折叠。
- 未修复 B 的 `grow_free`：4 KiB 归零退化成"每字节一次 `cmp` 锁表 + 一次 `movb`"的循环
  （4 条 × 4096 字节 × 163,840 块 = 3.35e9 条 = 该基准总指令的 98%；B1 是 16 字节向量存储）；
- 未修复 B 的 `copy_struct`：`index` 辅助被调用 2.05e8 次、每次 39 条 = 8.0e9 条（占总指令一半），
  B1 里它被内联消除（总指令 2.98e9）。

三处修复（全部落地）：

1. **锁表发放内联化**：malloc 的快路径改在发射的 IR 里做（自由链非空 → 弹出下标、把新链头写回
   全局；`key+1`、写 anchor、组装 word 也全在 IR 里），只有自由链为空才调 `__secl_lock_bump_take`。
2. **刚分配内存的检查在编译器侧消失**：CFG 侧新增 `__live_known`（当时写在 `cfg/builder.py`；
   现已外化为 `IR.LiveKnownBegin/End` 标记 + 检查插入 pass 的窗口），`__resolve_dyn_buffer`
   在填充循环期间登记缓冲出处，`__build_load/__build_store` 与帧锁同等对待（只跳过 live 项，
   in_bounds 照常）。这是关键修复——它让 LLVM 不必再做跨全局数组的别名推理。
3. **索引辅助强制内联**：`module.declare` 对 `index.*` 辅助加 `alwaysinline`（B 下它变胖后掉出
   内联阈值，每个元素多一次跨函数调用）。

第 3 项曾评估为"别名约束"（alias scope / TBAA），结论是**不做**：残余回退里 `churn_*` 是每次访问
一个新指针（load 不是循环不变的，alias 约束帮不上），`copy_struct` 是辅助函数体积问题（已由
强制内联解决），因此 alias 元数据既不是主因、又有静默误编译风险。

**修复后实测（min-of-5，pin=4；基线 = B1 的 `1a89010` 记录）**

full 集合（fat，负 = 更快）：`list` **−51.4%**、`deltablue` **−25.3%**、`copy_struct` **−22.7%**、
`havlak` **−19.9%**、`json` **−18.8%**、`storage` −12.1%、`richards` −9.0%、`queen` −8.0%、

#### 3.7.1 三项回退的后续调研（结论：拿不回来，除非换回 B1 布局）

对 `towers` / `chase` / `churn_single` 做了三条路的实测，全部否掉：

1. **CFG 层"检查融合"**：把 live 去重键从"分配锚点"改成"锁字段出处"，让同一指针的所有
   `FieldPtr`/`ElementPtr`/`Cast` 派生共享 live 键、同块内后续访问只查 `in_bounds`。
   108 份语料的语义校验只降不增，但 9 个基准 A/B 全落在噪声内（`towers` 4839.6 → 4875.7 ms）——
   **LLVM 已经对相同条件做了 CSE 与分支合并**，CFG 层少一个检查节点不改变机器码。
2. **LLVM 发射层"分支融合"**：把一个"检查 + 纯地址运算"窗口内的检查合成一个热路径分支，
   失败时按原顺序冷路径重测、报原错误码。热路径分支数确实下降（`push_disk` 安全检查分支 5→3，
   且融合形态存活到 `-O2` 后 IR），但 9 个基准 A/B 仍全在噪声内（`towers` +0.1%）——
   省下的分支与合取新增的 `and` 等值：**分支本身近乎免费，代价在每条检查的指令数**。
3. **表示层"锚定指针直接读块头 key"**（把 key 从全局表搬回块头，块头仍是 8 B）：callgrind
   `--cache-sim=yes` 显示锁表 load **不产生额外 cache miss**（D1/LL miss 与"读数据自身行"逐项相同），
   代价在指令数；而要把锚点放进指针（word 已满，需借判别位）后，读块头 key 的两条还原指令与今天的
   下标算术**等值**，拿不到 B1 那种 `load(data-16) == key` 的便宜形态。

**归因（同机实测）**：`live` 占 `towers` 43%（锁表 load 链 ≈25% + 分支/比较 ≈18%）、`json` 9%、
`churn_single` 7%、`chase` **0%**（`chase` 与检查无关，是节点布局/足迹）。B1 之所以便宜，是它的
指针直接携带绝对锁槽地址 + 64 位 key（`live` 只剩 load + icmp 两条），代价是 `T&` 24 B / 块头 16 B。
**16 B 的 `T&` 装不下"全地址 + 全 key"**——B 的紧凑（`json`/`churn_mixed` 的大赢）与 B1 的便宜 `live`
是同一枚硬币的两面，因此这三项按现状接受，不再有检查层的优化空间。

### 4.1 新增微基准（`bench/fatptr/`）

方向 B 的效果在 shootout 里会被检查开销与算法结构淹没，需要三个专项基准：

### P2.2 B2 调用约定原型（优先做）——**已做，实测否决（不改代码）**

**工作**：按 §3.2 实现"整数参数窗口内拆标量"，含签名判定、call/invoke/定义下降、stdlib 边界；
**先只做参数，不做返回**。

**实测**：参数侧原型落地（`SPLIT_FAT_PARAMS` 一处开关；24 B 的 `T*`/`T[]`/`str` 按字段拆、
16 B 的 `T&` 不动、按签名的整型槽数 ≤ 6 决定拆或整块传；直接调用、间接调用、函数定义三处共用

但：

- **机器码与基线逐指令相同**：`call_abi` 的 `.s` 指令多重集完全一致（3467 条，逐助记符计数相等），
  整份二进制只差 2 条寄存器分配；`list.an`（870 条）同样一致。
- **交替 A/B 实测 0**：`call_abi` min 37.24ms（拆）vs 37.26ms（不拆）、中位 40.41 vs 40.09；
  单链 A/B（只跑接收 1 个胖参的链）min 差 +9.6% 但中位 −0.4%，与"机器码相同"一致，属机器
  双态噪声。raw 态两种设置下**二进制逐字节相同**（md5 相等），是完美的噪声对照。

**原因**：LLVM 的 x86-64 后端把**一等聚合参数**按八字节拆进整型寄存器序列，不套用"超 16 B
一律 MEMORY"那条规则——后者只作用于 C 侧 `byval`（§2.2(a) 的 C 曲线就是这么来的）。也就是说
胖值参数今天已经走寄存器，B2 没有可动空间；返回值一侧确实走 sret，但那条规则 B2 不碰。

**回退**：原型改动已整体还原（判定开关、签名构造、调用点拆分、定义侧重组四处），工作树只保留
`bench/fatptr/` 的三件基准与本节记录。重新评估这一项没有意义，除非将来上马会改变**返回值**
传递方式的布局（例如 B3 的 16 B 指针）。

### P2.3 B1 32 位打包原型

**工作**：`index`/`size` 压 32 位 + 构造期上限检查（新诊断或复用 R001）；检查/算术/比较按 32 位重写。
**验收**：`copy_struct`/`chase` 有可解释的改善（40 → 32 B 约 −10~16% 的对应部分）；
全部语义清单通过；文档与 `@sizeof` 断言同步。
**回退**：字段宽度与检查宽度是集中常量，可回退。

**进展（实现完成，待完全档记录）**：聚合改成 `{ptr, ptr, i64, i32, i32}`（32 B）；提取端 `index`/`size`
零扩展到 u64、写入端截断（收窄只发生在 `index`/`size` 两处）；`@sizeof` 断言与类型/映射/错误码文档同步；
三套件全绿（756/156/99）+ `runtime/build.py --check --asan` 通过。

上限检查的落点是这一项的关键，实测走过两版：

1. **构造点全检查**（`malloc` 元素数 + 切片/`{T*,u64}` 长度）：完全档 fat 态整体退化——deltablue +9.7%、
   havlak +8.0%、fasta +5.8%、binarytree +4.9%。raw 态中位 +0.4%（噪声底），说明代价确实出在胖指针路径。
   逐点定位：把三处检查关掉后 deltablue 回到 −0.5%、havlak +0.5%；`-O2` 之后的 IR 里这些比较其实已被
   折叠（最终机器码几乎相同，指令数差 1.5%），代价来自**检查引入的额外基本块改变了优化/布局决策**
   （互测同一份代码：6.76 s ↔ 7.99 s 级别的稳定差异）。
2. **只在分配处检查**（当前实现）：视图长度都来自某个分配的容量，而分配元素数已在 `malloc` 处校验
   ≤ `MAX_VIEW_COUNT`，所以衍生视图必然可表示，不需要在每个切片构造/`T[]→T*` 派生处再查。
   另外把 `malloc` 的上限检查与原来的 i128 溢出检查合并（先卡元素数上限 ⇒ 元素数×元素大小必然落在
   u64 内），热路径上的宽整数乘法因此消失。`ptr` 集合结果：deltablue −2.1%、havlak −4.0%、
   binarytree −0.9%、queen +0.7%、其余 ±0.6%，raw 全项 ±0.8% —— **无项退化，若干项改善**。
   编译期数组退化长度另加静态上限检查（`__check_static_view_count`，无运行时成本）。

**残留假设（写进文档，不在热路径上兜底）**：一个长度**没有**对应分配、却超过 `MAX_VIEW_COUNT` 的视图
（只能由标准库内部的 `{ptr, len}` 原始构造产生），在转成 `T*` 时长度会被截断成较小值；截断只会让视图
变小，因此不产生越界，但会静默改变语义而不是报错。等出现真实的原始构造路径时再按 provenance 精确设卡。

**第三版试验（检查改 32 位原生，未采用）**：把良构/in_bounds 改成字段位宽内比较（`icmp u32`、offset
先卡 2^32、32 位和 + 回绕检测），并在 `element_ptr` 里用 32 位加法更新 index。它对直筒型 `T*` 访问有
好处（fasta +6.2% → +3.4%、nbody +4.2% → −1.1%），但**循环型基准反而退化**（sieve −0.7% → +5.7%、
revcomp +0.8% → +5.6%）：`check_element_arith` 的注释里已经写明"u64 同型使 ConstraintElimination 可
关联循环/分支约束消除本检查"，改成 32 位后这类消除不再发生，循环里的检查留了下来。
结论：**保留 u64 同型的检查形式**（字段仍按 32 位存储，只在检查/地址计算处提升），账面上"少几条
zext"不等于更快。这条与"检查的**存在**比检查的**内容**更影响性能"是同一现象的两面。

**方法论结论（用于后续候选的验收口径）**：本机上**不同二进制之间**的逐项差异里，有 ±3–6% 来自代码
布局/对齐，而不是机制成本——同一份源码重编两次的差 ≤0.5%，但只改 4 条 IR 指令（bounce 的 v3 vs pre）
就能稳定差 4%；把某处检查整段删掉（deltablue 6.76 s ↔ 7.99 s）也是稳定差 15%。因此：
1. 验收要同时看**中位数**与**分类**（哪些基准是 `T*` 密集、哪些是循环密集），不能只看单项；
2. 单项 ±3% 以内的差异先当布局噪声，±5% 以上才值得逐项查（用 equal-length 路径的交替 A/B 复核）；
3. raw 态（不受表示改动影响）永远作为同一轮的噪声对照。

**B1 收尾（完全档记录，21 项：19 shootout + 2 微基准）**：fat 中位 +0.1%、raw 中位 +0.1%（噪声底），
`T*` 密集项明显改善——json −9.6%、havlak −5.3%、deltablue −4.5%、cd −2.8%、permute −2.7%；
bounce/nbody/fasta/copy_struct 退化 +3.0%~+5.8%（fasta 已用 equal-length 交替 A/B 复核为真实差异，
其余在布局带内；copy_struct 的 raw 态同轮 +4.2%，说明该微基准规模偏小）。峰值 RSS 无项上升
（havlak 9.6→9.0 MB、json 2.2→2.0 MB，正是指针变小的预期）。三套件（756/156/99）+
`runtime/build.py --check --asan` 全绿；边界语义与 pre-B1 逐条一致（`p + 2^32`、`p + 2^64-1` 均报 S004，
正常访问与 one-past 行为不变）。

净账：整基准中位持平、四项 >3% 改善（合计约 −25%）对三项 >3% 退化（合计约 +13%）；B1 的字段打包同时是
B6 的 `T*` 布局前提（`{data, word, index:u32, size:u32}`），因此当时保留、不做回退。

**后续（本阶段状态已变）**：B1 后来被**变体 B**（8 B 块头 + 全局锁表 + 三处修复，见 §3.7）取代——
`T*` 24 B、`T&` 16 B、`T[]`·`str` 24 B，身份从块头搬到全局表项。B1 自此只作为对比基线。

### P2.4 16 B 引用可行性原型（B6 先行，B3 备选；依 P2.2/P2.3 结果决定）

**工作**：先做 B6（§3.6）的纯 C 原型——同一 `chase` / `copy_struct` 负载写三版（今天：锁字在块头、
指针 24 B；B6：重建锁址 + 16 B 指针；B3/槽表：多一次 load 或侧表），分离"ALU vs 额外 load vs 指针尺寸"
三项各自的贡献；再用 `ALLOC` 四项量 8 B 块头与按类计数器的开销。通过后再在**一个基准**（如 `chase`）
上做"16 B 指针"的端到端原型，量"检查变贵多少、节点变小省多少"。
**验收**：给出取舍结论（做 / 不做）与数据；若决定做，再写独立的迁移计划。

**进展（C 原型：做；YIAN 端到端：否决）**：随机链序的延迟受限追逐（4M 节点）里，无检查 19.01、
今天 18.83、B6 全分派 17.24、B6 只算 slab 17.29、证书/槽表 19.20 ns/节点；同构拷贝（DRAM 规模）
32 B/元素 0.310 ns vs 24 B/元素 0.220 ns。即：**延迟受限时检查免费、收益来自尺寸**，kind 分派
约 1.4%，**槽表方案更慢（不做）**。

按 §3.6 实现完 B6 编码后，YIAN 自己的 micro / ptr / alloc 三组端到端读数全面退化
（`copy_struct` +249%、`havlak` +196%、`deltablue` +179%、`towers` +116%、`richards` +106%，
分配器 churn +176%~+534%，raw 对照 ≤3.4%；详见 §3.6 表）：重建锁址的每检查成本压过了
指针变小的带宽收益。**B6 因此否决并已回退**；重启的前提是"检查点静态 kind
专用化"（见 §6）。C 原型与端到端的口径差见 §6 最后一条。

**后续（本阶段目标已达成）**：16 B 引用由**变体 B** 实现（`T&` = ⟨data, word⟩ 16 B，`T*` 24 B），
即"不重建锁址"的 16 B 形态；B6 与变体 A 均否决。B 的代价是把"每次检查的锁址重建"换成"每次检查
一次表 load"，收益在指针/堆密集处兑现（§3.7），三项回退见 §3.7.1。

## 6. 风险与开放问题

- **收益可能被高估**：§2.2(b) 的曲线是"纯追逐"，真实基准里追逐与计算交织，节点尺寸的敏感度
  会低一些；所以 P2.1 的基数必须先测，再决定投入。
- **ABI 拆分已被实测否决**（原"可能被 LLVM 抵消"）：胖值参数今天已经走寄存器——LLVM 的 x86-64
  后端把一等聚合参数按八字节拆进整型寄存器序列，改签名后机器码逐指令相同（§5 P2.2）。传参档位
  对方向 B 没有可动空间。
- **32 位上限是语义收缩**：`index`/`size` 压 32 位会让"单对象 > 4 GiB 元素跨度"从可用变成报错，
  需要明确写进诊断与文档（这是一个对外可见的限制）。
- **B3 会改动机制**：`live` 的实现方式、分配器的元数据、悬垂读语义都要重新论证；风险等级高于
  B1/B2，收益也最大，建议只做原型。
- **B6 的两处语义上限**（只在重启该路线时适用）：键位宽（按 kind 36–50 位，耗尽仍 R003 终止）与
  "大对象不跨 `2^k` 窗口"（分配器约束 + 虚拟地址浪费）都必须写进诊断与文档，并纳入 §4.3 验收清单；
  固定 32 位键会让回绕变得可达，不采用。
- **B6 已实测否决**：端到端上"重建锁址"的每检查成本（约 10 条 ALU + 指针 select 链，`-O2`
  主函数 +47% 指令）压过了指针变小（8 B/指针）的带宽收益，micro / ptr / alloc 三组全面退化
  （见 §3.6 表）。只有在"检查点静态已知 kind、只走堆公式"的专用化落地后才值得重测。
- **变体 B 的三项已知回退已定性**（`towers`/`chase`/`churn_single`）：三条优化路（CFG 融合、发射层
  分支融合、锚定指针读块头 key）逐条实测为零收益或不可行，见 §3.7.1。它们与 B1 的 16 B 指针布局
  绑定，因此"消除回退"与"保留 `json`/`churn_mixed` 的大赢"不可兼得，属已接受的取舍，不再作为开放
  问题跟踪。
- **`-O0` 未纳入**：本计划与主计划一样只以 `-O2` 基线验收；如果 `-O0` 也需要，验收要分档。
- **C↔YIAN 的口径差**：§2.2 的曲线来自 C 微基准，只用于判断方向与量级，不作为 YIAN 的收益承诺。
  已经踩过一次：C 的结构体参数经 clang 变成 `byval`（强制按内存传），而 YIAN 传的是 LLVM 一等聚合
  （后端按八字节拆进寄存器），同一条曲线的结论正好相反（§3.2/§5 P2.2）。凡涉及调用约定/参数传递的
  结论，必须在 `-t asm`/`-t bc -O2` 上复核，不能借 C 侧读数外推。
